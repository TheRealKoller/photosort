# 0006 - Auth-Implementierung

**Status:** Accepted
**Erstellt:** 2026-07-20
**Akzeptiert:** 2026-07-20
**Bezug:** Als fehlendes Prerequisite beim Schärfen von Spec 0002 (Manuelle Kategorisierung) entdeckt und seit der Schärfung von Spec 0005 (Minimales Projekt-Frontend) als deren direktes, blockierendes Prerequisite bestätigt. ADR [`decisions/0003-auth-model.md`](../decisions/0003-auth-model.md) legt das grundsätzliche Modell bereits fest. Jetzt im idea-sharpener-Gespräch vom 2026-07-20 selbst geschärft.

## Ziel

Zwei bekannte Nutzer (Daniel und seine Frau) können sich am Backend authentifizieren, sodass geschützte Endpunkte eine `user_id` verlässlich und fälschungssicher ableiten können — Grundlage für nutzerbezogene Bewertungen (Spec 0002) und für den Login-Screen im Frontend. Diese Spec ist die erste sichtbare Oberfläche von PhotoSort überhaupt (kommt zeitlich vor Spec 0005) und die erste echte Sicherheitsgrenze des Systems.

## User Story

Als Daniel (oder meine Frau) möchte ich mich mit meinem Benutzernamen und Passwort in PhotoSort einloggen, damit meine Kategorisierungen eindeutig mir zugeordnet werden — ohne mich bei jedem Besuch neu anmelden zu müssen, solange ich mein eigenes Gerät benutze.

## Akzeptanzkriterien

**Backend — `/auth/login`**

- [ ] `POST /auth/login` mit korrektem `username`+`password` → `200`, Body enthält nichtleeren `access_token` (String) und `token_type: "bearer"`.
- [ ] `POST /auth/login` mit falschem Passwort für existierenden User → `401`, generische `detail`-Meldung (fester, dokumentierter Wortlaut, z.B. "Ungültige Anmeldedaten").
- [ ] `POST /auth/login` mit unbekanntem Username → `401` mit identischem Response-Body (Status + `detail`) wie beim Fall "existierender User, falsches Passwort" — Test vergleicht beide Responses explizit auf Gleichheit.
- [ ] Der Login-Codepfad verifiziert bei unbekanntem Username dennoch gegen einen Dummy-Argon2-Hash mit identischen Kostenparametern (Codepfad-Test, keine Wall-Clock-Timing-Messung — in CI unzuverlässig).
- [ ] `username`/`password` im Request-Schema auf `max_length` (z.B. 128) begrenzt.
- [ ] Nach 5 Fehlversuchen innerhalb einer Minute von derselben Client-IP an `POST /auth/login`: `429 Too Many Requests`.

**Backend — `get_current_user` / Retrofit**

- [ ] Aufruf eines geschützten Endpunkts (`/projects`, `/opencloud/*`) ohne `Authorization`-Header → `401`.
- [ ] Aufruf mit gültigem Token für existierenden User → reguläres Verhalten wie bisher.
- [ ] Aufruf mit abgelaufenem Token (`exp` in der Vergangenheit, direkt via `jwt.encode` konstruiert) → `401`.
- [ ] Aufruf mit manipuliertem/falsch signiertem Token oder abweichendem Algorithmus (z.B. `alg: none`) → `401`; `jwt.decode(..., algorithms=["HS256"])` fixiert den erlaubten Algorithmus explizit im Code.
- [ ] Aufruf mit strukturell gültigem Token, das auf einen nicht mehr existierenden User (`sub`-Claim) verweist → `401`.
- [ ] `/health` und `/auth/login` bleiben ohne Token erreichbar (Regressionstest).
- [ ] Ein parametrisierter Test zählt alle Pfade/Methoden unter den `projects`- und `opencloud`-Routern auf und prüft je `401` ohne Token — verhindert künftig versehentlich ungeschützte Endpunkte im selben Router.
- [ ] Bestehende Tests in `test_api_projects.py`/`test_api_opencloud_browse.py` laufen weiterhin grün, jetzt über eine authentifizierte Client-Fixture.
- [ ] App-Start verweigert den Betrieb (Fehler beim Boot), falls `settings.secret_key` dem Platzhalter `"change-me"` entspricht oder kürzer als 32 Zeichen ist.

**Backend — Seed-Migration**

- [ ] Migration auf leerer DB legt genau zwei User mit den konfigurierten Usernamen an; Passwort ist über `verify_password` gegen den konfigurierten Klartext prüfbar.
- [ ] Migration auf einer DB, in der einer der beiden Usernamen bereits mit einem anderen Passwort-Hash existiert: dieser Hash bleibt unverändert, nur der fehlende zweite User wird ergänzt.
- [ ] Migration auf einer DB, in der beide Usernamen bereits existieren: No-op, kein Fehler, kein doppelter Insert.
- [ ] Migrations-Stdout/-Stderr enthält an keiner Stelle die konfigurierten Klartext-Passwörter (Test fängt Ausgabe ab und prüft explizit).

**Frontend — Login-Flow**

- [ ] Erfolgreicher Login speichert das Token (`setToken`) und navigiert zu `state.from` (Fallback `/`) — inkl. Tiefenlink-Fall: unangemeldeter Aufruf von z.B. `/projects/42` → Redirect zu `/login` mit `state.from` gesetzt → nach Login zurück zu `/projects/42`, nicht zu `/`.
- [ ] Fehlgeschlagener Login zeigt den `detail`-Text aus der Fehlerantwort, speichert kein Token, navigiert nicht.
- [ ] `ProtectedRoute` ohne Token → `<Navigate to="/login" state={{from: location}} />`; mit Token → `<Outlet />` (reine Präsenzprüfung, keine clientseitige Ablaufprüfung).
- [ ] `api/client.ts` hängt bei vorhandenem Token den `Authorization`-Header an, bei fehlendem Token nicht.
- [ ] `api/client.ts` löscht bei `401`-Antwort das Token und feuert `photosort:unauthorized` genau einmal.
- [ ] Der globale `photosort:unauthorized`-Listener navigiert zu `/login` — Testfall "401 mitten in laufender Session" (gültiges Token beim Laden, spätere Anfrage liefert wegen zwischenzeitlichem Ablauf `401`) über einen zweiten API-Call simuliert, nicht nur den initialen Login.
- [ ] Direkter Aufruf von `/login` bei bereits vorhandenem, nicht abgelaufenem Token: sofortiger Redirect zu `/` bzw. `from`, ohne das Formular anzuzeigen.
- [ ] Logout-Button ruft `clearToken()` + `navigate("/login")` auf, ohne Backend-Aufruf.

## Architektur / Umsetzung

### Neue ADR

[`decisions/0005-auth-implementation.md`](../decisions/0005-auth-implementation.md) (Accepted) ergänzt ADR 0003 um die konkrete technische Umsetzung: Bibliothekswahl (`argon2-cffi`, `PyJWT`, `slowapi`) und Token-Transport (Bearer-Header + `localStorage`, keine Cookies). Diese ADR beantwortet damit auch die in Spec 0002 und Spec 0005 aufgeschobene CSRF-Frage abschließend: kein CSRF-Schutz nötig, da kein Cookie-Transport verwendet wird.

**Hinweis zur Reihenfolge:** ADR [`decisions/0004-frontend-app-shell.md`](../decisions/0004-frontend-app-shell.md) (React Router + TanStack Query) wurde ursprünglich im Zuge von Spec 0005 entworfen, wird aber tatsächlich von dieser Spec 0006 zuerst eingeführt (`ProtectedRoute` braucht Routing, der Login-`useMutation`-Aufruf braucht React Query) — die ADR gilt unverändert für beide Specs.

### Backend — Datenmodell

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str] = mapped_column(unique=True)
    password_hash: Mapped[str]
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
```

`username` ist ein freies Textfeld, kein Enum — die zwei bekannten Nutzer sind Seed-Konfiguration, kein Teil des Codes.

Alembic: eine Schema-Migration (autogeneriert, `users`-Tabelle) plus eine idempotente Seed-Datenmigration, die zwei Accounts anlegt (Username/Passwort aus neuen Settings-Feldern `auth_seed_user1_username`/`_password`, `_user2_...`, Werte aus `.env`). Idempotent = vor dem Insert per `username` prüfen, ob der Account schon existiert; bestehende Passwörter werden nie überschrieben.

### Backend — Bibliotheken (`backend/pyproject.toml`)

- `argon2-cffi` (Modul `argon2`, `PasswordHasher`) fürs Hashing.
- `PyJWT` (Modul `jwt`), Algorithmus `HS256`, signiert mit `settings.secret_key`.
- `slowapi` für Rate-Limiting an `POST /auth/login` (5 Versuche/Minute pro Client-IP, Zähler in Redis über `settings.redis_url`).
- Token-Extraktion über FastAPIs eingebautes `fastapi.security.HTTPBearer` — keine weitere Abhängigkeit.

Neues Modul `backend/src/photosort/security.py`:
- `hash_password(password: str) -> str`
- `verify_password(password: str, password_hash: str) -> bool` (fängt `VerifyMismatchError` ab)
- `create_access_token(user: User) -> str` (Claims: `sub=str(user.id)`, `username`, `exp` = jetzt + 30 Tage)
- `decode_access_token(token: str) -> dict` (wirft bei ungültig/abgelaufen; `algorithms=["HS256"]` explizit fixiert)

### Backend — Endpunkte und Dependency-Struktur

- `backend/src/photosort/api/auth.py`, neuer Router `POST /auth/login`: Body `{username, password}` → `{access_token, token_type: "bearer"}`. Bei falschem Username *oder* Passwort identische 401-Antwort; Verifikation läuft auch bei unbekanntem Username gegen einen Dummy-Hash. Rate-Limiting via `slowapi` direkt auf dieser Route. Router öffentlich, kein `get_current_user`.
- **Kein `POST /auth/logout`.** Ohne Server-Session-Store kann ein solcher Endpunkt serverseitig nichts invalidieren — Logout ist rein clientseitig (Token aus `localStorage` löschen + Redirect zu `/login`).
- `api/deps.py`: neue Dependency `get_current_user(credentials: HTTPAuthorizationCredentials | None = Depends(HTTPBearer(auto_error=False)), session: AsyncSession = Depends(get_session)) -> User`. 401 bei fehlendem Header, ungültiger Signatur, abgelaufenem Token oder nicht mehr existierendem User.
- Kein `GET /auth/me`: geschützte Frontend-Routen erkennen "kein Token" rein aus der Präsenz im `localStorage`; "Token vorhanden, aber ungültig/abgelaufen" fängt der globale 401-Handler in `api/client.ts` reaktiv ab.
- Retrofit: `dependencies=[Depends(get_current_user)]` auf Router-Ebene in `api/projects.py` und `api/opencloud.py` (nicht pro Funktion einzeln). `/health` und `/auth/login` bleiben öffentlich.

### Frontend — Integration

Diese Spec führt `react-router` und `@tanstack/react-query` in `frontend/package.json` bereits ein (gemäß ADR 0004).

- **`frontend/src/api/client.ts`** (Choke Point laut ADR 0004): schlanker `fetch`-Wrapper, hängt bei vorhandenem Token automatisch `Authorization: Bearer <token>` an. Bei `401`-Antwort: Token löschen + `window.dispatchEvent(new CustomEvent("photosort:unauthorized"))`. Ein zentraler Listener (in `App.tsx`/`AuthProvider`) reagiert mit `navigate("/login")` — Redirect-Logik bleibt an einer Stelle statt in jeder Query dupliziert.
- **`frontend/src/auth/token.ts`**: `getToken()/setToken()/clearToken()` um `localStorage` (Schlüssel `photosort_token`).
- **`frontend/src/pages/LoginPage.tsx`**: Formular (Username/Passwort), `useMutation` gegen `POST /auth/login`; bei Erfolg Token speichern + zur ursprünglich angeforderten Route navigieren; bei Fehler `detail`-Text unverändert anzeigen.
- **`frontend/src/auth/ProtectedRoute.tsx`**: prüft nur Token-Präsenz; fehlt er, `<Navigate to="/login" replace state={{ from: location }} />`, sonst `<Outlet />`.
- **`main.tsx`/`App.tsx`**: `BrowserRouter` + `QueryClientProvider`, Route `/login` öffentlich, restliche Routen unter `ProtectedRoute`-Layout (Platzhalter-Inhalt bis Spec 0005 die eigentlichen Projekt-Routen ergänzt). Logout: Button ruft `clearToken()` + `navigate("/login")` auf, kein Backend-Call.

### Umsetzungsreihenfolge (TDD)

1. Backend-Datenzugriff: `User`-Modell, Migration (Schema + idempotenter Seed), Settings-Felder.
2. Backend-Kernlogik: `security.py` (Hashing, Token erzeugen/validieren) — isoliert testbar ohne HTTP.
3. Backend-API: `get_current_user`, `POST /auth/login` (inkl. Rate-Limiting, Algorithm-Pinning, Secret-Startup-Guard), Retrofit der bestehenden Router.
4. Frontend-Grundgerüst: `react-router`/`@tanstack/react-query` einbinden, `api/client.ts` + `auth/token.ts`.
5. Frontend-UI: `LoginPage`, `ProtectedRoute`, Verdrahtung in `App.tsx`, Logout-Aktion.

## UI/UX

Erste sichtbare Oberfläche von PhotoSort überhaupt (kommt zeitlich vor Spec 0005 — `specs/architecture/0004-design-system.md` wurde entsprechend korrigiert). Bezug: [`architecture/0004-design-system.md`](../architecture/0004-design-system.md).

### Login-Screen (`/login`)

- **Layout:** eigenständiger, zentrierter Kartenbereich (max-width ~360–400px) *ohne* App-Shell-Kopfzeile — es existiert noch kein Nutzerkontext. Einspaltig, gleich auf Mobil wie Desktop: Produktname, Username-Feld, Passwort-Feld, Submit-Button "Anmelden" (volle Breite, ≥44px Höhe). Kein Registrieren-Link, kein "Passwort vergessen" (kein Self-Signup/Reset-Flow laut ADR 0003).
- **Initial/leer:** beide Felder leer, Submit aktiv; `required` auf beiden Feldern verhindert Submit bei leerem Feld rein clientseitig. Username-Feld erhält Autofokus.
- **Ladezustand:** Busy-Button-Muster — Submit-Button deaktiviert, Label wechselt zu "Anmelden…" mit Inline-Spinner; beide Felder zusätzlich deaktiviert.
- **Fehlerzustand (falsche Zugangsdaten):** Banner am Formularanfang mit dem einheitlichen `detail`-Text wörtlich (`role="alert"`). Anders als beim sonstigen Formularfehler-Muster wird **kein einzelnes Feld markiert** — das würde die Anti-Enumeration-Maßnahme (identische Meldung bei falschem User oder Passwort) faktisch aushebeln. Passwortfeld wird nach einem Fehlversuch geleert, Username bleibt erhalten.
- **Redirect-Ziel nach Erfolg:** `location.state.from`, sonst `/`. Direkter Aufruf von `/login` bei bereits vorhandenem, gültigem Token: sofortiger Redirect ohne Formular anzuzeigen.
- **Session-abgelaufen-Fall:** Navigiert der globale 401-Listener wegen eines ungültig gewordenen Tokens zu `/login`, wird zusätzlich `state.reason === "expired"` übergeben. LoginPage zeigt dann einen neutralen Hinweis "Sitzung abgelaufen — bitte erneut anmelden" (kein rotes Fehler-Styling, kein Bedienfehler des Nutzers).

### App-Shell / geschützte Bereiche

- Minimale Kopfzeile über jeder geschützten Route: links Produktname "PhotoSort" (verlinkt `/`), rechts Anzeige **"Angemeldet als {username}"** neben der Logout-Aktion (Button/Link, ≥44×44px, Text-Label "Abmelden") — aus dem JWT-Payload abgeleitet. Sinnvoll, da beide Nutzer sich potenziell ein Gerät/eine installierte PWA teilen und sonst nicht sofort klar wäre, wessen Bewertung gerade eingeht.
- Logout ist eine bestätigungslose Aktion (nur destruktive/schwer-rückgängige Aktionen bekommen einen Bestätigungsdialog; erneutes Anmelden ist trivial) — Klick löscht das Token sofort und navigiert synchron zu `/login`.
- Unterhalb der Kopfzeile bleibt der Seiteninhalt vorerst der bestehende Platzhaltertext aus `App.tsx`; Spec 0005 ersetzt diesen Bereich später durch die eigentlichen Projekt-Ansichten.
- `ProtectedRoute` zeigt bei fehlendem Token keinen eigenen Lade-/Fehlerzustand, sondern leitet unmittelbar zu `/login` weiter — reine Client-seitige Prüfung der Token-Präsenz, kein Server-Roundtrip.

### Design-System-Ergänzungen (im Zuge dieser Spec vorgenommen)

`specs/architecture/0004-design-system.md` aktualisiert: Reihenfolge-Korrektur (0006 ist tatsächlich erste Oberfläche, nicht 0005), neues Muster "Standalone-Bildschirm vs. App-Shell", Logout als bestätigungslose Aktion, explizite Sicherheits-Ausnahme "keine Feldmarkierung bei Login-Fehlern", Attributions-Korrektur bei Busy-Button und Formular-Fehlerbanner (jetzt Spec 0006 statt 0005 als Ursprung).

## Security

Dieses Feature führt die erste echte Authentifizierungsgrenze des Projekts ein und ist damit in vollem Umfang sicherheitsrelevant. Details projektweit verankert in [`architecture/0003-securitykonzept.md`](../architecture/0003-securitykonzept.md).

1. **Algorithm-Confusion / `alg: none` beim JWT-Decode (Muss-Kriterium).** `jwt.decode(token, settings.secret_key, algorithms=["HS256"])` fixiert den erlaubten Algorithmus explizit im Code — nie aus dem Token-Header übernehmen oder `algorithms` weglassen.
2. **Schwaches/Platzhalter-Signing-Secret (Muss-Kriterium, Blocker).** App-Start verweigert den Betrieb, falls `secret_key` dem Platzhalter `"change-me"` entspricht oder kürzer als 32 Zeichen ist — sonst könnte jeder gültige JWTs fälschen und vollen Zugriff auf beide Accounts (und transitiv alle Familienfotos) erlangen.
3. **User-Enumeration am Login-Endpunkt (Muss-Kriterium).** Identische 401-Antwort (Status, Body, Header) bei unbekanntem Username vs. falschem Passwort; Verifikation läuft bei unbekanntem Username trotzdem gegen einen Dummy-Argon2-Hash mit identischen Kostenparametern. Verbleibende Mikro-Timing-Differenzen sind für dieses Zwei-Nutzer-Setup nicht praktisch ausnutzbar.
4. **Credential-Stuffing/Brute-Force gegen `POST /auth/login` (Muss-Kriterium, Blocker).** PhotoSort ist aus dem offenen Internet erreichbar (Stakeholder-Entscheidung vom 2026-07-20, auch für Zugriff unterwegs) — Argon2 allein bremst verteilte automatisierte Versuche nicht ausreichend. Umsetzung: `slowapi`, 5 Versuche/Minute pro Client-IP, ausschließlich an `POST /auth/login`, Zähler in Redis (`settings.redis_url`) für Konsistenz über mehrere Backend-Prozesse; `429` bei Überschreitung.
5. **Übergroße Login-Payloads (Muss-Kriterium).** `username`/`password` über Pydantic mit `max_length` (z.B. 128) begrenzen — Argon2-Verify ist bewusst langsam und würde sonst unnötig CPU-Zeit binden.
6. **Seed-Migration und Secrets-Handling.** `AUTH_SEED_USER1/2_USERNAME/PASSWORD` ausschließlich über `.env`, nie im Code/in Specs. Kein Logging der Klartext-Passwörter (Test fängt Migrations-Stdout/-Stderr ab und prüft dies explizit); bestehende Alembic-Logger-Konfiguration loggt keine SQL-Parameter.
7. **Token-Transport und CSRF (bereits entschieden, ADR 0005).** Bearer-Header + `localStorage` — kein CSRF-Schutzmechanismus nötig. Kehrseite: erhöhte XSS-Relevanz (Token unmittelbar auslesbar, Session-Hijacking bis zu 30 Tage, kein Widerruf möglich). Verbindliche Konvention: kein `dangerouslySetInnerHTML` mit nutzergenerierten/externen Werten. Jedes künftige Feature mit Freitext-Eingaben/Drittanbieter-Skripten hebelt diese Abwägung aus und muss erneut bewertet werden.
8. **Auth-Durchsetzung projektweit (Muss-Kriterium, Blocker).** `get_current_user` muss bei fehlendem/ungültigem/abgelaufenem Token oder nicht mehr existierendem User einheitlich `401` liefern. Retrofit auf `api/projects.py`/`api/opencloud.py` per Router-Dependency, verifiziert durch einen parametrisierten Vollständigkeitstest über alle Pfade/Methoden. Kein Feature mit personenbezogenen Nutzerdaten (allen voran `Rating`, Spec 0002) darf live gehen, solange dies nicht real umgesetzt ist.

**Verdict:** Kein Blocker gegen die Architektur/den Ansatz selbst (Argon2, JWT HS256, Bearer+localStorage, Seed-Migration) — für dieses private Zwei-Nutzer-Setup angemessen. Blocker für den Merge sind die konkreten Implementierungspunkte 2, 4 und 8 (Secret-Startup-Guard, Rate-Limiting, tatsächliche Router-Absicherung) — als explizite Akzeptanzkriterien/Tests bereits oben aufgenommen.

## Entscheidungen (2026-07-20, im Idea-Sharpening-Gespräch mit Daniel geklärt)

- **Account-Anlage:** Seed-Migration (Alembic), die beim Deploy automatisch die zwei Accounts anlegt; Initial-Passwörter aus Umgebungsvariablen — kein CLI-Befehl, kein Admin-UI.
- **Session-Dauer:** langlebiges JWT (~30 Tage), kein Refresh-Token-Mechanismus — bewusste Vereinfachung für zwei bekannte, private Nutzer.
- **Bibliotheken/Token-Transport:** `argon2-cffi` + `PyJWT` (HS256) + Bearer-Header/`localStorage`, siehe ADR [`decisions/0005-auth-implementation.md`](../decisions/0005-auth-implementation.md) — beantwortet damit auch die in Spec 0002/0005 aufgeschobene CSRF-Frage: kein CSRF-Schutz nötig.
- **Logout:** rein clientseitig (kein Backend-Endpunkt), da ohne Server-Session-Store nichts zu invalidieren wäre.
- **Nutzeranzeige:** Kopfzeile zeigt zusätzlich "Angemeldet als {username}" — beide Nutzer teilen sich potenziell ein Gerät/eine installierte PWA, Verwechslung soll ausgeschlossen werden.
- **Erreichbarkeit/Rate-Limiting:** PhotoSort ist aus dem offenen Internet erreichbar (auch für Zugriff unterwegs) — Rate-Limiting an `POST /auth/login` damit Muss-Kriterium, nicht optionales Restrisiko.
- **Reihenfolge:** Diese Spec kommt vor Spec 0005 (Minimales Projekt-Frontend), nicht danach — führt daher auch das Routing-/Server-State-Grundgerüst (ADR 0004) zuerst ein. Design-System-Dokument entsprechend korrigiert.
- **Testebenen:** Backend-Integrationstests laufen `get_current_user` real durch (eigene `authenticated_api_client`-Fixture, keine Mock-Umgehung); Frontend-Integrationstests mit echtem `MemoryRouter`/`QueryClientProvider`, API an der Modulgrenze gemockt. Timing-Angriffsschutz nur als Codepfad-Test, keine Wall-Clock-Messung. `specs/architecture/0002-testkonzept.md` entsprechend ergänzt.

## Out of Scope

Self-Signup, Passwort-Reset-Flow, Refresh-Token-Mechanismus, Rollen-/Rechtemodell, OAuth/Fremd-Login-Provider, Account-Verwaltungs-UI (Accounts entstehen ausschließlich per Seed-Migration), serverseitige Token-Widerrufbarkeit vor Ablauf.
