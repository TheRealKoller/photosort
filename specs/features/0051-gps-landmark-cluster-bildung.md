# 0051 - GPS-/Zeit-/Sehenswürdigkeit-basierte Clusterbildung mit gegenseitiger Herleitung

**Status:** Implemented ([PR #381](https://github.com/TheRealKoller/photosort/pull/381))
**Erstellt:** 2026-08-20
**Bezug:** Issue [#169](https://github.com/TheRealKoller/photosort/issues/169) (Story), `inbox/0022-gps-zeit-clusterbildung-benannte-cluster.md` (Ursprung, nach Anlage dieser Spec gelöscht — bewusst kein Link), ADR [`decisions/0029-gps-landmark-cluster-bildung.md`](../decisions/0029-gps-landmark-cluster-bildung.md) (zweiphasige Cluster-Bildung, unverändert gültig), ADR [`decisions/0072-ortsbezogene-cluster-anzeigeort-als-antwortableitung.md`](../decisions/0072-ortsbezogene-cluster-anzeigeort-als-antwortableitung.md) (die vier seit 2026-08-20 verschobenen Punkte), [`features/0039-kuratierung-tage-und-benannte-cluster.md`](./0039-kuratierung-tage-und-benannte-cluster.md) (bestehende Tageszeit-Cluster-Anzeige, deren Out-of-Scope-Grenze hier gezielt aufgehoben wird), [`features/0047-sehenswuerdigkeit-erkennung-cloud-vision-api.md`](./0047-sehenswuerdigkeit-erkennung-cloud-vision-api.md) (Landmark-Erkennung, inzwischen implementiert — diese Spec konsumiert deren Ergebnis), [`decisions/0021-kriterien-datenmodell-kuratierungs-pipeline.md`](../decisions/0021-kriterien-datenmodell-kuratierungs-pipeline.md) (gateführte Zwei-Phasen-Pipeline), [`decisions/0071-kuratierung-stabile-auswahl-ohne-backfill-und-einsehbarer-vorrat.md`](../decisions/0071-kuratierung-stabile-auswahl-ohne-backfill-und-einsehbarer-vorrat.md) (Top-N-Auswahl + Nachladen), Idea-Sharpening-Gespräch mit Daniel am 2026-08-20, technische Nachschärfung am 2026-09-09.

## Ziel

Die bestehende Cluster-Bildung auf `/curate` (Spec 0039) gruppiert Fotos ausschließlich nach Zeitfenstern (1h-Lücke). Das führt zu falsch zusammengefassten Clustern, wenn innerhalb einer Stunde tatsächlich mehrere Orte besucht wurden (z.B. zwei Sehenswürdigkeiten kurz hintereinander), und lässt eine mögliche Orts-Information ungenutzt, obwohl sie oft in den Fotos selbst (EXIF-GPS) oder über die Landmark-Erkennung (Spec 0047) bereits vorliegt.

Diese Spec erweitert die Cluster-BILDUNG selbst (nicht nur ihre Anzeige) um GPS-Nähe und erkannte Sehenswürdigkeiten als zusätzliche Signale, inklusive gegenseitiger Herleitung: Fotos ohne eigene GPS-Daten können anhand zeitlich benachbarter Fotos mit GPS im selben Cluster einen Ort für die Anzeige zugewiesen bekommen. Rein vorausschauende Erweiterung ohne konkret erlebten Auslöser — im Sharpening-Gespräch bewusst in voller Ausbaustufe bestätigt (siehe Entscheidungen).

## User Story

Als Nutzer (Daniel oder seine Frau) möchte ich, dass Fotos beim Kuratieren nicht nur nach Zeit, sondern auch nach Ort gruppiert werden, damit zeitlich nah beieinanderliegende, aber räumlich unterschiedliche Aufnahmen (z.B. zwei Sehenswürdigkeiten in einer Stunde) nicht fälschlich in einem Cluster landen, und die Cluster-Überschrift mir zeigt, wo ein Cluster entstanden ist.

## Akzeptanzkriterien

**GPS-Extraktion:**
- [ ] Beim Scan wird `Photo.gps_lat`/`Photo.gps_lon` als Dezimalgrad befüllt (inkl. korrekter Süd-/West-Vorzeichenumkehr aus `GPSLatitudeRef`/`GPSLongitudeRef`), wenn ein lesbares `GPSInfo`-EXIF-IFD vorhanden ist. Fehlt es oder ist es unlesbar, bleiben beide Felder `None` — ein einzelnes unlesbares Foto darf den Scan-Lauf nie abbrechen (`extract_gps`, analog `extract_taken_at`).
- [ ] Es gibt nie eine halbe Koordinate: scheitert eine Komponente, werden **beide** verworfen.
- [ ] Ein fehlender oder von `N`/`S` bzw. `E`/`W` abweichender `GPSLatitudeRef`/`GPSLongitudeRef` verwirft die Koordinate — **kein** stiller Default auf Nord/Ost.
- [ ] Werte außerhalb `-90…90` bzw. `-180…180` sowie das exakte Paar `(0.0, 0.0)` (Kamera-Artefakt bei fehlgeschlagenem Fix) werden verworfen. Die Prüfung ist ein Bereichsvergleich, **kein** Klemmen — sonst passierte `NaN` (`IFDRational` mit Nenner 0 ergibt `nan` ohne Exception) und legte die Listenantwort des Projekts dauerhaft auf HTTP 500.
- [ ] Beim Aktualisieren eines geänderten Fotos werden beide Felder **unbedingt** geschrieben, auch zurück auf `None` — es ist der einzige Pfad, über den das Entfernen von GPS aus einer Quelldatei in PhotoSort ankommt.

**Cluster-Bildung (Phase A, Zeit + GPS):**
- [ ] Ein neues Cluster beginnt, wenn die Haversine-Distanz zum **letzten Foto mit Koordinate im laufenden Cluster** `GPS_CLUSTER_SPLIT_DISTANCE_METERS` überschreitet — auch wenn die Zeitlücke `TIME_CLUSTER_GAP` nicht überschritten ist. Die Bezugskoordinate wird an **jeder** Cluster-Grenze zurückgesetzt, damit nie über eine Grenze hinweg verglichen wird.
- [ ] Ein Foto ohne eigene GPS-Koordinate löst nie selbst einen Split aus, wird beim Distanzvergleich übersprungen **und unterdrückt eine Trennung zwischen seinen koordinatentragenden Nachbarn nicht**.
- [ ] `GPS_CLUSTER_SPLIT_DISTANCE_METERS = 500.0` ist eine dokumentierte Modulkonstante in `scoring.py` (kein Settings-/Env-Wert, konsistent mit `TIME_CLUSTER_GAP`/`SHARPNESS_REJECT_THRESHOLD`).
- [ ] **Backward Compatibility:** Ohne jede GPS-Koordinate im Lauf ist das Ergebnis von `assign_clusters` `dict`-identisch zum bisherigen `assign_time_clusters`.

**Cluster-Verfeinerung (Phase 2, Landmark):**
- [ ] Ein Phase-A-Cluster mit ≥2 unterschiedlichen, nicht-leeren `landmark_name`-Werten wird in `PhotoRanking.cluster_key` weiter aufgeteilt (`refine_clusters_by_landmark`), exakter String-Vergleich, kein Fuzzy-Matching. `PhotoScore.cluster_key` wird dabei **nie** mutiert — bewusste, dokumentierte Divergenz beider Felder (analog `category_key`, ADR 0021).
- [ ] Die Schlüsselform ist indexbasiert: `cluster-<n>-<i>`, 1-basiert, in **alphabetischer** Reihenfolge der Namen vergeben, kein Name im Schlüssel. Fotos ohne Namen behalten den Basis-Schlüssel `cluster-<n>` — ein Cluster mit zwei Namen und namenlosen Fotos ergibt also genau drei Schlüssel. Bei genau einem Namen im Cluster findet **keine** Verfeinerung statt.
- [ ] Die Zuordnung ist deterministisch: dieselbe Eingabe in anderer Reihenfolge ergibt dieselben Schlüssel.
- [ ] Die Verfeinerung greift auch in einem Lauf **ohne** Cloud-Phase, wenn die Namen aus einem früheren Lauf in `photo_landmark_detections` stehen (Einwilligung aus, Cloud-Häkchen abgewählt, oder alle Fotos bereits früher erkannt).
- [ ] **Backward Compatibility:** Ohne Landmark-Daten ist `PhotoRanking.cluster_key` für jedes Foto `dict`-identisch zu `PhotoScore.cluster_key` (reiner Passthrough).

**Gegenseitige Herleitung (Anzeige, nicht persistiert):**
- [ ] Ein GPS-loses Foto bekommt für die Anzeige die Koordinate des zeitlich nächsten GPS-tragenden Fotos im **vollständigen Cluster des Bezugslaufs** zugewiesen (alle `PhotoRanking`-Zeilen des letzten erfolgreichen `CriterionScoringRun` mit demselben `cluster_key`), **unabhängig davon, welche Fotos die Antwort enthält**. Bei zwei gleich weit entfernten Nachbarn gewinnt der frühere Zeitpunkt, bei identischem `taken_at` die kleinere `photo_id`. Gibt es im Cluster kein GPS-tragendes Foto, bleibt kein Ort hergeleitet.
- [ ] `PhotoOut.location` ist `null`, wenn im gesamten Cluster keine Koordinate vorliegt — kein Objekt aus lauter `null`-Feldern. `source` ist `"exif"`, wenn das Foto eine eigene Koordinate trägt, sonst `"derived"`.
- [ ] Der hergeleitete Ort wird nirgends persistiert.

**Cluster-Anzeige (`/curate`):**
- [ ] Cluster-Überschrift zeigt Ort **und** Tageszeit gemeinsam (Ort ergänzt, ersetzt nicht): `"<Ort> · <Tageszeit> (<Zeitspanne>)"`.
- [ ] Der Ortsteil kommt fertig aufgelöst als `PhotoOut.cluster_place` vom Server und ist auf jedem Foto desselben Clusters identisch. Die Rangfolge wird **nicht** im Frontend nachgebildet: `kind="landmark"` → Sehenswürdigkeit-Name, `kind="coordinate"` → gerundete Koordinate (2 Nachkommastellen, ~1,1 km), `kind="multiple"` → `"Mehrere Orte"`, `null` → gar kein Ortsteil.
- [ ] `kind="multiple"` führt **nie** eine stellvertretende Koordinate mit.
- [ ] **Der Ortsteil hängt nicht davon ab, welche Fotos sichtbar sind:** `cluster_place` ist über `GET /photos` (beide Modi) und `GET /curation-candidates` desselben Bezugslaufs identisch und unabhängig von `top_n_per_category`/`limit`/`offset`. Insbesondere zeigt ein Cluster `kind="landmark"` bzw. `kind="multiple"` auch dann, wenn das tragende Foto wegen der Top-N-Auswahl gar nicht in der Antwort steht.
- [ ] **Backward Compatibility:** Fehlt jede Ortsinformation, ist die Überschrift zeichengleich mit der heutigen (Spec 0039, unverändert).
- [ ] API liefert `PhotoOut.location.lat`/`.lon` in voller EXIF-Präzision, keine serverseitige Rundung (siehe Entscheidungen). Die Rundung auf 2 Nachkommastellen liegt in `cluster_place`, weil dieselbe Zahl dort über `"coordinate"` vs. `"multiple"` entscheidet.

**Projektbindung (sicherheitsrelevantes Muss-Kriterium):**
- [ ] Die Ortsabfrage filtert auf `criterion_scoring_run_id`, **nie** auf `cluster_key` allein. `cluster_key` ist `cluster-<n>`, je Lauf neu vergeben und in jedem Projekt derselbe String; `photo_rankings` trägt keine `project_id`. Ohne dieses Prädikat ordnete die Herleitung systematisch Koordinaten aus fremden Projekten zu.

## Datenmodell-Bezug

Additive Migration: zwei neue `Photo`-Spalten `gps_lat: float | None`, `gps_lon: float | None`. `PhotoRanking.cluster_key` kann ab jetzt feiner unterteilt sein als `PhotoScore.cluster_key` (bewusste Divergenz, siehe ADR 0029/0021). Siehe [`docs/architecture.md`](../../docs/architecture.md) (wird von `architect` bei Umsetzung ergänzt).

## Architektur / Umsetzung

Grundlage: ADR [`0029`](../decisions/0029-gps-landmark-cluster-bildung.md) (zweiphasige Cluster-Bildung, unverändert gültig) und ADR [`0072`](../decisions/0072-ortsbezogene-cluster-anzeigeort-als-antwortableitung.md), die die Punkte entscheidet, die sich seit 2026-08-20 durch die Umsetzung von Spec 0047 sowie durch ADR 0049/0069/0071 verschoben haben.

**1. Koordinaten beim Einlesen (`Photo.gps_lat`/`.gps_lon`).** Neues `opencloud/exif.py::extract_gps` als Pendant zu `extract_taken_at` — liest `IFD.GPSInfo` aus demselben bereits per Range-Read geladenen Byte-Fenster (`_EXIF_RANGE_BYTES`, `worker.py::_fetch_and_thumbnail`), also ohne einen einzigen zusätzlichen Netzwerkzugriff. Rechnet Grad/Minute/Sekunde in Dezimalgrad um und kehrt das Vorzeichen bei `GPSLatitudeRef == "S"`/`GPSLongitudeRef == "W"` um. Vertrag wie bei `extract_taken_at`: breites `except Exception` → `None`, ein einzelnes unlesbares Foto bricht einen Scan nie ab (Muss-Kriterium des Security-Abschnitts). Zwei technisch lesbare Werte gelten trotzdem als „kein Ort" und werden bereits hier verworfen, damit sie die Datenbank nicht erreichen (ADR 0072, Entscheidung 6): **exakt `(0.0, 0.0)`** (bekanntes Kamera-Artefakt; ein solches Foto risse sein Cluster sonst zweimal auf) und ein **fehlender `GPSLatitudeRef`/`GPSLongitudeRef`** (die Referenz zu raten führte zu einer falschen Koordinate auf der Südhalbkugel/westlich des Nullmeridians — „kein Ort" ist überall sauber behandelt, „falscher Ort" nirgends). `_fetch_and_thumbnail` liefert statt eines nackten `datetime` ein kleines eingefrorenes Ergebnis-Objekt (Zeitpunkt + Koordinate); `_process_scan_block` schreibt beide Felder, beim Aktualisieren eines geänderten Fotos **immer** (auch auf `None` zurück), damit kein Wert einer früheren Dateiversion stehen bleibt.

**2. Der Ort in der Cluster-Bildung (Phase A, `scoring.py`).** `assign_time_clusters`/`TimeClusterCandidate` werden zu `assign_clusters`/`ClusterCandidate` erweitert (dieselbe Funktion, kein Parallelmuster) — `ClusterCandidate` trägt zusätzlich `gps_lat`/`gps_lon: float | None`. In dem einen, bereits vorhandenen sortierten Durchlauf beginnt ein neues Cluster, wenn die Zeitlücke `TIME_CLUSTER_GAP` überschritten wird **oder** die Haversine-Distanz zum **letzten Foto mit Koordinate im laufenden Cluster** `GPS_CLUSTER_SPLIT_DISTANCE_METERS` überschreitet. Beide Bedingungen sind gleichrangig und stehen in derselben Prüfung — es gibt keine „Reihenfolge" von Zeit- und Ortstrennung, nur eine Cluster-Grenze. Die Referenzkoordinate wird an jeder Cluster-Grenze zurückgesetzt; ein Foto ohne eigene Koordinate wird im Vergleich übersprungen und löst nie selbst eine Trennung aus (ADR 0072, Entscheidung 5). Distanz: private Haversine-Hilfsfunktion mit Stdlib-`math`, keine neue Abhängigkeit. `GPS_CLUSTER_SPLIT_DISTANCE_METERS = 500.0` — dokumentierte, unkalibrierte Modulkonstante neben `TIME_CLUSTER_GAP`/`SHARPNESS_REJECT_THRESHOLD`, Begründung des Werts in ADR 0072, Entscheidung 4.

**3. Die Sehenswürdigkeit in der Cluster-Verfeinerung (Phase 2, `worker.py::run_criterion_scoring`).** Neue reine Funktion `scoring.py::refine_clusters_by_landmark(base_cluster_key_by_photo, landmark_name_by_photo) -> dict[int, str]`: enthält ein Basis-Cluster zwei oder mehr **verschiedene** nicht-leere Namen, bekommt jeder Name ein eigenes Cluster (`cluster-3-1`, `cluster-3-2`, … in alphabetischer Reihenfolge der Namen vergeben — deterministisch, ohne Namen im Schlüssel, ADR 0072 Entscheidung 3); Fotos ohne Namen behalten den Basis-Schlüssel. Exakter Zeichenkettenvergleich, kein Fuzzy-Matching. Verdrahtet wird sie **nach** der Landmark-Phase und **vor** dem Aufbau der Partitionen — sie ersetzt den bisherigen reinen Passthrough `cluster_by_photo[photo.id] = score.cluster_key or ""`. Die Namen kommen aus einem einzelnen Lesezugriff auf `photo_landmark_detections` über die Kandidaten des Laufs (neue Hilfsfunktion nach dem Muster von `_remote_category_evidence`), nicht aus einer laufinternen Abbildung — die Aufteilung wirkt damit auch in Läufen ohne Cloud-Phase (ADR 0072, Entscheidung 2). `PhotoScore.cluster_key` wird dabei **nie** mutiert (Ownership-Grenze ADR 0021); die Divergenz zu `PhotoRanking.cluster_key` ist gewollt und dokumentiert. Verifiziert: Der einzige weitere Schreibpfad auf `cluster_key`, `worker.py::reassign_photo_category`, bekommt seinen `cluster_key` aus der **Hauptzeile in `PhotoRanking`** (`api/photos.py::_run_and_primary_ranking`), nicht aus `PhotoScore` — die Divergenz ist dort strukturell folgenlos.

**4. Zwei getrennte Ortsfelder in der API, beide im Backend berechnet und nicht persistiert (`api/photos.py`).**

- `PhotoOut.location` (`lat`, `lon`, `source: "exif" | "derived"`) — der Ort **dieses Fotos**: die eigene Koordinate in voller EXIF-Präzision (keine serverseitige Rundung, siehe Security-Abschnitt) oder, ohne eigene, die des zeitlich nächstgelegenen Fotos **mit** Koordinate im selben finalen Cluster (bei Gleichstand die des kleineren `photo_id`); `null`, wenn der Cluster keine trägt.
- `PhotoOut.cluster_place` (`kind: "landmark" | "coordinate" | "multiple"`, dazu `landmark_name` bzw. `lat`/`lon` **auf zwei Nachkommastellen gerundet**) — der bereits aufgelöste Ort des **Clusters**, auf jedem Foto desselben Clusters identisch; `null` ohne jede Ortsinformation. `kind="landmark"`, wenn im Cluster eine Erkennung vorliegt (nach der Verfeinerung höchstens eine; defensiv die des chronologisch frühesten Fotos); sonst `kind="coordinate"` bei genau einer verschiedenen gerundeten Koordinate im Cluster und `kind="multiple"` bei mehreren — dieser Fall trägt bewusst **keine** Koordinate.

Beide Felder entstehen in **einer** Hilfsfunktion mit **einer** Abfrage über den **vollständigen** Cluster des Bezugslaufs, nicht über die Fotos der Antwort: die Kuratierungsansicht sieht je Partition nur `rank_position <= topN`, die nachgeladenen Kandidaten laufen über eine eigene Abfrage und fließen nie in die Hauptliste zurück, und `topN` ist ein Suchparameter (1–10). Im Frontend gebildet wäre der Cluster-Ort deshalb **dauerhaft** eine Aussage über die Top-N — sowohl „Mehrere Orte" als auch der Sehenswürdigkeit-Name (ADR 0072, Entscheidung 1). Die Rundung auf ~1 km liegt im Backend, weil dort dieselbe Zahl über „eine Koordinate oder mehrere Orte" entscheidet; das Frontend formatiert nur noch.

Beide Felder werden **einheitlich auf allen Lesepfaden** ausgeliefert, nicht nur im Kuratierungsmodus (Daniels Entscheidung, 2026-09-09): ein je Query-Modus divergierendes `PhotoOut` wäre genau die „zweite, driftende Abbildung", vor der der Kommentar an dieser Stelle in `api/photos.py` warnt.

**SICHERHEIT — Laufbindung (Muss-Kriterium):** Die Abfrage holt Fotos eines `cluster_key`, und `cluster_key` ist `cluster-<n>`, je Lauf neu vergeben und **in jedem Projekt derselbe String**; `PhotoRanking` trägt keine `project_id`. Die einzige Bindung an das Projekt des Pfadparameters ist `criterion_scoring_run_id` aus `_latest_successful_criterion_scoring_run_id(session, project_id)`. Dieses Prädikat steht deshalb **ausgeschrieben in der Ortsabfrage** — ohne es lieferte die Herleitung Koordinaten aus einem fremden Projekt, bei genau der Datenklasse, die dieses Feature erstmals überhaupt exponiert (dieselbe Auflage wie am Endpunkt `curation_candidates`, Spec 0357). `_photos_by_id` filtert nur nach Id und ist ausdrücklich **keine** zweite Verteidigungslinie. Fehlt die Lauf-Id, ist das Ergebnis „kein hergeleiteter Ort" — die Ausfallrichtung ist „nichts anzeigen", nie „aus irgendeinem Lauf herleiten".

**5. Die Cluster-Überschrift bleibt eine Frontend-Ableitung (`frontend/src/utils/timeOfDay.ts`).** `formatClusterHeading()` bekommt zusätzlich zu `taken_at` das `cluster_place` je Foto und setzt die Überschrift aus Ort **und** Tageszeit zusammen: `"<Ort> · <Tageszeit> (<Zeitspanne>)"`. Tag, Tageszeit, Zeitspanne und die bestehende Früheste-Foto-Regel bleiben unverändert und entstehen weiterhin aus den sichtbaren Fotos; der Ortsteil wird fertig aufgelöst übernommen, die Rangfolge wird **nicht** im Frontend nachgebildet: `kind="landmark"` → der Name, `kind="coordinate"` → `"48.86, 2.29"` (zwei Nachkommastellen, `-0.0` als `0.0`), `kind="multiple"` → `"Mehrere Orte"`, `null` → gar kein Ortsteil und damit eine zu heute zeichengleiche Überschrift. `landmark_name` ist freier, extern erzeugter LLM-Text und darf ausschließlich als regulärer Textknoten gerendert werden (dieselbe Auflage wie bei `FineLabelOut.raw_label`).

**Datenmodell/Migration:** rein additiv, zwei nullable `REAL`-Spalten `photos.gps_lat`/`photos.gps_lon`, kein Backfill, keine bestehende Spalte ändert sich, kein `PhotoScore`/`PhotoRanking`-Schemaeingriff (deren `cluster_key` bekommt nur einen reicheren Wertebereich).

**Bekannte Grenze (Daniels Entscheidung, bewusst so):** Der Scan überspringt Dateien mit unverändertem `Etag` (`worker.py::_classify_scan_entries`), und die Cache-Varianten tragen kein EXIF mehr (`thumbnails.py::generate_variants`) — bereits gescannte Fotos bekommen ihre Koordinaten erst, wenn sich die Datei auf OpenCloud ändert. Kein Nachzug des Bestands, keine Markerspalte, kein zusätzlicher Arbeitsposten im Scan (siehe Out of Scope).

**Betroffene/neue Dateien:** `backend/alembic/versions/<rev>_gps_koordinaten.py` (neu), `backend/src/photosort/models.py`, `backend/src/photosort/opencloud/exif.py`, `backend/src/photosort/scoring.py`, `backend/src/photosort/worker.py`, `backend/src/photosort/api/photos.py`, `backend/src/photosort/landmark.py` (Sanitisierung an der Quelle), `backend/src/photosort/cloud_vision.py` (`_sanitize_label_text` wandert hierher), `backend/src/photosort/demo_state.py`, `frontend/src/api/types.ts`, `frontend/src/utils/timeOfDay.ts`, `docs/architecture.md`. `frontend/src/pages/CurateCategoriesPage.tsx` bleibt unverändert — es reicht die vollen `PhotoOut`-Objekte bereits an `formatClusterHeading()` durch.

**Reihenfolge der Umsetzung:** Datenzugriff vor Logik vor Auslieferung — Migration/Modell → `extract_gps` → Scan-Verdrahtung → `assign_clusters` → `refine_clusters_by_landmark` → API-Felder → Frontend-Überschrift → Demo-Daten → Doku. Der GPS-Anteil ist unabhängig von jeder Cloud-Einwilligung lauffähig; die Sehenswürdigkeit-Aufteilung ist es seit der Umsetzung von Spec 0047 ebenfalls (die frühere strukturelle Blockade besteht nicht mehr).

## UI/UX

Sichtbare Oberfläche vorhanden (`ux-ui-designer`-Konsultation 2026-08-20, nachgezogen 2026-09-09) — die Cluster-Überschrift (`<h3>`) auf `/curate` wird um optionale Orts-/Landmark-Information ergänzt.

**Neue Cluster-Überschrift mit Orts-Kontext**, Format `"<Ort> · <Tageszeit> (<Zeitspanne>)"`, Tageszeit bleibt immer sichtbar (ergänzt, nicht ersetzt). Der Ortsteil kommt fertig aufgelöst als `PhotoOut.cluster_place` vom Server; das Frontend bildet die Rangfolge nicht nach, sondern verzweigt über `kind`:

- `kind="landmark"`: `"Eiffelturm · Nachmittags (12:00–14:00 Uhr)"`
- `kind="coordinate"`: `"48.86, 2.29 · Nachmittags (12:00–14:00 Uhr)"`
- `kind="multiple"`: `"Mehrere Orte · Nachmittags (12:00–14:00 Uhr)"`
- `cluster_place === null`: `"Nachmittags (12:00–14:00 Uhr)"` — zeichengleich mit heute

**Umsetzungsort:** `formatClusterHeading()` in `frontend/src/utils/timeOfDay.ts`. Die Tageszeit-Berechnung und -Formatierung bleiben unverändert. `CurateCategoriesPage.tsx` rendert den gelieferten Text unverändert in die `<h3>` und braucht keine Änderung.

**Typografie & Layout:**

- Element: `<h3>` mit `text-base` (Überschriftenleiter des Design-Systems: h3 = Untergruppe). **Korrektur gegenüber der Fassung von 2026-08-20**, die `text-lg` nannte — der Wert stimmt seit dem Wechsel auf „Dark Utility Register" nicht mehr mit dem Code überein.
- Trennzeichen zwischen Ort und Tageszeit: Mittelpunkt `" · "` (kein Komma, um Verwechslung mit dem Dezimaltrenner der Koordinate zu vermeiden).
- Der Ortsteil ist ein Textpräfix, kein separates Element, kein Badge.

**Lange Sehenswürdigkeit-Namen:** kein Kürzen, keine Ellipse. Übliche Namen sind kurz (10–30 Zeichen); lange (z.B. „Kathedrale von Santiago de Compostela") brechen nach den Standardregeln der Überschrift um. Die Cluster-Überschrift ist keine enge Fläche wie eine Grid-Kachel — Zweizeiligkeit durch Umbruch ist akzeptabel und besser als ein abgeschnittener Ortsname. Die harte Obergrenze liegt ohnehin schon im Backend (`MAX_LANDMARK_NAME_LENGTH = 80`, Verwerfen statt Abschneiden, siehe Security).

**LLM-Freitext (Muss):** `landmark_name` ist der Rohausgabe-Text eines externen Modells. Er darf **ausschließlich als regulärer React-Textknoten** gerendert werden — nie `dangerouslySetInnerHTML`, nie als HTML-String-Prop einer Radix-/shadcn-Komponente, nie in `href`/`src`/`style`, nie als React-`key` (diese Rolle trägt weiterhin `clusterKey`). `title`/`aria-label` als Attribut bleibt zulässig. Dieselbe Auflage wie bei `FineLabelOut.raw_label`.

**Barrierefreiheit:** unverändert — semantisches HTML, die `<h3>` trägt die Überschrift-Rolle, keine zusätzlichen `aria-label` nötig.

**Design-System (`specs/architecture/0004-design-system.md`):** keine Ergänzung nötig — spezifische Seitenänderung (Textpräfix in einer bestehenden `h3`), kein wiederverwendbares abstraktes UI-Muster.

## Security

Sicherheitsrelevant, ja (`security-engineer`-Konsultation 2026-08-20, **nachgezogen 2026-09-09** auf den geänderten Architektur-Ansatz). Verifiziert: `thumbnails.py::generate_variants` verwirft beim Neuschreiben der Thumbnail-/Display-Varianten alle EXIF-Metadaten inkl. GPS — `GET /photos/{id}/image` liefert weder heute noch nach diesem Feature GPS-Daten. Die neuen `Photo.gps_lat`/`.gps_lon` und ihre API-Exposition sind damit der **erste** Kanal, über den Standortdaten aus Familienfotos das System verlassen. Vollständige Herleitung siehe `specs/architecture/0003-securitykonzept.md`, Abschnitt „Standortdaten (GPS aus EXIF)" samt Fortschreibung vom 2026-09-09.

**Was sich gegenüber der ersten Konsultation geändert hat:** Der Ansatz von 2026-08-20 fügte zwei Zahlenfelder hinzu. Der jetzt umzusetzende Ansatz exponiert zusätzlich **extern erzeugten Freitext** und berechnet den Anzeige-Ort **im Backend über den vollständigen Cluster**. Die frühere Aussage „keine neue Nutzereingabe, keine Injection-Fläche" trägt deshalb nur noch für den GPS-Anteil, nicht mehr für das Feature als Ganzes.

### 1. Erstmalige API-Exposition von LLM-Freitext als Ortsname (Muss-Kriterien)

`cluster_place.landmark_name` stammt aus `photo_landmark_detections.name` (Spec 0047, Implemented) und ist damit von einem externen Modell erzeugter Freitext, der erstmals die API verlässt und in einer Cluster-Überschrift gerendert wird. Spec 0047 hatte „kein UI-Verweis in v1" festgelegt; diese Grenze wird hier bewusst und ausschließlich für den Cluster-Namenszweck aufgehoben.

**Befund — der Landmark-Name ist im Unterschied zu `FineLabelOut.raw_label` nie saniert worden.** `landmark.py::_landmark_detection_from_json` prüft ausschließlich `isinstance(name, str)` und klemmt die *Konfidenz*; auf den Namen wirkt weder eine Zeichensanitisierung noch eine Längengrenze. Der Feinlabel-Pfad hat beides (`remote_classification.py::_sanitize_label_text`, `MAX_FINE_LABEL_LENGTH = 60`, verwerfen statt abschneiden). Der Landmark-Pfad hat es nie gebraucht, weil der Wert nie angezeigt wurde — genau dieser Schutz fällt hier weg.

- **XSS-Fläche:** gering und durch das bestehende Muster gedeckt. React escapet reguläre Textknoten; `CurateCategoriesPage.tsx` rendert die Überschrift als `<h3>{heading}</h3>`, und `formatClusterHeading()` liefert einen einfachen String. **Muss-Kriterium (wortgleich aus dem Feinlabel-Fall übernommen):** Rendering ausschließlich als regulärer React-Textknoten — nie `dangerouslySetInnerHTML`, nie als HTML-String-Prop einer Radix-/shadcn-Komponente, nie in `href`/`src`/`style`; `title`/`aria-label` als Attribut bleibt zulässig. Abgesichert durch einen Test analog `CloudVisionStatusList.test.tsx`. Der Landmark-Name darf außerdem **nie** als React-`key` dienen (heute trägt `clusterKey` diese Rolle, das bleibt so).
- **Zeichensanitisierung (Muss):** escapetes Rendering schützt gegen XSS, aber nicht gegen optische Verfälschung durch Bidi-/Zero-Width-Zeichen und nicht gegen mehrzeilige Logeinträge. `_sanitize_label_text` (Unicode-`Cc`/`Cf` entfernen, Whitespace-Folgen zusammenziehen) wird deshalb **an der Quelle** in `_landmark_detection_from_json` angewandt — mit derselben Funktion, nicht mit einer zweiten Fassung davon. Sie wandert dafür nach `cloud_vision.py`, das bereits die providerneutrale gemeinsame Schicht beider Cloud-Pfade ist.
- **Altbestand (Muss):** unter Spec 0047 sind bereits reale, kostenpflichtig erzeugte Zeilen mit unsaniertem Rohtext entstanden. Sie neu zu erkennen kostet Geld, sie zu löschen vernichtet bezahlte Daten — anders als beim Feinlabel-Fall (`UPDATE photo_scores SET category_override = NULL` als Sicherheitsbedingung) gibt es keinen kostenlosen Migrationsweg. Deshalb saniert **zusätzlich der Lesepfad**, der `cluster_place.landmark_name` befüllt. Die doppelte Anwendung ist hier kein Redundanz-Fehlgriff, sondern die einzige Deckung des Altbestands; der Grund gehört als Kommentar an die Lesestelle, sonst entfernt ihn später jemand als vermeintliche Dopplung.
- **Längenbegrenzung (Muss):** `MAX_LANDMARK_NAME_LENGTH = 80`, ein zu langer Name wird **verworfen, nie abgeschnitten** — das Cluster gilt dann als ohne Landmark und fällt auf die Koordinaten-Stufe zurück. Zwei Gründe: `refine_clusters_by_landmark` vergleicht exakt, ein abgeschnittener Name führte zwei verschiedene Sehenswürdigkeiten in einem Cluster zusammen (dieselbe Begründung wie die Slug-Kollision bei den Feinlabels); und die Überschrift ist einzeilig gedacht. 80 statt 60, weil echte Sehenswürdigkeitsnamen länger sind als Feinlabels („Kathedrale von Santiago de Compostela"). Wie `MAX_FINE_LABEL_LENGTH` eine **Degenerationsgrenze, keine Sanitisierungsmaßnahme**.
- **Nicht als Befund gewertet:** ein Name, der `" · "` oder Klammern enthält, kann die Struktur der Überschrift optisch nachahmen. Das ist kosmetisches Spoofing ohne Sicherheitsfolge; der gefährliche Teil (Bidi-/Zero-Width-Zeichen) ist durch die Sanitisierung abgedeckt.

**Prompt-Injection über Bildinhalte — erstmals steuert der Landmark-Name Kontrollfluss, mit bezifferter oberer Schranke.** `refine_clusters_by_landmark` teilt ein Cluster anhand eines vom Modell erzeugten Strings auf. Nach dem projektweiten Muss-Kriterium aus ADR 0069 („jede steuernde Verwendung eines Fremdwerts braucht eine bezifferte obere Schranke ihrer Wirkung") wird sie hier beziffert: die Zahl der Teil-Cluster eines Phase-A-Clusters ist durch die Zahl der Fotos **in diesem Cluster** absolut begrenzt (Extremfall: jedes Foto ein eigenes Cluster); der Kuratierungsmodus liefert dann höchstens den vollen Bildvorrat des Projekts aus — genau die Antwortgröße, die ADR 0071 mit `GET /projects/{id}/curation-candidates` ohnehin als zulässig gesetzt hat. Keine unbegrenzte Wirkung. Unangetastet bleibt die harte Trennlinie: `resolve_category`/`derive_photo_category` behalten ihre Signatur, der Landmark-Name geht in **keine** Kategorieentscheidung ein — er wirkt ausschließlich auf `PhotoRanking.cluster_key`, nie auf `PhotoScore.cluster_key` und nie auf `category_key`.

### 2. Backend-seitige Ortsherleitung über den vollständigen Cluster (Muss-Kriterien)

**Befund: `cluster_key` ist weder projekt- noch laufübergreifend eindeutig, und `photo_rankings` trägt keine `project_id`.** `scoring.py::assign_time_clusters` vergibt `f"cluster-{index}"` je Lauf; `cluster-0` existiert in **jedem** Projekt und in **jedem** Lauf. Die Projekt-Skopierung des gesamten Lesepfads hängt allein an `criterion_scoring_run_id`, aufgelöst über `CriterionScoringRun.project_id` (dieselbe strukturelle Tatsache, die die Konsultation zu Spec 0357 benannt hat).

- **Muss:** der neue Query filtert auf `criterion_scoring_run_id`, **nie** auf `cluster_key` allein. Ohne diese Filterung ordnete `source: "derived"` einem Foto **systematisch** — nicht nur im Grenzfall — Koordinaten aus fremden Projekten zu, weil die Schlüsselkollision garantiert ist, nicht zufällig. Dasselbe gilt für `cluster_place`.
- **Muss:** die Lauf-Id wird **einmal pro Request** aufgelöst und durchgereicht, nie innerhalb der Herleitung neu bestimmt. Sonst treffen Rangzeilen aus Lauf A auf Cluster-Mitgliedschaften aus Lauf B, sobald zwischen zwei Queries ein Lauf fertig wird. Betroffen sind alle drei `_to_photo_out`-Aufrufstellen (`list_photos` in beiden Query-Modi, `curation_candidates`).
- **Muss:** fehlt die Lauf-Id, ist das Ergebnis „kein hergeleiteter Ort". Die Ausfallrichtung ist „nichts anzeigen", nie „aus irgendeinem Lauf herleiten" — eine vergessene Durchreichung ergibt dann `null` statt eines falschen Ortes.
- **Muss:** die Herleitung liest `PhotoRanking.cluster_key` (den landmark-verfeinerten Schlüssel), nicht `PhotoScore.cluster_key`. Der gröbere Schlüssel führte den Ort über genau die Landmark-Grenze hinweg, die dieses Feature gerade zieht.
- **Muss (Verfügbarkeit):** **ein** Query pro Request, nicht einer pro Foto — Präzedenz `_partition_sizes`. Die Ergebnismenge ist durch die Projektgröße begrenzt, dieselbe Schranke, unter der `_partition_sizes` bereits läuft.

**Keine neue Sichtbarkeitsasymmetrie.** Der hergeleitete Ort stammt aus Fotos, die in der Antwort nicht enthalten sind, macht aber nichts sichtbar, was der Anfragende nicht ohnehin über das Standard-Listing desselben Projekts abrufen könnte (beide Nutzer sehen alle Projekte, „kein Innentäter-Modell"). Kein neuer Endpunkt, kein neuer Auth-Pfad: additive Feld-Erweiterung an den bestehenden, je Endpunkt per `Depends(get_current_user)` geschützten Lese-Endpunkten. Weder `location` noch `cluster_place` sind eine Funktion des anfragenden Nutzers — die in `api/photos.py::_to_photo_out` dokumentierte Auflage („ein Antwort-Zwischenspeicher/`ETag` muss den Nutzer im Schlüssel führen") bleibt allein von `suggestion` getragen und wird durch diese Felder **nicht** erweitert.

**`source` ist ein Sicherheitsmerkmal, kein Anzeigedetail.** `GPS_CLUSTER_SPLIT_DISTANCE_METERS` begrenzt den **Schritt** zwischen zwei aufeinanderfolgenden Fotos, nicht den **Durchmesser** eines Clusters — ein Spaziergang in 400-m-Schritten teilt nie und kann Kilometer überspannen. Eine `source: "derived"`-Koordinate kann deshalb beliebig weit von der tatsächlichen Aufnahmestelle entfernt liegen; sie ist eine Schätzung, nie eine Messung. **Muss:** `source` steht in der API-Antwort, wird nicht persistiert, und kein künftiger Verbraucher (Kartenansicht, Export, Reverse-Geocoding) darf `derived` wie `exif` behandeln.

### 3. EXIF-GPS-Parsing: Plausibilitätsgrenzen (Muss-Kriterien)

Der best-effort/breite-`except Exception`-Vertrag von `extract_gps` (analog `extract_taken_at`) bleibt Muss-Kriterium — ein einzelnes unlesbares Foto darf einen Scan-Lauf nie abbrechen. **Er reicht hier aber nicht aus.**

**Verifiziert am Projektstand (Pillow 12.3.0):** `IFDRational(x, 0)` ergibt **`nan` ohne jede Exception**, und `nan` propagiert durch die DMS-Arithmetik. Landet es in `Photo.gps_lat`, nimmt PostgreSQL (`double precision`) es an und SQLite im Testlauf ebenfalls — aber Starlettes `JSONResponse.render` serialisiert mit `allow_nan=False`: ein einziges betroffenes Foto legt die **gesamte** Listenantwort des Projekts dauerhaft auf 500, bis ein erneuter Scan den Wert überschreibt. Exakt die Defektklasse, die das Sicherheitskonzept bereits für die Kategorie-Konfidenz festhält, mit derselben Konsequenz: **die Prüfung gehört an den Parser, nicht an die Datenbankschicht** — über die DB-Schicht ist ihr nicht beizukommen, weil der Testlauf auf SQLite läuft.

Verbindliche Grenzen:

- `-90.0 <= lat <= 90.0` und `-180.0 <= lon <= 180.0` als **Bereichsvergleich, nie als Klemmen** — ein Klemmen ließe `nan` durch, weil jeder Vergleich `False` ergibt (dieselbe Falle wie bei der Konfidenz).
- Scheitert eine Komponente, werden **beide** verworfen. Nie eine halbe Koordinate.
- `GPSLatitudeRef`/`GPSLongitudeRef` müssen nach Trimmen von Whitespace/NUL und Großschreibung exakt `N`/`S` bzw. `E`/`W` lauten. Fehlend oder abweichend verwirft die Koordinate — **kein stiller Default auf `N`/`E`**, der spiegelte die Südhalbkugel wortlos auf die Nordhalbkugel.
- Genau drei DMS-Komponenten; ihre Konvertierung liegt **innerhalb** des geschützten Blocks (ein absurder Zähler wirft `OverflowError` — eine Exception und damit gedeckt, aber nur dort).
- Der `try` umfasst Arithmetik **und** Bereichsprüfung, nicht nur `Image.open`/`get_ifd` — anders als bei `extract_taken_at`, wo die riskante Stelle tatsächlich nur das Öffnen/Parsen ist.
- Ein abgeschnittenes Range-Read-Fenster (`worker.py::_EXIF_RANGE_BYTES = 131_072`) ergibt **nicht** verlässlich „gar kein Wert" — je nach Abbruchpunkt eine Ausnahme **oder** einen teilgelesenen Unsinnswert. Den zweiten Fall deckt allein die Bereichsprüfung.
- Das exakte Paar `(0.0, 0.0)` wird verworfen — Geräte schreiben es bei fehlgeschlagenem Fix, es liegt im gültigen Bereich, setzt ein Cluster in den Golf von Guinea und risse bei 500 m Schwelle sein Cluster gleich zweimal auf (hinein und hinaus).

**Logging (Muss): Koordinaten gehören nie in ein Log.** Standortdaten sind seit ADR 0029 ein eigenständiges Asset; eine Logzeile ist eine schwächer geschützte, länger lebende Oberfläche als die Datenbank. Weder ein akzeptierter noch ein verworfener Rohwert wird geloggt — nur ein festes Grund-Token (`ausserhalb_intervall`, `ref_fehlt`, `nicht_numerisch`) plus `photo_id`, nach dem Muster von `remote_classification.py::_CONFIDENCE_REASON_*` und aus derselben Begründung: die Fehlerklasse trägt den vollen Diagnosewert, der konkrete Wert nichts darüber hinaus. Für einen mitgeloggten Landmark-Namen gilt `%r` plus Längenbegrenzung (Log-Injection).

### 4. Unbedingtes Zurückschreiben beim Scan (Muss-Kriterium)

`_fetch_and_thumbnail` liefert künftig Zeitpunkt **und** Koordinate; `_process_scan_block` schreibt **beide** Felder für jeden verarbeiteten Arbeitsposten, auch zurück auf `None`. Das ist eine Datenschutzbedingung, keine Aufräum-Kosmetik: es ist der **einzige** Pfad, über den das *Entfernen* von GPS aus einer Quelldatei in PhotoSort ankommt — also genau die Handlung, die eine datenschutzbewusste Person vornimmt. Ein bedingtes Schreiben (`if gps is not None`) hielte die alte Koordinate unbegrenzt fest, und die Anwendung zeigte weiter einen Ort an, den die Datei nachweislich nicht mehr enthält, ohne dass das irgendwo auffiele. Für Nicht-JPEG-Posten wird kein EXIF gelesen, beide Felder bleiben `None` — konsistent, sie hatten nie eine Koordinate. Die bestehende Typzusicherung nach `asyncio.gather` (`assert isinstance(taken_at, datetime)`) muss beim Wechsel auf einen zusammengesetzten Rückgabewert weiterhin die **Form** festnageln, damit keine durchgereichte `BaseException` in die Felder entpackt wird.

### 5. Unverändert gültig

- **Kein SSRF, keine neue Netzwerkverbindung:** GPS teilt sich das bereits für `taken_at` geladene Range-Read-Fenster, Haversine läuft rein lokal.
- **Keine Kombination mit der Cloud-Vision-API:** GPS/EXIF wird nie an Anthropic/Mistral übertragen (ADR 0029/0025); die `display`-Variante trägt keine EXIF-Daten. Die Re-Identifikationskette „GPS + Landmark + Cloud-Transfer" tritt strukturell nicht ein — beide Werte kommen ausschließlich lokal zusammen.
- **API-Präzision (Daniels Entscheidung 2026-08-20):** volle EXIF-Präzision in `location` statt serverseitiger Rundung; die Rundung auf 2 Dezimalstellen liegt in `cluster_place`. **Das ist eine Verlagerung der Anzeigeableitung, keine Härtung** — die volle Präzision steht in derselben Antwort, `cluster_place` rundet nur, weil dort dieselbe Zahl über `"coordinate"` vs. `"multiple"` entscheidet. Das bestehende JWT-Diebstahl-Restrisiko wird dadurch in der Datenschutzdimension verschärft (zusätzlich zum Fotozugriff exakte Standortdaten, potenziell die Wohnadresse) — bewusst akzeptiert statt serverseitig gehärtet, begründet mit Flexibilität für eine mögliche künftige Kartenansicht.
- **Reichweite der Ortsfelder (Daniels Entscheidung 2026-09-09):** `location` und `cluster_place` werden einheitlich auf allen Lesepfaden ausgeliefert, nicht nur im Kuratierungsmodus. Datensparsamkeit wurde gegen ein einheitliches `PhotoOut` abgewogen; ein je Query-Modus divergierendes Antwortobjekt wäre die größere Fehlerquelle.
- **`GPS_CLUSTER_SPLIT_DISTANCE_METERS = 500.0` statt 2000 hat für sich genommen keine Datenschutzfolge:** weder die gespeicherte noch die übertragene Präzision ändert sich; die Schwelle wirkt nur auf die Partitionierung, und `cluster-3` sagt nichts über einen Ort aus. Zweitrangiger Effekt in die entlastende Richtung: die feinere Auflösung lässt die Fotos eines Clusters häufiger in dieselbe 2-Dezimalstellen-Zelle (~1,1 km) fallen, der `kind="multiple"`-Fall greift seltener und die angezeigte gerundete Koordinate ist öfter ein treuer Repräsentant.
- **Reverse-Geocoding bleibt Out of Scope** — eigene künftige Spec mit eigener `security-engineer`-Konsultation (neue externe Abhängigkeit, sensiblere Datenexposition).

## Teststrategie

Vollständig in `specs/architecture/0002-testkonzept.md` als Sektion **„GPS-Cluster-Split (Haversine mit zurückgesetzter Bezugskoordinate) + indexbasierte Landmark-Verfeinerung aus persistierten Zeilen + eine Anzeigeherleitung, deren Bezugsmenge NICHT die Antwort ist"** festgehalten (`test-engineer`-Konsultation 2026-08-20, **am 2026-09-09 vollständig überschrieben**, nachdem sich der Architekturansatz an vier Stellen verändert hat). Kernpunkte:

- **Unit (`backend/tests/test_scoring.py`), Schwerpunkt `assign_clusters`:** Bestandsfälle der Zeitfenster-Clusterbildung bleiben unverändert grün; neue Fälle für den reinen GPS-Sprung ohne Zeitlücke, das Schwellwertverhalten **am Symbol statt am Zahlwert** (`GPS_CLUSTER_SPLIT_DISTANCE_METERS ± ε`, nie `500` als Literal), die drei Fälle rund um die **Bezugskoordinate** (koordinatenloses Foto unterdrückt keine Trennung; Rücksetzung an der Zeitgrenze; Rücksetzung nach einem GPS-Split), die **kumulative Drift ohne Split** und die exakte `dict`-Gleichheit gegen eine im Test nachgebildete Referenzimplementierung des alten Zeitverhaltens.
- **Unit, Haversine einzeln:** identische Koordinaten, Antipoden, 180°-Meridian, Breitenabhängigkeit — plus ein **Einheitennachweis** an einer bekannten Referenzstrecke (1° Breite ≈ 111 195 m, ±0,1 %). Bei 500 m Schwelle ist ein Meter/Kilometer-Dreher die Grenze zwischen „trennt nie" und „trennt immer"; die abstrakten Schwellwerttests bestehen bei jeder Einheit und finden ihn nicht.
- **Unit `refine_clusters_by_landmark` (DB-frei, `dict[int, str | None]`):** Schlüsselform (`cluster-3-1`, 1-basiert, kein Name im Schlüssel) gegen ein festes Erwartungs-`dict`; **alphabetische** Vergabe statt Antreffreihenfolge; **Determinismus über die Eingabereihenfolge**; Codepunkt-Sortierkonvention (keine locale-abhängige Kollation); **unbenannte Fotos behalten den Basis-Schlüssel** (ein Cluster mit zwei Namen und zwei namenlosen Fotos ergibt genau drei Schlüssel); genau ein Name im Cluster → keine Verfeinerung; Passthrough; exakter String-Vergleich ohne Fuzzy-Matching.
- **Integration (`backend/tests/test_worker_criterion_scoring.py`):** **Lauf ohne Cloud-Phase als Rot-Anker** — Einwilligung aus bzw. alle Fotos bereits früher erkannt, Namen liegen nur in `photo_landmark_detections`: die Aufteilung muss vollständig greifen. Dazu gemischte Herkunft in einem Lauf (belegt, dass nach der Cloud-Phase gelesen wird), Wirkungslosigkeit von Zeilen zu Fotos ohne Kandidatenzeile, der `PhotoRanking`-vs-`PhotoScore`-Divergenz-Regressionstest samt expliziter „unverändert"-Assertion auf `PhotoScore`, der Passthrough-Fall und der Nachweis, dass die Partitionsbildung den verfeinerten Schlüssel nutzt.
- **Unit (`backend/tests/test_exif.py`) `extract_gps`:** Vorzeichenumkehr Süd/West tatsächlich angewendet; fehlendes IFD und trunkierte Bytes → `None` ohne propagierten Fehler; `IFDRational` mit Nenner 0; DMS→Dezimalgrad an einer Referenzkoordinate mit enger Toleranz; **Paar-Invariante** (beide Werte oder keiner); fehlender `GPSLatitudeRef`/`GPSLongitudeRef` → `None` statt Annahme „Nord/Ost"; Wertebereich und Verwerfen von exakt `(0.0, 0.0)`.
- **Integration (`backend/tests/test_api_photos.py`), die Anzeigeherleitung — Pflichtabdeckung:** Bezugsmenge ist der **vollständige Cluster des Bezugslaufs**, nie die Fotos der Antwort. Zwei Rot-Anker: (a) das einzige koordinatentragende Foto eines Clusters liegt auf `rank_position` 11, abgefragt mit `top_n_per_category=3` → alle drei sichtbaren Fotos tragen `location` mit `source="derived"`; (b) das einzige Foto mit einer Erkennung bzw. das einzige mit abweichender gerundeter Koordinate liegt außerhalb der Antwort → `cluster_place.kind` ist trotzdem `"landmark"` bzw. `"multiple"`. Dazu die Gleichheit von `cluster_place` über `list_photos` (beide Modi, `limit=1` wie `limit=60`) und `curation_candidates` als direkter „springt nicht"-Nachweis, `cluster_place` auf allen Fotos eines Clusters identisch (gruppiert nach `cluster_key` geprüft, nicht stichprobenweise — `location` *darf* je Foto verschieden sein, `cluster_place` **nicht**), `kind="multiple"` führt nie `lat`/`lon`, zwei Koordinaten mit gleicher gerundeter Stelle → `kind="coordinate"` (naheliegender Fehler: Vergleich der **ungerundeten** Werte, der schon bei 40 m zuschlägt), die **Rundungskonvention selbst** dort, wo sie entsteht (zwei Nachkommastellen, negative Werte, Halbschritt) — sie entscheidet über die Stufe und gehört deshalb ins Backend, die `null`-Abgrenzung getrennt für beide Felder (namentlich `location = null` bei gesetztem `cluster_place`, wenn der Cluster nur einen Namen und kein Foto eine Koordinate trägt), der deterministische Tie-Break, das Verhalten ohne Bezugslauf/ohne Kandidatenzeile und eine feste, fotoanzahl-unabhängige Abfrageanzahl (`before_cursor_execute`-Mitschnitt, Muster aus `test_project_deletion.py`).
- **Sicherheit — Laufbindung als Pflichtfall:** `cluster_key` ist `cluster-<n>`, je Lauf neu vergeben und **in jedem Projekt derselbe String**; `PhotoRanking` trägt keine `project_id`. Eine Herleitungsabfrage ohne `criterion_scoring_run_id`-Prädikat zieht Koordinaten aus einem fremden Projekt — bei genau der Datenklasse, die dieses Feature erstmals überhaupt exponiert. Dasselbe gilt für Namen, nicht nur Koordinaten — sonst benennte `cluster_place` ein Cluster nach einer Sehenswürdigkeit aus einem fremden Projekt. Testfall: zwei Projekte mit je `cluster-0`, nur B hat Koordinaten und Erkennungen, A muss `location = null` **und** `cluster_place = null` liefern.
- **Sanitisierung und Längengrenze als Verhalten, nicht als Implementierungsdetail:** Pflichtfall an einer **unsanierten Bestandszeile** (ein Test nur an der Quelle beweist für den Altbestand aus Spec 0047 nichts, und für ihn gibt es keinen kostenlosen Migrationsweg); ein Name über `MAX_LANDMARK_NAME_LENGTH = 80` oder ein nach der Sanitisierung leerer Name lässt den Cluster auf `kind="coordinate"` bzw. `null` **zurückfallen** — der Rückfall ist der Testgegenstand, nicht das Verwerfen. Ohne diese Fälle stehen drei Muss-Kriterien des Security-Abschnitts ohne jeden Test da, und das 80-%-Gate rötet dabei nie.
- **Migration:** eigener `test_migration_*`-Fall (beide Spalten nullable, Bestandszeilen überleben mit `NULL`, `downgrade()` entfernt sie), `test_migration_chain.py` bleibt bei einem Head, `test_postgres_ddl_compatibility.py` deckt die Typwahl mit ab.
- **Demo-Zustand (`demo_state.py`/`test_demo_state.py`):** der Seeder muss alle vier Anzeigezustände der Cluster-Überschrift erzeugen — sonst ist die Sichtprüfung über `browse-app` für drei davon blind, und das ist die einzige nicht automatisierte Kontrollinstanz des Features.
- **Frontend (`vitest`, `timeOfDay.test.ts`):** `formatClusterHeading()` übernimmt den Ortsteil fertig aufgelöst und aggregiert nicht selbst. Pflichtfall **Teilmengen-Invarianz** (dieselbe Cluster-Fixture mit 3 und mit 10 Fotos → identische Überschrift), alle vier Zustände plus unveränderter Fallback ohne Ortsinformation, reine Formatierung mit Vorzeichen (`-0.0` als `0.0`; die Rundungskonvention selbst wird im Backend geprüft, wo sie entsteht), `kind="multiple"` zeigt nie eine Koordinate, uneinheitliche `cluster_place`-Werte im Eingabearray (defensiv) sind deterministisch, Trennzeichen und Reihenfolge als Zeichenkettenvergleich.
- **Frontend, LLM-Freitext:** ein Test analog `CloudVisionStatusList.test.tsx`, der belegt, dass ein `landmark_name` mit HTML-artigem Inhalt als Text erscheint und nicht als Markup.
- **E2E/Smoke:** keiner (Aufnahmekriterium: nur, was jsdom prinzipiell nicht kann). Kalibrierung von `GPS_CLUSTER_SPLIT_DISTANCE_METERS` bleibt manueller Stichproben-Review durch Daniel.

**Coverage-Gate:** Bei gemessenen ~97 % Backend-Coverage könnte die neue Hilfsfunktion in `api/photos.py` samt Verdrahtung vollständig ungetestet bleiben, ohne das 80-%-Gate (`--cov-fail-under=80`) zu röten. Die oben genannten Pflichtfälle sind **namentlich** verbindlich und werden nie aus der Prozentzahl abgeleitet.

**Relevante Edge Cases:** Bezugskoordinate über ein koordinatenloses Foto hinweg und ihre Rücksetzung an jeder Cluster-Grenze; kumulative Drift unter der Schwelle; 180°-Meridian und Breitenabhängigkeit; Meter-vs-Kilometer; halbes Koordinatenpaar und `(0.0, 0.0)`; drei Schlüssel aus einem Cluster mit zwei Namen und namenlosen Fotos; genau ein Name → keine Verfeinerung; Lauf ohne Cloud-Phase und gemischte Herkunft der Landmark-Zeilen; tragendes Foto außerhalb der Antwort (Top-N und `limit`/`offset`, für `location` wie für `cluster_place`); Cluster ohne jede Ortsinformation; fehlender Bezugslauf; gleichnamiger `cluster_key` in einem fremden Projekt; unsanierte Bestandszeile aus Spec 0047; zu langer und nach Sanitisierung leerer Name → Rückfall auf die Koordinatenstufe.

**Nicht automatisiert testbar (bekannte Lücken, im Testkonzept dokumentiert):** der unkalibrierte 500-m-Schwellwert (nur Verhalten an der Schwelle und Einheit sind geprüft, nie die Zahl); die Kette EXIF → Cluster → Überschrift ist nirgends durchgehend geprüft, ein sich aufhebender Vorzeichen-/Einheitenfehler bliebe unsichtbar; ob ein echtes Vision-Modell für zwei Fotos derselben Sehenswürdigkeit denselben String liefert (exakter Vergleich), prüft nichts und kann hier nichts prüfen.

**Testkonzept ergänzt:** `specs/architecture/0002-testkonzept.md` — Sektion vollständig überschrieben (die vier ungültig gewordenen Testaussagen der Fassung von 2026-08-20 sind dort namentlich benannt statt still ersetzt), plus drei neue Einträge unter „Bekannte Lücken".

## Entscheidungen

**Aus dem Idea-Sharpening-Gespräch mit Daniel (2026-08-20):**

- **Kern der Idee:** GPS/Zeit/Landmark verändern die Cluster-BILDUNG selbst, nicht nur eine kosmetische Namenserweiterung wie in Spec 0039 — Daniel hat sich explizit für den größeren Eingriff entschieden.
- **Abhängigkeit zu Spec 0047:** diese Spec baut bewusst auf der Landmark-Erkennung auf, statt unabhängig nur mit rohen GPS-Koordinaten zu arbeiten. (Die damals daraus folgende strukturelle Blockade besteht nicht mehr — Spec 0047 ist inzwischen implementiert.)
- **Devil's-Advocate-Ergebnis:** kein konkret erlebtes Problem (rein vorausschauend), Abhängigkeit von 0047, in der Praxis oft fehlende GPS-Daten, und ein zunächst identifizierter Pipeline-Architektur-Konflikt wurden Daniel offen vorgelegt — er hat sich bewusst für die volle Idee entschieden.
- **Pipeline-Konflikt-Auflösung (an `architect` delegiert):** zweiphasige Cluster-Bildung ohne neuen Job/ohne Pipeline-Umbau (ADR 0029) — `PhotoScore.cluster_key` (früh, Zeit+GPS) und `PhotoRanking.cluster_key` (spät, zusätzlich Landmark-verfeinert) dürfen bewusst divergieren, analog zur `category_key`-Trennung aus ADR 0021.
- **Reverse-Geocoding (an `architect` delegiert):** bewusst Out-of-Scope — neue externe Abhängigkeit + sensiblere Datenexposition, verdient eine eigene künftige Spec mit eigener Security-Konsultation.
- **Cluster-Überschrift-Aufbau:** Ort ergänzt die Tageszeit-Angabe, ersetzt sie nicht — die Zeit-Orientierung aus Spec 0039 bleibt immer erhalten.
- **GPS-Anzeige-Präzision:** grob, 2 Nachkommastellen (~1 km) für die Anzeige.
- **API-GPS-Präzision (Rückfrage von `security-engineer`):** volle EXIF-Präzision über die API statt serverseitiger Rundung — mehr Flexibilität für künftige Features (z.B. Kartenansicht), bewusst akzeptierte Verschärfung des bestehenden JWT-Diebstahl-Restrisikos in der Datenschutz-Dimension.
- **„Mehrere Orte"-Trigger-Präzisierung (von `test-engineer` aufgedeckter Widerspruch, als rein technische Frage direkt aufgelöst):** ursprünglich als „unterschiedliche Landmark-Namen im selben Cluster" definiert — unvereinbar mit der Architektur, da `refine_clusters_by_landmark` genau dann aufteilt. Der Zustand ist ausschließlich in der Koordinaten-Stufe erreichbar (keine Landmark-Info, aber abweichende gerundete Koordinaten im Cluster).
- **Priorität — Niedrig (nach Schärfung bestätigt):** rein vorausschauend, kein akuter Missstand. (Der Board-Wert steht heute auf `Mittel`; maßgeblich ist das Board, nicht diese historische Notiz.)

**Aus der technischen Nachschärfung (2026-09-09, vor der Umsetzung):**

- **Bestandsnachzug: nein (Daniel).** Der Scan überspringt Dateien mit unverändertem `Etag`, und die Cache-Varianten haben ihr EXIF verloren — Koordinaten entstehen nur für ab jetzt neu eingelesene oder auf OpenCloud geänderte Dateien. Die Alternative (Markerspalte + reduzierter Arbeitsposten, der nur das EXIF-Fenster liest, einmalig ~128 KB pro Bestandsfoto) wurde Daniel mit Kosten und Folgen vorgelegt und bewusst verworfen. Sie hätte ein zusätzliches Akzeptanzkriterium und eine eigene ADR erfordert.
- **Trennabstand: 500 m (Daniel, Empfehlung des `architect` bestätigt).** Der auslösende Story-Fall liegt innerstädtisch bei einigen hundert Metern (Eiffelturm ↔ Trocadéro ≈ 700 m); die 2000 m aus dem unverbindlichen Vorschlag in ADR 0029 hätten genau ihn nicht getrennt. Bewusst in Kauf genommene Kehrseite: Aufnahmen aus einem fahrenden Fahrzeug erzeugen viele kleine Cluster.
- **Reichweite der Ortsfelder: einheitlich auf allen Lesepfaden (Daniel, Rückfrage von `security-engineer`).** Datensparsamkeit wurde gegen ein einheitliches `PhotoOut` abgewogen; ein je Query-Modus divergierendes Antwortobjekt wäre die größere Fehlerquelle.
- **Zwei getrennte Ortsfelder statt eines (`architect`, ADR 0072, technische Entscheidung):** Der von `test-engineer` gemeldete Defekt reicht weiter als gemeldet — die nachgeladenen Kandidaten fließen nicht nur „nicht in `items`", sie fließen nie zurück; die Überschrift wäre also **dauerhaft** eine Aussage über die Top-N statt beim Aufklappen zu springen. Und derselbe Defekt trifft den Sehenswürdigkeit-Namen: trägt in einem Cluster nur ein Foto auf Rang 12 eine Erkennung, bliebe der Cluster dauerhaft unbenannt. Ein bloßes `multiple_places: bool` hätte nur die Hälfte geheilt. Deshalb `cluster_place` mit `kind` — der fertig aufgelöste Zustand, nicht ein Flag; das Frontend bildet die Rangfolge nicht nach, und `kind="multiple"` kann strukturell keine stellvertretende Koordinate mitführen.
- **`(0.0, 0.0)` und fehlender Ref werden in `extract_gps` verworfen (`test-engineer` vorgeschlagen, `architect` übernommen):** beide gehören in den Parser, nicht in die Verbraucher — was dort verworfen wird, erreicht die Datenbank gar nicht erst.
- **Landmark-Name wird saniert und längenbegrenzt (`security-engineer`):** `_sanitize_label_text` an der Quelle **und** im Lesepfad (der Altbestand aus Spec 0047 ist unsaniert und hat keinen kostenlosen Migrationsweg), `MAX_LANDMARK_NAME_LENGTH = 80` mit Verwerfen statt Abschneiden.
- **Dritte Sanitisierungsstelle: `worker.py::_landmark_names` (bei der Umsetzung ergänzt, im Review bestätigt).** Die beiden oben genannten Stellen decken die *Anzeige*, nicht die *Cluster-Bildung*. Ohne Sanitisierung auch dort risse ein unsanierter Altname sein Cluster gegen den sauberen Zwilling desselben Orts auf — `refine_clusters_by_landmark` vergleicht exakt. Derselbe Altbestandsgrund, eigener Testfall.
- **`text-lg` → `text-base` (`ux-ui-designer`):** die Angabe von 2026-08-20 stimmt seit dem Wechsel auf „Dark Utility Register" nicht mehr mit dem Code überein.

Keine offenen Fragen mehr für den Scope dieser Spec.

## Out of Scope

- **Nachträgliches Einlesen der Koordinaten bereits gescannter Fotos** — Koordinaten entstehen nur für ab jetzt neu eingelesene oder auf OpenCloud geänderte Dateien (Daniels Entscheidung 2026-09-09, siehe Entscheidungen).
- Reverse-Geocoding (Koordinaten → Klartext-Ortsname wie „Paris") — eigene, künftige Spec mit eigener Security-Konsultation.
- Änderung der Landmark-Erkennung selbst (Spec 0047) — diese Spec konsumiert nur deren Ergebnis (`landmark_name`), saniert es aber beim Lesen.
- Persistierung der hergeleiteten Orte und des Cluster-Orts — rein zur Anzeigezeit berechnet, günstig neu berechenbar.
- Serverseitige Rundung/Härtung der GPS-Präzision in `location` — bewusst nicht gewünscht (Daniels Entscheidung, siehe Security-Abschnitt).
- Karten-/Geo-Visualisierung der Fotos — reine Textanzeige in der Cluster-Überschrift, kein Kartenwidget.
- Konfigurierbarkeit der Schwellenwerte über UI/Settings — reine Modulkonstanten im Code.
