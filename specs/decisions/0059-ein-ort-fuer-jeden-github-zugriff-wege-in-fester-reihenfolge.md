## Kontext

PhotoSorts Entwicklungsablauf greift an vielen Stellen auf GitHub zu: Issues anlegen und beschreiben, Board-Status und Priorität setzen und lesen, Pull Requests eröffnen und verknüpfen, ein Copilot-Review anfordern und auswerten. Jede dieser Stellen kennt heute genau **einen** Zugangsweg — die CLI `gh` —, und in Cloud-Sessions trägt der nicht. Am 2026-09-06 in einer solchen Session erneut gemessen:

```
gh api graphql …                → HTTP 403: This GraphQL query is not enabled for this session —
                                  only the pinned set of PR-review operations is served.
gh api repos/TheRealKoller/photosort/issues/339
                                → HTTP 403: GitHub access is not enabled for this session.
gh issue view 339               → 403 (spricht intern GraphQL)
gh project item-edit 8 …        → unknown owner type
```

Dieselbe Session liest und schreibt Issues und Pull Requests **problemlos** — über die GitHub-MCP-Werkzeuge, angemeldet als Repository-Eigentümer. Der Befund ist damit derselbe wie in ADR 0056 und in [`docs/setup.md`](../../docs/setup.md) bereits notiert: **Die Grenze verläuft am Client, nicht am Transport und nicht an den Rechten.**

Zwei Dinge machen daraus ein Architekturproblem statt einer Fußnote:

**Erstens ist der Schaden wiederkehrend.** Er fällt in *jeder* Cloud-Session an, und er fällt an Schritten an, die eigentlich gehen würden. Eine remote begonnene Story scheitert heute schon am Anlegen des Issues — obwohl die Session Issues anlegen kann.

**Zweitens ist die Ursache strukturell.** Nicht die einzelne Befehlszeile ist falsch, sondern dass jede Stelle im Ablauf ihren Zugangsweg selbst und einzeln kennt. Es gibt keinen Ort, an dem sich „probiere Weg A, dann Weg B" überhaupt formulieren ließe. Der 2026-09-05 erreichte Zustand (ADR 0057) hat die Befehle immerhin an einer Stelle gesammelt — aber nur die Board- und Issue-Befehle. Die Pull-Request-Operationen liegen bis heute außerhalb, direkt in `.claude/skills/ship-feature/SKILL.md`, weil ein Skill namens `github-board` niemand einlädt, um einen Pull Request zu eröffnen. Der Name hat die Sammlung begrenzt.

Ein dritter Befund kam bei der Konsultation zu dieser Story hinzu und ist für den Zuschnitt entscheidend: **Der Werkzeugkasten unterscheidet sich nicht nur zwischen Umgebungen, sondern zwischen Kontexten derselben Session.** Der als Subagent laufende `architect` bekam auf einen Aufruf von `mcp__github__issue_read` die Antwort „Its MCP server 'github' is connected but does not offer this tool here" — der Server ist verbunden, sein Werkzeugsatz für Subagenten aber beschnitten. Es gibt außerdem **keine `.mcp.json` im Repository**: Die MCP-Anbindung ist Eigenschaft der Umgebung und der Nutzerkonfiguration, nicht des Projekts. Ein Entwurf, der die MCP-Werkzeuge als gesetzt voraussetzt, wäre damit genauso zerbrechlich wie der heutige, der `gh` voraussetzt.

## Entscheidung

### 1. Genau ein Ort: der Skill `github-access` (vormals `github-board`)

`.claude/skills/github-board/` wird zu `.claude/skills/github-access/`, Verzeichnis und Frontmatter-`name`. Der Zuschnitt ist ab hier nicht mehr „das Board", sondern **jeder GitHub-Zugriff des Entwicklungsablaufs**: Issue, Board, Pull Request, Copilot-Review.

Die Umbenennung ist nicht Kosmetik. Der alte Name war die *Ursache* der heutigen Verstreuung: Er beschreibt einen Ausschnitt, und alles außerhalb dieses Ausschnitts landete folgerichtig woanders. Ein Ort, der nur die Hälfte der Zugriffe aufnimmt, erzeugt genau die zweite Hälfte, die er nicht aufnimmt.

Danach gilt, ohne Ausnahme:

- **Keine andere Datei enthält einen GitHub-Befehl oder einen GitHub-Werkzeugaufruf.** Nicht `capture`, `refinement`, `spec-writer`, `ship-feature`; nicht die Review-Skills; nicht `CLAUDE.md`; nicht die Agenten-Dateien.
- **Erlaubt bleibt in anderen Dateien ausschließlich der *Name* einer Operation** aus dem Katalog (Abschnitt 2), in Backticks, plus die Ablauf-Logik drumherum: wann sie läuft, in welcher Reihenfolge, unter welcher Bedingung, wie ihr Ergebnis ausgewertet wird. Die Ablauf-Logik gehört weiterhin in den jeweiligen Ablauf-Skill — sie ist dessen Gegenstand, nicht der des Zugriffs.
- **Rein lokales `git` bleibt unberührt** (`git status`, `git diff`, `git log`, `git checkout`, `git commit`, `git push`). `git push` spricht zwar mit GitHub, ist aber kein Zugriff auf Issues/Board/Pull Requests und hat keinen zweiten Weg; er bleibt dort, wo er heute steht.
- **Nicht berührt ist `.github/workflows/`** (heute: `gh pr merge --auto --squash` in `release-please.yml`). Das läuft in GitHub Actions mit dem `GITHUB_TOKEN`, nicht in einer Session, hat keinen alternativen Weg und keinen Bezug zu dieser Entscheidung.

`github-access` **bleibt Text.** Kein Werkzeug, kein Skript, keine Wiederbelebung von `scripts/gh-board.py` — ADR 0057, Abschnitt 4 gilt darin unverändert fort, und die Begründung („ein Wrapper um zwei konstante Argumente ist teurer als die Wiederholung") wird durch mehrere Wege nicht schwächer, sondern stärker: Ein Werkzeug müsste die MCP-Werkzeuge selbst gar nicht erreichen können, es liefe in einem Subprozess ohne Zugriff auf den Werkzeugkasten der Session.

Ein Ablauf-Skill lädt `github-access` **einmal** über das Skill-Werkzeug, an seinem ersten GitHub-Berührungspunkt, und arbeitet danach für den Rest seines Laufs mit dem geladenen Katalog. Dasselbe Muster, mit dem der `review`-Orchestrator die `review-*`-Skills aufruft.

### 2. Der Operationskatalog: stabile IDs, und pro Operation die Wege in fester Reihenfolge

Der Skill führt eine geschlossene Liste von **Operationen**. Jede trägt eine stabile, kebab-case ID in Backticks (`issue-anlegen`, `board-status-setzen`, `pr-erstellen`, …). Diese ID ist die einzige Form, in der andere Dateien auf einen GitHub-Zugriff verweisen. Das ist nicht Formalismus, sondern der Mechanismus, der „genau ein Ort" von einer Absichtserklärung zu einer statisch prüfbaren Eigenschaft macht (Abschnitt 8): Ein geschlossenes Vokabular lässt sich gegen den Katalog halten, eine Prosa-Beschreibung nicht.

Jede Operation nennt ihre **Zugangswege in fester Reihenfolge**. Ein „Weg" ist eine Klasse von Zugriffsmitteln; heute gibt es genau zwei:

- **`mcp`** — die GitHub-MCP-Werkzeuge der Session.
- **`gh`** — die CLI.

**Die Reihenfolge ist `mcp` vor `gh`**, überall wo beide existieren. Drei Gründe: In der Umgebung, wegen der die Leiter überhaupt gebaut wird, trägt der erste Versuch dann sofort statt nach einem sicheren Fehlschlag; lokal tragen beide Wege, es geht also nichts verloren; und der MCP-Weg hat keine Shell, also auch keinen Injektionsrand (Regel 4.1 ist dort strukturell erfüllt).

**Der Preis ist benannt und bewusst hingenommen:** Der Alltag läuft danach über den Weg, den kein statischer Test prüfen kann, während die statisch geprüften `gh`-Befehlsformen (Abschnitt 8) zum selten gelaufenen Rückfallweg werden. Ein Formfehler im `gh`-Weg fiele also erst dann auf, wenn er gebraucht wird — im ungünstigsten Fall in genau der Session, in der er die letzte Möglichkeit ist. Die Formprüfungen bleiben deshalb ausdrücklich bestehen und werden **nicht** mit dem Argument abgebaut, sie prüften einen Nebenweg: Sie sind die einzige Absicherung, die dieser Weg noch hat, und ihr Wert steigt in dem Maß, in dem er seltener läuft. Die Gegenoption (`gh` zuerst, MCP als zweiter Weg) hielte den geprüften Weg im Alltag, kostete aber in jeder Cloud-Session je Operation einen sicher scheiternden Aufruf, bevor der funktionierende drankommt — abgewogen und am 2026-09-06 von Daniel zugunsten von `mcp` zuerst entschieden.

Der vollständige Katalog mit Zuordnung. Keine heute vorhandene Operation geht verloren; die sechs bisher außerhalb liegenden Pull-Request-Operationen aus `ship-feature` sind ausdrücklich enthalten:

| Operation | Wege (in dieser Reihenfolge) | heute beheimatet in |
|---|---|---|
| `issue-anlegen` | `mcp`, `gh` | `github-board`, `capture` |
| `issue-lesen` | `mcp`, `gh` | `refinement`, `spec-writer` |
| `issue-body-schreiben` | `mcp`, `gh` | `github-board`, `refinement` |
| `issue-titel-schreiben` | `mcp`, `gh` | `github-board`, `refinement` |
| `issue-kommentieren` | `mcp`, `gh` | `github-board` (Träger für `## Lokal nachzuholen`) |
| `issue-verwerfen` (Close mit `not planned`) | `mcp`, `gh` | `github-board`, `refinement` |
| `pr-erstellen` | `mcp`, `gh` | **`ship-feature`** |
| `pr-body-schreiben` | `mcp`, `gh` | **`ship-feature`** |
| `pr-verknuepfung-lesen` (`closingIssuesReferences`, `baseRefName`) | `mcp`, `gh` | `github-board`, **`ship-feature`** |
| `copilot-review-anfordern` | `mcp`, `gh` | **`ship-feature`**, `CLAUDE.md` |
| `pr-reviewstand-lesen` | `mcp`, `gh` | **`ship-feature`** |
| `pr-reviewkommentare-lesen` | `mcp`, `gh` | **`ship-feature`** |
| `pr-reviewkommentar-beantworten` | `gh` (`mcp` nur, falls ein Werkzeug dafür vorliegt) | **`ship-feature`** |
| `board-aufnahme` | `gh` | `github-board`, `capture` |
| `board-status-setzen` | `gh` | `github-board`, `refinement`, `spec-writer`, `ship-feature` |
| `board-prioritaet-setzen` | `gh` | `github-board`, `refinement` |
| `board-status-und-prioritaet-lesen` | `gh` | `github-board`, `refinement`, `spec-writer` |

**Die vier Board-Operationen haben genau einen Weg**, und das ist keine Lücke im Katalog, sondern eine Eigenschaft der Welt: Projects (V2) spricht ausschließlich GraphQL, eine REST-Entsprechung existiert nicht, und die MCP-Werkzeuge bieten für Projects V2 keine Operation an. Siehe Abschnitt 5.

**Der `mcp`-Weg wird auf Operationsebene benannt, nicht auf Werkzeugnamen-Ebene.** Normativ ist „das GitHub-MCP-Werkzeug, das diese Operation ausführt"; der am 2026-09-06 beobachtete Werkzeugname steht als *Hinweis* daneben, nicht als Vorschrift. Grund: Der Werkzeugsatz ist nachweislich nicht stabil — er unterscheidet sich zwischen Hauptsession und Subagent derselben Session (Kontext) und liegt außerhalb des Repositories. Ein Katalog, der auf exakte Namen normiert, wäre bei der nächsten Server-Version falsch, und niemand im Ablauf merkte es, bevor eine Story daran hängt. Ein Ablauf, der die Operation kennt, findet das passende Werkzeug in seinem Kasten; ein Ablauf, der einen veralteten Namen sucht, findet nichts.

**Jeder Katalogeintrag trägt `owner` und `repo` als Literal — auf jedem Weg.** Auf dem `gh`-Weg ist `--repo TheRealKoller/photosort` schon heute Pflicht an schreibenden Verben und statisch geprüft, aber es gab dort einen stillen Rückhalt: `gh issue edit <NNN>` **ohne** `--repo` wirkt auf das Repository des Arbeitsverzeichnisses und fällt bei einem Fehler in der Repo-Angabe auf das richtige Repo zurück. Ein MCP-Werkzeug kennt kein Arbeitsverzeichnis; `owner` und `repo` sind dort Pflichtparameter **ohne Rückfallwert**. Der sichere Vorgabewert entfällt also mit dem Wegwechsel, und was bisher ein Gürtel neben den Hosenträgern war, wird zur einzigen Absicherung. Beide Werte stehen deshalb im Katalogtext jeder Operation als Literal, nicht als Platzhalter, und die statische Prüfung aus Abschnitt 8 erfasst beide Wege.

**Jede lesende Operation nennt ihre Feldmenge als Obergrenze der Auswertung — wegunabhängig.** Der Katalog schreibt zu `pr-verknuepfung-lesen` `closingIssuesReferences` und `baseRefName` fest, zu `pr-reviewstand-lesen` `reviewRequests` und `reviews`, zu `issue-lesen` `body`, `title`, `labels`, `state`, `author`. Ausgewertet wird ausschließlich, was dort steht; alles andere gilt als nicht gelesen, auch wenn es in der Antwort steht.

**Das ist an einer Stelle ein bewusst getragener Rückschritt, und der wird nicht schöngeredet.** `gh pr view --json closingIssuesReferences,baseRefName` verengt die Feldmenge **strukturell**: Titel, Body und Autor eines fremdbeschreibbaren Pull Requests entstehen im Agenten-Kontext gar nicht erst. Eine Auswertungsgrenze wirkt dagegen erst, wenn die Daten schon da sind — sie ist eine Regel über den Umgang mit Text, der bereits im Kontext liegt, und damit prinzipiell schwächer als eine Grenze, die den Text nie ankommen lässt. Mit `mcp` vor `gh` (Abschnitt 2 oben) trifft das `pr-verknuepfung-lesen` und `pr-reviewstand-lesen` im Regelbetrieb. Am 2026-09-06 von Daniel entschieden: keine Ausnahme von der Wegreihenfolge, die Auswertungsgrenze reicht. Getragen wird das Restrisiko von der Absicherung, die daneben *strukturell* wirkt und deshalb ausdrücklich Teil dieser Entscheidung ist:

**Der Katalog enthält keine Operation, die Issue-Kommentare liest.** Das ist keine Feldliste, sondern eine Eigenschaft des Vokabulars: Was es als Operation nicht gibt, kann kein Ablauf aufrufen, und weil andere Dateien ausschließlich über Operations-IDs auf GitHub zugreifen (Abschnitt 1), ist die Grenze statisch prüfbar statt appellativ. In der Sache ist sie strenger als die heutige Regel „lies ausschließlich `issue.body`, niemals Kommentare", die als Satz in `spec-writer` steht und beim nächsten Umbau übersehen werden kann. **Die eine Ausnahme:** `pr-reviewkommentare-lesen` holt die Copilot-Findings am **eigenen** Pull Request — der Zweck des Schritts, und ein Fund, der ohnehin am Code geprüft und nicht geglaubt wird.

**Bei einem mehrdeutigen Fehlschlag einer anlegenden Operation wird nicht blind der nächste Weg gegangen.** Betroffen sind `issue-anlegen`, `pr-erstellen` und `issue-kommentieren`: Reißt die Verbindung ab oder läuft eine Zeitüberschreitung, kann der Schreibzugriff angekommen sein. Der zweite Weg erzeugte dann ein **zweites öffentliches, nicht zurücknehmbares Artefakt** — ein doppeltes Issue, ein doppelter Pull Request. Diese drei Operationen verifizieren deshalb nach einem mehrdeutigen Fehlschlag zuerst **lesend**, ob das Artefakt existiert, und gehen den nächsten Weg nur, wenn es das nicht tut. Zwei Abgrenzungen, damit daraus keine allgemeine Vorsicht wird, die die Leiter lähmt: Ein **eindeutiger** Fehlschlag (HTTP 403, „Werkzeug existiert hier nicht", Validierungsfehler) ist nicht betroffen — dort ist nichts entstanden, der nächste Weg wird sofort versucht. Und für alle **zielzustands-idempotenten** Operationen (ADR [`0048`](./0048-board-operationen-zielzustands-idempotent.md), Prinzip fortgeführt in ADR 0057, Abschnitt 5.2) bleibt der zweite Versuch der Normalfall: `board-status-setzen` zweimal abzusetzen setzt einen Zustand und führt keinen Übergang aus.

**`pr-reviewkommentar-beantworten`** ist die eine Operation, für die zum Zeitpunkt dieser ADR nicht belegt ist, dass ein MCP-Werkzeug existiert (das Antworten in einem bestehenden Inline-Thread ist etwas anderes als das Erstellen eines Reviews). Sie wird deshalb mit `gh` als einzigem belegten Weg geführt und ausdrücklich als „`mcp` unbelegt" markiert — **nicht** mit einem erfundenen Werkzeugnamen aufgefüllt. Wer die Operation das nächste Mal in einer Session mit MCP-Werkzeugen ausführt und dabei ein passendes findet, ergänzt den Weg. Ein unbelegter Weg im Katalog wäre schlimmer als ein fehlender: Er scheiterte still und verschöbe die Diagnose.

### 3. Kein Urteil vor dem Versuch — und die Grenze, die ein Blick in den eigenen Werkzeugkasten nicht überschreitet

Mehrere Wege pro Operation eröffnen eine Versuchung, die es mit einem Weg nicht gab: erst zu ermitteln, „wo wir hier eigentlich sind", und dann den passenden Weg zu wählen. Genau das ist verboten. ADR 0052 (Abschnitt 2/3) und ADR 0056 (Abschnitt 1) bleiben tragend, und zwar in dieser Ausformung:

1. **Ein vorhandener Weg wird immer versucht, nie vorab beurteilt.** Kein Probe-Aufruf, kein `gh auth status`, kein „Rate-Limit abfragen, um zu sehen ob GitHub antwortet", keine Auswertung von Umgebungsvariablen, kein Schluss von irgendeinem Merkmal (Hostname, Pfad, Vorhandensein eines Verzeichnisses, gesetzte Tokens) auf eine „Session-Art". Es gibt im ganzen Ablauf keinen Begriff „Cloud-Session", von dem eine Entscheidung abhinge — es gibt nur Operationen, Wege und Ergebnisse.

2. **Ein Weg, dessen Werkzeug in dieser Session gar nicht existiert, ist kein Weg.** Er wird übersprungen, und aus dem Überspringen wird *kein* Schluss über die Umgebung gezogen. Das ist keine Messung, und der Unterschied ist nicht spitzfindig: Der Werkzeugkasten liegt dem Ablauf ohnehin offen vor, er muss nichts dafür ausprobieren, es entsteht kein Aufruf und keine Antwort von GitHub. Die Auskunft ist über die Umgebung außerdem nichtssagend — ein Subagent dieses Repositories hat die MCP-Werkzeuge auch lokal nicht (gemessen am 2026-09-06). Wer daraus auf „remote" schlösse, läge in der Hälfte der Fälle falsch; genau deshalb *darf* daraus nichts geschlossen werden.

3. **Kein Gedächtnis über Operationen hinweg.** Jede Operation beginnt oben an ihrer Leiter. Ein Weg, der bei der vorigen Operation gescheitert ist, wird bei der nächsten wieder versucht. Ein solches Gedächtnis wäre eine Vorabmessung mit einem Schritt Verzögerung — dieselbe Sache, nur schwerer zu erkennen. Der Preis (in einer Session, in der `gh` gesperrt ist, ein zusätzlicher scheiternder Aufruf je Operation) ist derselbe, den ADR 0057, Abschnitt 6 Punkt 1 bereits bewusst zahlt: „ihn zu versuchen kostet nicht mehr, als ihn zu messen, und ist ehrlicher".

4. **Scheitert ein Weg, wird der nächste versucht. Erst wenn alle Wege gescheitert sind, gilt die Operation als fehlgeschlagen.** Ein Wegwechsel ist kein Befund und wird nicht berichtet — er ist der Normalbetrieb der Leiter. **Die eine Ausnahme:** Bei einem *mehrdeutigen* Fehlschlag der drei anlegenden Operationen wird vor dem Wegwechsel lesend verifiziert, ob das Artefakt doch entstanden ist (Abschnitt 2, letzter Absatz vor `pr-reviewkommentar-beantworten`). Sie gilt eng und nur dort: Ein doppeltes Issue ist öffentlich und nicht zurücknehmbar, ein zweimal gesetzter Board-Status ist folgenlos.

5. **Die Meldung des zuletzt versuchten Wegs geht wörtlich in den Chat-Bericht.** Nicht die des ersten, nicht eine Zusammenfassung: die letzte, denn sie ist die, die das tatsächliche Hindernis beschreibt. In ein dauerhaftes GitHub-Artefakt geht sie nicht (Abschnitt 4.3).

### 4. Die Härtungsregeln, wegunabhängig — vier tragende Regeln statt einer Liste von Shell-Details

Die heutigen Regeln sind an der Kommandozeile formuliert, weil es nur sie gab. Bei einem MCP-Werkzeug gibt es keine Shell und damit keine Kommandozeilen-Injektion — das ist aber ein Argument dafür, die Regeln auf ihre tragende Aussage zurückzuführen, und keines dafür, sie entfallen zu lassen. Vier Regeln, jede zuerst wegunabhängig, dann je Weg konkretisiert:

**4.1 Freitext ist immer ein abgegrenzter Wert, nie Teil der Aufrufstruktur.**
Kein Text, den der Ablauf nicht selbst und vollständig erzeugt hat, wird durch Zeichenketten-Verkettung in einen Aufruf hineingeschrieben.
- Auf dem `gh`-Weg: Bodies **immer** über `--body-file`, Titel über `--title "$(cat <pfad>)"`; beide Dateien mit dem Schreib-Werkzeug angelegt, nie per Shell-Umleitung mit interpoliertem Inhalt. Die doppelten Anführungszeichen um `$(cat …)` bleiben tragend (ohne sie zerlegte die Shell den Inhalt an Leerzeichen und expandierte Globs). Unverändert wie heute.
- Auf dem `mcp`-Weg: Der Text geht als eigener, typisierter Parameter. Die Regel ist dort **strukturell erfüllt** — es gibt keine Struktur, in die er hineinlaufen könnte. Genau das ist festzuhalten, damit niemand die Regel für gegenstandslos hält: Sie gilt, sie ist nur bereits eingelöst.

> **„Strukturell erfüllt" gilt je Regel, nie je Weg.** Auf dem `mcp`-Weg ist **allein 4.1** strukturell erfüllt. Die Regeln 4.2, 4.3 und 4.4 sind dort **unverändert offen** und müssen dort genauso aktiv eingehalten werden wie auf dem `gh`-Weg — 4.2 sogar dringlicher, weil dort kein Metazeichen-Alarm mehr davor liegt (siehe unten). Der Katalog ordnet die Erfüllung deshalb je Regel und Operation zu und trifft **keine** Sammelaussage der Form „der MCP-Weg ist der sichere". Ein Weg pauschal für sicher zu erklären ist der kürzeste Weg, die drei offenen Regeln zu verlieren.

**4.2 Jeder Wert, der einen Aufruf *steuert*, ist geschlossen und selbst gebildet.**
Steuernde Werte sind: Issue- und PR-Nummern, die daraus gebildete URL, Repository und Owner, Feldnamen, Status- und Prioritätswerte, Labels, Close-Gründe. Sie stammen ausschließlich aus dem laufenden Ablauf, werden gegen ein Muster validiert (`^[0-9]+$` für Nummern, `^\d{4}$` für Spec-Nummern) oder stehen als Literal im Skill-Text. **Keine Zeichenkette aus einer Werkzeug-Antwort, einer `gh`-Ausgabe, einem Issue-Body oder einem Kommentar wird je Teil eines Aufrufs. Kein `eval`.**

Diese Regel ist die, die beim Wegwechsel am leichtesten verlorenginge, und die, deren Verlust am teuersten wäre. Sie schützt nämlich nicht in erster Linie vor Shell-Injektion, sondern vor **der Wahl des falschen Ziels**: Eine Issue-Nummer, die aus fremdem Text stammt, schickt einen Schreibzugriff an ein fremdes Issue — über ein MCP-Werkzeug genauso zuverlässig wie über eine Kommandozeile, nur ohne jeden Shell-Metazeichen-Alarm. Das Repository ist öffentlich; ein Fehlgriff ist nicht zurücknehmbar.

Die eine, eng gefasste Ausnahme bleibt und wird wegunabhängig gefasst: Aus der Antwort eines **Anlege**-Aufrufs (`issue-anlegen`, `pr-erstellen`) darf die **Nummer** übernommen werden, weil der Ablauf sie nirgends anders her bekommt — auf dem `gh`-Weg aus der ausgegebenen URL geparst, auf dem `mcp`-Weg aus dem strukturierten Zahlenfeld gelesen, in **beiden** Fällen gegen `^[0-9]+$` validiert und danach ausschließlich als Zahl weiterverwendet. Die URL wird auch dann aus der geprüften Zahl **gebildet**, nie übernommen. Freitext (Titel, Body, Fehlermeldungen) fällt nie unter diese Ausnahme.

**4.3 In ein dauerhaftes GitHub-Artefakt gelangt ausschließlich selbst erzeugter Inhalt.**
Unverändert und schon heute wegunabhängig. Fehlermeldungen, fremde Ausgaben, Zitate aus Issue-Bodys oder Kommentaren gehen in den Chat-Bericht, den ein Mensch liest — nie in einen Issue-Kommentar oder einen PR-Body.

**4.4 Ein Titel wird auf Wohlgeformtheit geprüft — das ist eine Eigenschaft des Werts, keine der Shell.**
Genau eine nicht leere Zeile, kein führendes oder nachgestelltes Leerzeichen, keine Steuerzeichen, keine Bidi-Overrides (U+202A–U+202E, U+2066–U+2069), keine Zero-Width-Zeichen (U+200B–U+200D, U+FEFF), kein U+0085/U+2028/U+2029. Ein Titel ist öffentlich, erscheint in Benachrichtigungen und in der Suche und wird überflogen, nicht gelesen — das gilt unabhängig davon, wie er dorthin kam.
- Auf dem `gh`-Weg: geprüft an der Titel-Datei, unmittelbar vor dem Aufruf geschrieben und vor dem Absetzen gelesen. Der zusätzliche gh-eigene Grund bleibt bestehen: Ein falscher Pfad liefert eine **leere** Substitution, aus einem Tippfehler würde `--title ""` statt eines lauten Fehlschlags.
- Auf dem `mcp`-Weg: **ebenfalls über eine Titel-Datei.** Der Titel wird auch dort mit dem Schreib-Werkzeug materialisiert, an der Datei geprüft und erst danach als Parameter übergeben.

  Das ist eine Korrektur an einer früheren Fassung dieser ADR, die „dieselben Kriterien, ohne den Datei-Umweg" vorsah, weil „die Datei nie der Zweck war". Für den **Transport** stimmt das — für die **Prüfung** nicht. Bidi-Overrides und Zero-Width-Zeichen sind genau die Klasse von Zeichen, die im eigenen Kontext unsichtbar ist: Ein Modell, das eine Zeichenkette „ansieht", sieht ein U+202E nicht, und ein Titel, der rückwärts läuft oder unsichtbare Zeichen trägt, ginge unbemerkt durch. Die Datei ist das einzige Substrat, an dem die Kriterien aus 4.4 **mechanisch** ausführbar sind statt nur behauptet. Der Preis ist ein Dateischreibvorgang, den der Transport nicht bräuchte — verglichen mit einer Prüfung, die in der einzigen Kategorie versagt, für die sie geschrieben wurde, ist das billig.

**4.5 Auf jedem Weg das benannte, typisierte Mittel — nie eine selbst zusammengesetzte Anfrage.**
Das ist die wegunabhängige Fassung der Regel aus ADR 0017 („native `gh`-Subcommands statt roher GraphQL-Aufrufe"). Sie war nie eine Aussage über `gh`; sie ist eine Aussage über die Form: kleine, stabile Angriffsfläche, keine handgeschriebene Query, kein selbst gebauter Request-Körper.
- Auf dem `gh`-Weg unverändert: ein Subcommand, wo es einen gibt. Die eine begründete Ausnahme bleibt bestehen — `gh api graphql` für `board-status-und-prioritaet-lesen`, weil `gh project item-list` die gesamte Item-Liste lädt und genau daraus schon einmal einen Fehler erzeugt hat (Spec 0302). Query als Literal in einfachen Anführungszeichen, Nummer ausschließlich als typisierte Variable `-F number=<NNN>`.
- Ein MCP-Werkzeug ist **kein roher API-Aufruf**, sondern ein benannter, typisierter Aufruf ohne selbst geschriebene Query — es erfüllt die Eigenschaft, um derentwillen die Regel Subcommands bevorzugt. Es ist deshalb nach dieser Regel zulässig, und ADR 0017 muss dafür nicht abgelöst, sondern nur richtig gelesen werden. **Nicht** zulässig bleibt, was die Regel schon immer ausgeschlossen hat: ein generisches „schick diesen Request an diese URL"-Werkzeug für eine Operation, für die ein benanntes existiert.

### 5. Was remote auf keinem Weg trägt, bleibt ehrlich benannt

`github-access` benennt ausdrücklich, was in einer Cloud-Session über **keinen** Weg erreichbar ist: `board-status-setzen`, `board-prioritaet-setzen`, `board-status-und-prioritaet-lesen`, `board-aufnahme`. Nicht als offene Aufgabe, nicht als bekannter Mangel, sondern als **Eigenschaft der Umgebung**, mit der nachgewiesenen Ursache: Projects (V2) spricht ausschließlich GraphQL; die Zwischenschicht der Session bedient GraphQL nur für einen fest verdrahteten Satz von PR-Operationen; eine REST-Entsprechung existiert nicht; die MCP-Werkzeuge bieten dafür keine Operation an. Vier gemessene Sackgassen, kein fünfter Weg in Sicht.

Daraus folgt:

- **`## Lokal nachzuholen` bleibt unverändert** in Form, Wortlaut und Regeln — einschließlich des festen Satzes, der Regel „nur selbst erzeugter Inhalt in dauerhafte Artefakte" (4.3) und der Vorgabe, dass die Nummern im Wiederholbefehl ausschließlich aus dem laufenden Ablauf stammen. Der Abschnitt wird aber als **Normalfall einer Cloud-Session** beschrieben statt als Ausnahme. Das ist kein Wortspiel: Ein als Ausnahme gerahmter Bericht lädt dazu ein, ihn als Fehler zu behandeln und nach einer Behebung zu suchen, die es nicht gibt.
- **Der Wiederholbefehl bleibt die `gh`-Form**, auch wenn der Regelweg einer Operation `mcp` ist. Er ist für einen Menschen an einem Terminal gedacht, und bei den vier betroffenen Operationen ist `gh` ohnehin der einzige Weg.
- **Kein Abbruch** wegen einer gescheiterten Board-Operation. Die eigentliche Arbeit ist wichtiger als ihr Etikett.
- **Keine Zustandsdatei, kein Nachhol-Automatismus, kein Ersatzträger.** Die Board-Operationen werden **nicht** über Labels, Kommentare oder ein anderes Feld nachgebaut. Ein solcher Ersatz erzeugte einen zweiten Wahrheitsort für den Story-Status — genau das, was der native Lebenszyklus aus ADR 0057 abgeschafft hat.
- **Der strukturelle Schutz aus ADR 0057, Abschnitt 6 Punkt 3 bleibt tragend:** Beide Session-Schreibzugriffe stehen vor der Arbeit, die sie ankündigen. Ein Fehlschlag lässt die Story auf dem früheren, konservativeren Wert stehen, nie auf einem weiter fortgeschrittenen.

**Was sich gegenüber ADR 0057, Abschnitt 7 ändert:** Dort blieben remote `Ready`, `In Progress` und die Board-Aufnahme offen — und stillschweigend auch sämtliche Issue-Schritte, weil sie an `gh` hingen. Mit der Leiter tragen alle Issue- und alle Pull-Request-Operationen remote. Übrig bleiben genau die vier Board-Operationen. Eine Story kommt in einer Cloud-Session damit von der Erfassung bis zum eröffneten, verknüpften, von Copilot reviewten Pull Request — und danach auf `Review` und `Done`, weil diese beiden Übergänge auf GitHubs Servern entstehen (ADR 0057, Abschnitt 2, unverändert). Nachzuholen bleiben zwei Etiketten und eine Board-Aufnahme.

**Woran auffällt, dass dieser Abschnitt überholt ist:** `board-status-setzen` läuft in einer Cloud-Session durch, statt zu scheitern — oder ein MCP-Werkzeug für Projects V2 taucht auf. Trifft eines von beidem zu, ist allein noch dieser Abschnitt nachzuziehen.

### 6. Jede Stelle sagt, was sie darf: drei Stufen, an jeder Datei ausgesprochen

Es gibt genau drei Erlaubnisstufen, und jede Skill- und Agenten-Datei, die GitHub berührt oder plausibel berühren könnte, spricht ihre Stufe aus:

| Stufe | Bedeutung | Wer |
|---|---|---|
| **lesend und schreibend** | darf jede Operation des Katalogs | `capture`, `refinement`, `spec-writer`, `ship-feature`, `github-access` |
| **nur lesend** | darf ausschließlich lesende Operationen | `review` (der Orchestrator) |
| **kein GitHub-Zugriff** | weder lesend noch schreibend | die fünf Perspektiven-Skills `review-tests`, `review-requirements`, `review-security`, `review-architecture`, `review-ux`; alle sieben Agenten-Dateien unter `.claude/agents/`; `browse-app`, `design-system`, `skiller` |

**Warum die fünf Perspektiven-Skills „kein GitHub-Zugriff" bekommen und nicht „nur lesend":** Sie führen heute keinen einzigen GitHub-Zugriff aus — außerhalb ihres Schreibverbot-Absatzes steht in keiner der fünf Dateien eine `gh`-Zeile. Ihr Gegenstand ist ein lokaler Diff gegen `main`, den sie mit lokalem `git` gewinnen. „Nur lesend" räumte ihnen ein Recht ein, das keine von ihnen braucht, und ein nicht gebrauchtes Recht ist eine Angriffsfläche ohne Gegenwert — insbesondere hier, wo Lesen bedeutet, fremdbeschreibbaren Text in einen Kontext zu holen, der anschließend Fix-Aufträge formuliert. Der `review`-Orchestrator behält „nur lesend", weil für ihn ein Ad-hoc-Lauf gegen einen Pull Request vorgesehen bleibt.

Drei Festlegungen dazu:

- **Das Schreibverbot der Review-Skills wird wegunabhängig formuliert.** Heute steht dort eine Aufzählung von `gh`-Befehlsnamen (`gh pr create`, `gh pr edit`, `gh pr merge`, `gh api` mit `-X POST/PATCH/PUT/DELETE`). Diese Form verbietet, was sie benennt — und erlaubt damit versehentlich jedes MCP-Schreibwerkzeug, das es bei ihrer Formulierung noch nicht gab. Ab jetzt: **kein schreibender GitHub-Zugriff, gleich über welchen Weg.** Lesende Zugriffe bleiben erlaubt, ebenso lokales lesendes `git`. Die Aufzählung entfällt ersatzlos; sie war nie die Regel, sondern ihre unvollständige Illustration.
- **Subagenten haben keinen GitHub-Zugriff. Die tragende Kontrolle dafür ist und bleibt die Konvention in den Agenten-Dateien** (ADR 0037, Abschnitt 3; ADR 0057, Begründung), ab jetzt in jeder der sieben Dateien ausgesprochen. Daneben steht ein **beobachteter, nicht zugesicherter** Umgebungsbefund: Am 2026-09-06 enthielt der MCP-Werkzeugsatz eines Subagenten dieses Repositories die GitHub-Werkzeuge nicht („Its MCP server 'github' is connected but does not offer this tool here"). Das ist Client-Konfiguration — es gibt keine `.mcp.json` im Repository, das Projekt kann diesen Zustand weder herstellen noch prüfen noch seine Änderung bemerken. Er zählt deshalb als Verteidigung in der Tiefe und **nicht** als Zusicherung: Fällt er weg, ändert sich an der Erlaubnisstufe nichts, weil sie nie auf ihm beruhte. Eine frühere Fassung dieser ADR sprach hier von „strukturell abgesichert" — das war zu stark und ist hiermit korrigiert.
- **Für `research-engineer` wird die Grenze ausdrücklich gezogen:** Externe Recherche auf öffentlichen Webseiten — auch solchen auf github.com — ist kein GitHub-Zugriff im Sinne dieser ADR. Gemeint sind Issues, Board und Pull Requests **dieses** Repositories im Rahmen des Entwicklungsablaufs.
- **Die Erlaubnisstufen sind Text plus statischer Test, nicht technisch durchgesetzt — das ist eine bekannte Lücke.** Ein Skill, der entgegen seiner Stufe eine Operation aufriefe, würde vom Test aus Abschnitt 8 an der *Datei* gefasst, nicht am *Aufruf*: Die Prüfung liest Dateien, sie steht nicht zwischen Agent und Werkzeug. Am 2026-09-06 von Daniel entschieden, dass das für Story #339 reicht. Eine technische Schranke über Berechtigungsregeln in einer `.claude/settings.json` wird als **eigene Folge-Story** aufgenommen und ist ausdrücklich nicht Teil dieser ADR. Festgehalten wird die Lücke hier, damit sie nicht durch die Existenz der Tabelle als geschlossen erscheint.
- **`CLAUDE.md` nennt keinen Befehl mehr.** Die Konvention „nach dem Eröffnen wird ein Copilot-Review angefordert" bleibt wortgleich in Kraft; nur die Befehlszeile `gh pr edit <PR> --add-reviewer "@copilot"` weicht dem Operationsnamen `copilot-review-anfordern`. Eine Verfassung legt die Regel fest, nicht das Mittel.

### 7. Wie ADR 0057 abgelöst wird: ein benannter Teil, nicht das Ganze

ADR 0057 ist einen Tag alt und trägt neun Abschnitte, von denen acht unverändert gültig sind — der fünfwertige Lebenszyklus, die Auslöser-Tabelle, `Done` heißt „vom Board", der Ersatz der vier Werkzeug-Prüfungen, das Fehlschlag-Muster, der PR-ohne-Merge-Rückfall. Diese ADR ändert genau zwei Dinge daran: **welche Gestalt ein Zugriff hat** (Abschnitt 4, erster Satz) und **wie weit die Remote-Grenze reicht** (Abschnitt 7).

`specs/README.md` kennt bisher nur die grobe Form: „eine spätere Änderung der Entscheidung erzeugt eine neue ADR, die die alte als *Superseded* markiert". Diese ADR nimmt eine feinere: ADR 0057 behält den Status `Accepted` und bekommt in ihrem Kopf einen Vermerk „**Teilweise abgelöst:** Abschnitt 4 (erster Satz) und Abschnitt 7 durch ADR 0059". Begründung:

- Ein `Superseded` auf ADR 0057 wäre **sachlich falsch**. Es sagte, die Entscheidung sei abgelöst — abgelöst ist ein Nebenaspekt. Wer künftig fragt „warum schreibt GitHub drei der fünf Übergänge selbst?", würde von einem `Superseded`-Etikett auf eine falsche Fährte geschickt.
- Die Alternative, ADR 0059 den kompletten Lebenszyklus wiederholen zu lassen, damit `Superseded` ehrlich wird, erzeugte ein zweites Abbild derselben Entscheidung. Zwei Abbilder driften.
- Der Präzedenzfall spricht nicht dagegen: ADR 0017 und ADR 0052 tragen bereits Statuszeilen, die pro Abschnitt aufschlüsseln, was überlebt und was fällt. Der einzige Unterschied hier ist, dass die Mehrheit überlebt statt der Minderheit — das ändert die Genauigkeit der Aussage, nicht das Verfahren.

Das Bearbeiten des ADR-Kopfes ist dabei kein Bruch der Unveränderlichkeit: Die Statuszeile *ist* der dafür vorgesehene Mechanismus, sie wird bei jeder Ablösung angefasst. Der Entscheidungstext von ADR 0057 bleibt unangetastet.

**Der Preis ist benannt und bewusst hingenommen:** Damit gibt es neben `Superseded` eine zweite, feinere Abstufung, die `specs/README.md` bisher nicht kannte — und wer künftig den Status einer ADR liest, muss zusätzlich auf einen Teil-Vermerk achten, statt sich auf ein einziges Wort verlassen zu können. Die Gegenoption (ADR 0057 vollständig `Superseded`, diese ADR übernimmt die acht weitergeltenden Abschnitte wortgetreu) wäre konventionstreu gewesen, hätte aber ein zweites Abbild desselben Lebenszyklus erzeugt, das driften kann, und ein Etikett vergeben, das eine gültige Entscheidung als abgelöst ausweist. Am 2026-09-06 abgewogen und von Daniel zugunsten des Teil-Vermerks entschieden. Damit die nächste ADR die Abstufung nicht neu erfinden oder erraten muss, wird sie in `specs/README.md` festgehalten (siehe Konsequenzen) — eine Abstufung, die nur in einer einzelnen ADR steht, ist keine Konvention, sondern ein Einzelfall.

### 8. Statisch abgesichert, nicht nur behauptet

„Genau ein Ort" ist eine Eigenschaft, die bei jeder künftigen Änderung stillschweigend verletzt werden kann — dieselbe Klasse Fehler, gegen die `scripts/tests/test_board_referenzfreiheit.py` bereits schützt. Sie wird deshalb geprüft:

- **Neu:** Keine Datei unter `.claude/**` außer `.claude/skills/github-access/SKILL.md` und keine Zeile in `CLAUDE.md` enthält einen GitHub-Aufruf — weder eine `gh issue`/`gh pr`/`gh project`/`gh api`-Befehlszeile noch einen `mcp__github__`-Werkzeugnamen. Mit demselben Selbstschutz wie der bestehende Test (Mindestzahl gelesener Dateien, Gegenprobe an einer Datei, in der das Muster zutreffen *muss*), damit eine kaputte Dateiaufzählung nicht als grüner Test durchgeht. Nicht im Suchraum: `docs/` (dort stehen legitime Setup-Befehle wie `gh auth login` und die dokumentierte Messung), `specs/` und `CHANGELOG.md` (historisch korrekt), `.github/workflows/` (siehe Abschnitt 1).
- **Neu:** Kein Verweis auf den alten Skill-Namen `github-board` in einer verwalteten Datei — dieselbe Mechanik und dieselben drei Ausnahmen wie beim bestehenden `gh-board`-Muster, an das es sich anlehnt.
- **Neu:** Der Katalog enthält **keine** Operation, die Issue-Kommentare liest (Abschnitt 2). Geprüft am Vokabular: Keine Operations-ID und keine Feldmenge im Katalog nennt Issue-Kommentare; einzige zulässige Fundstelle ist `pr-reviewkommentare-lesen`. Das ersetzt den heutigen Prosa-Satz „lies ausschließlich `issue.body`, niemals Kommentare" in `spec-writer` durch eine Eigenschaft, die beim nächsten Umbau nicht übersehen werden kann.
- **Neu:** Jede Operation nennt `owner` und `repo` als Literal, auf **beiden** Wegen (Abschnitt 2) — der `gh`-Weg verliert mit dem MCP-Weg seinen stillen Rückfallwert aus dem Arbeitsverzeichnis. Die bestehende `--repo`-Prüfung an schreibenden `gh`-Verben wird entsprechend auf die Katalogeinträge des `mcp`-Wegs ausgedehnt.
- **Erhalten:** Die Formprüfungen der `gh`-Befehle (`--repo` an schreibenden Verben, `--body-file` statt `--body`, `--title "$(cat …)"`, gültige Feld-/Wertepaare am Board, Projektnummer und Owner). Ihr Suchraum bleibt `.claude/**` — er soll gerade auch dann greifen, wenn ein Befehl versehentlich wieder außerhalb auftaucht.
- **Neu verankert:** Die Reihenfolge Body → Titel → `Ready` in `refinement` (heute über Zeilennummern von Befehlen geprüft) wird über die **Operations-IDs** geprüft. Die Reihenfolge ist eine Eigenschaft des Ablaufs, nicht der Befehlsform; sie gehört damit ohnehin dorthin und überlebt den Umbau als Aussage statt als Zeilennummer-Zufall.

## Begründung

- **Warum ein Ort und nicht „mehrere Wege dort, wo es weh tut":** Der punktuelle Fix (in `capture` zusätzlich einen MCP-Aufruf nennen) wäre in einer Stunde erledigt und in einem Monat wieder auseinandergelaufen. Die Kosten dieser Story liegen nicht in der Leiter, sondern in der Verstreuung, die sie vervielfachen würde: Sechzehn Operationen an sechs Stellen, jede mit zwei Wegen, ergäben zweiunddreißig Stellen, an denen eine Regel richtig oder falsch stehen kann. An einem Ort sind es sechzehn Einträge und eine Regel.
- **Warum die Umbenennung Teil der Story ist und nicht Kosmetik:** Der Name `github-board` hat den Zuschnitt gemacht. Er ist der nachweisbare Grund, warum die Pull-Request-Operationen bis heute außerhalb liegen — ein Skill, den man für das Board lädt, nimmt keinen `gh pr create` auf. Wer die Sammlung erweitert, ohne den Namen zu ändern, hat die Ursache stehen lassen und darf sich über die nächste Auswanderung nicht wundern.
- **Warum die Leiter fest und nicht adaptiv ist:** Eine adaptive Reihenfolge („merk dir, was hier funktioniert hat") wäre effizienter und wäre genau die Session-Erkennung, die ADR 0056 verworfen hat — nur unter anderem Namen und schwerer zu erkennen, weil sie sich als Optimierung tarnt. Der Preis der festen Reihenfolge ist ein scheiternder Aufruf pro Operation in einer Session, in der der erste Weg nicht trägt. Das ist billig und ehrlich.
- **Warum der Werkzeugkasten-Blick trotzdem erlaubt ist:** Der Unterschied zu einer Messung liegt nicht in der Absicht, sondern im Gegenstand. Eine Messung fragt GitHub etwas und schließt aus der Antwort auf die Welt; der Werkzeugkasten-Blick schaut auf die eigene Hand. Er erzeugt keinen Aufruf, verbraucht kein Rate-Limit, kann nicht falsch antworten und lässt — das ist der entscheidende Teil — **keinen** Schluss auf die Umgebung zu, weil derselbe Befund lokal und remote auftritt. Die Abgrenzung ist deshalb in Abschnitt 3 nicht als Vertrauenssache formuliert, sondern über das Verbot jedes daraus gezogenen Schlusses.
- **Warum die Härtungsregeln auf vier reduziert und nicht bloß dupliziert werden:** Zwei parallele Regellisten („so bei `gh`, so bei MCP") wären zwei Orte, an denen eine Regel fehlen kann. Vier tragende Regeln mit je einer Konkretisierung pro Weg haben einen Ort, an dem die Regel steht, und einen, an dem ihre Ausführung steht. Kommt ein dritter Weg, ist die Regel schon da.
- **Warum ausdrücklich festgehalten wird, dass 4.1 bei MCP „strukturell erfüllt" ist statt „nicht anwendbar":** Weil „nicht anwendbar" die erste Stufe ist, auf der eine Sicherheitsregel verschwindet. Eine erfüllte Regel bleibt lesbar und prüfbar; eine nicht anwendbare wird beim nächsten Umbau gestrichen.
- **Warum die Board-Grenze benannt und nicht umgangen wird:** Ein Ersatzträger (Status als Label, Priorität als Kommentar) wäre in einem Nachmittag gebaut und erzeugte einen zweiten Wahrheitsort für den Story-Status, den GitHubs native Workflows nicht kennen und nicht bedienen. ADR 0057 hat den einen Wahrheitsort gerade erst hergestellt. Zwei Etiketten von Hand nachzuziehen ist der billigere Preis.
- **Warum die MCP-Werkzeuge auf Operationsebene und nicht auf Namensebene normiert werden:** Der Werkzeugsatz ist nachweislich instabil (verschieden zwischen Hauptsession und Subagent, außerhalb des Repositories konfiguriert). Ein Katalog mit exakten Namen wäre eine Kopie fremden Zustands im eigenen Repository — dieselbe Bauart wie die vier Knoten-IDs, die ADR 0057, Abschnitt 4 ausdrücklich abgeschafft hat, und dieselbe Bauart wie die `STATUS_VALUES`-Konstante, die vom Board abdriften konnte.
- **Warum die eine unbelegte Operation als unbelegt markiert und nicht geraten wird:** Ein erfundener Werkzeugname im Katalog scheitert leise und an der falschen Stelle. Ein ausgewiesen fehlender Weg scheitert an der richtigen und sagt dem nächsten Leser, was zu tun ist.

## Konsequenzen

- **`.claude/skills/github-board/` → `.claude/skills/github-access/`** (Verzeichnis, Frontmatter-`name`, Beschreibung). Inhalt: Operationskatalog mit stabilen IDs und Wegleiter je Operation (Abschnitt 2), die vier Härtungsregeln wegunabhängig (Abschnitt 4), die Erlaubnisstufen (Abschnitt 6), die Lebenszyklus-Tabelle unverändert, `## Lokal nachzuholen` wörtlich unverändert und als Normalfall gerahmt (Abschnitt 5). Neu darin beheimatet: die sechs Pull-Request-Operationen aus `ship-feature` — **und die Berichtsvorlagen unter `## Lokal nachzuholen`**, die heute in vier Ablauf-Skills je eine `gh`-Befehlszeile tragen.
- **`.claude/skills/ship-feature/SKILL.md`:** verliert jede Befehlszeile; die Ablauf-Logik (Reihenfolge, Bedingungen, Auswertung, Wartezeit vor dem zweiten Board-Lesen, Skip-Regel des Copilot-Reviews, Finalisierung) bleibt vollständig erhalten und verweist auf Operations-IDs.
