## Kontext

Daniel ist die Qualität der lokalen Kategorie-Klassifizierung (PEOPLE/LANDSCAPE/DETAIL, ADR 0015: mediapipe-Gesichtserkennung + Pillow-Unschärfe-Heuristik) zu ungenau. Eine Remote-Klassifizierung durch ein Cloud-Vision-Modell (Anthropic/Mistral, analog zum bereits produktiven `landmark`-Kriterium, ADR 0025/0031) soll ergänzend — nicht ersetzend — verfügbar sein, mit Kostenschätzung vor dem Lauf, eigenem expliziten Trigger, und der Möglichkeit, eine Remote-Erkennung für ein einzelnes Foto manuell zu übernehmen, sofort wirksam (Umsortierung in eine neue Cluster×Kategorie-Partition, neu berechnetes Ranking dort), nicht erst beim nächsten vollen `score-criteria`-Lauf.

**Bindende Kurskorrektur (Klärungsgespräch mit Daniel, 2026-08-23), die diese Fassung von der ursprünglichen Aufgabenstellung abhebt:** Das Remote-Modell soll **nicht** gegen ein festes 3-Werte-Enum klassifizieren. Es liefert pro Foto **1-3 strukturierte, aber frei formulierte Schlagworte** (kein fixes Vokabular) — z.B. "Geburtstag", "Strand", "Hund". Kategorien sollen sich aus diesen Ergebnissen **ergeben**, nicht vorher feststehen — die offenen Remote-Labels werden in das bestehende, bereits produktive zweistufige Verfahren (`criteria.py::derive_active_categories`/`derive_category_key`, ADR 0023) integriert: sie werden an der bestehenden 15%-Häufigkeits-Schwelle (`CATEGORY_ACTIVE_THRESHOLD_FRACTION`) gemessen UND nehmen an der Pro-Foto-Gewinner-Auswahl (höchster normierter Score gewinnt) **gemeinsam** mit den lokal registrierten Kriterien teil — eine einzige, vereinheitlichte Auswahl statt zwei getrennter Systeme nebeneinander. Lokale Detektoren (Gesichtserkennung, Landschafts-Heuristik, Tier-/Gebäude-ML) bleiben dabei technisch unverändert — sie liefern weiter ihre heutigen festen `criterion_key`-Werte mit numerischem Score, werden nicht selbst auf offene Labels umgebaut.

Wichtige begriffliche Klarstellung gegenüber der Aufgabenstellung: `PhotoScore.category` existiert seit ADR 0021 (Spec 0037) nicht mehr — die "lokale Kategorie" eines Fotos lebt heute als `PhotoRanking.category_key`, abgeleitet über `criteria.py::derive_category_key` aus den `PhotoCriterionScore`-Werten des jeweils letzten `CriterionScoringRun`. Diese ADR knüpft an dieses aktuelle Datenmodell an.

Eine offene Schlagwort-Menge braucht eine **Zusammenfassung nahezu gleichbedeutender Label** ("Hund"/"Hunde"/"hund", ggf. sprachübergreifend "dog"), sonst verwässert jede Umschreibung dieselbe inhaltliche Kategorie in viele, einzeln unter der 15%-Schwelle bleibende Einzel-Label, die alle im Catch-all `"detail"` verschwinden — das widerspräche dem eigentlichen Ziel der Idee. Reine Kleinschreibung+Trim reicht dafür laut Daniel explizit nicht aus; eine spürbare Ähnlichkeits-Zusammenfassung ist gefordert. Das macht diese ADR zusätzlich zur bereits architekturrelevanten Datenmodell-Grundstruktur auch in einer zweiten Dimension architekturrelevant: einer neuen externen Abhängigkeit (lokales Text-Embedding-Modell).

## Entscheidung

### 1. Offene Remote-Schlagworte statt festem Enum — Integration in `derive_active_categories`/`derive_category_key` per zur-Laufzeit-entdeckten Pseudo-Kriterien-Keys

Das Vision-LLM liefert pro Foto ein JSON-Array von 1 bis 3 `{"label": "<kurzes Schlagwort>", "confidence": <0-1>}`-Objekten (Prompt fordert deutsche Schlagworte, akzeptiert aber jede vom Modell gelieferte Sprache — die Ähnlichkeits-Zusammenfassung in Punkt 4 fängt sprachliche Varianz strukturell auf, statt sie im Prompt zu erzwingen). Jedes Label wird über eine kanonische Label-Registry (Punkt 2/4) auf einen `canonical_key` (z.B. `"hund"`) abgebildet und als `photo_category_detections`-Zeile persistiert (Punkt 2) — bis hierhin rein informativ, wie in der vorherigen Fassung.

**Neu, zentraler Architektur-Umbau:** `worker.py::run_criterion_scoring` liest — bevor es `derive_active_categories`/`derive_category_key` aufruft — die für die aktuelle Kandidatenmenge bereits vorhandenen `photo_category_detections`-Zeilen (aus einem **früheren, separaten** `classify-categories-remote`-Lauf; **kein** neuer Cloud-Aufruf an dieser Stelle) und merged sie als zusätzliche, pseudokriterien-artige Einträge in dieselbe `candidate_values: dict[photo_id, dict[str, float]]`-Struktur, die ohnehin bereits für alle lokalen Kriterien geführt wird — unter dem Schlüssel `f"remote:{canonical_key}"`, Wert = `confidence` (Maximum, falls ein Foto mehrfach auf denselben `canonical_key` gemappt wurde, siehe Punkt 4). `derive_active_categories`/`derive_category_key` (`criteria.py`) bekommen dafür einen neuen, optionalen dritten Parameter `dynamic_keys: frozenset[str] = frozenset()` — die Menge der in diesem Lauf tatsächlich vorkommenden `remote:*`-Pseudo-Keys:

```python
DYNAMIC_LABEL_PRESENCE_THRESHOLD = 0.01  # ADR 0032: gleiche Konstanten-Klasse wie
# _TIER_CATEGORY_PRESENCE_THRESHOLD/_GEBAEUDE_CATEGORY_PRESENCE_THRESHOLD - ein vom Vision-LLM
# gelieferter Wert ist bereits eine "erkannt"-Aussage, dieser Schwellwert trennt nur "vorhanden"
# von "fehlender Eintrag" (candidate_values.get(key, 0.0)), keine zweite Konfidenzkalibrierung.

def derive_active_categories(
    candidate_values: dict[int, dict[str, float]],
    threshold_fraction: float = CATEGORY_ACTIVE_THRESHOLD_FRACTION,
    dynamic_keys: frozenset[str] = frozenset(),
) -> frozenset[str]:
    ...  # bestehende Schleife über CRITERIA_REGISTRY unveraendert, danach zusaetzlich:
    for key in dynamic_keys:
        present_count = sum(
            1 for values in candidate_values.values()
            if values.get(key, 0.0) >= DYNAMIC_LABEL_PRESENCE_THRESHOLD
        )
        if (present_count / total) >= threshold_fraction:
            active.add(key)
    return frozenset(active)


def derive_category_key(
    criterion_values: dict[str, float],
    active_criteria: frozenset[str],
    dynamic_keys: frozenset[str] = frozenset(),
) -> str:
    qualifying: list[str] = []
    for key in active_criteria:
        if key in dynamic_keys:
            threshold = DYNAMIC_LABEL_PRESENCE_THRESHOLD
        else:
            definition = CRITERIA_REGISTRY.get(key)
            if definition is None or definition.category_presence_threshold is None:
                continue
            threshold = definition.category_presence_threshold
        if criterion_values.get(key, 0.0) >= threshold:
            qualifying.append(key)
    if not qualifying:
        return CATEGORY_DETAIL
    winner = min(qualifying, key=lambda key: (-criterion_values.get(key, 0.0), key))
    return winner.removeprefix("remote:") if winner.startswith("remote:") else winner.removeprefix("content_")
```

**Warum kein neuer Typ (`DynamicCategoryCandidate` o.ä.) nötig ist:** Ein früherer Entwurf dieser ADR sah eine eigene Dataclass für zur-Laufzeit-entdeckte Kandidaten vor. Bei genauerem Hinsehen reicht ein einfaches `frozenset[str]` der Pseudo-Keys — der `canonical_key` steckt bereits vollständig im Pseudo-Key selbst (`f"remote:{canonical_key}"`), `removeprefix("remote:")` liefert ihn symmetrisch zum bestehenden `removeprefix("content_")`-Muster (ADR 0023 Punkt 4) zurück. Keine zweite Mapping-Struktur, kein zusätzlicher Typ — dieselbe Sparsamkeit, die ADR 0023 bereits für die Registry-Kriterien etabliert hat.

**Warum das rechtfertigt ist, obwohl es die alte ADR-Aussage "rein informativ, keine automatische Wirkung auf `derive_category_key`/`derive_active_categories`" umkehrt:** Genau das ist die bindend geänderte Produktanforderung — "Kategorien entstehen aus den Ergebnissen" heißt jetzt ausdrücklich: sobald ein `classify-categories-remote`-Lauf für einen Teil der Kandidaten Ergebnisse geliefert hat, fließen diese beim NÄCHSTEN `score-criteria`-Lauf automatisch in die Kategorie-Bildung ein — genau wie jedes andere `category_eligible`-Kriterium. Das manuelle Override (Punkt 6, unverändert vom Grundprinzip her bestehend) bleibt trotzdem sinnvoll: es korrigiert die automatische Zuordnung für ein *einzelnes* Foto sofort, ohne auf den nächsten vollen Lauf zu warten.

**Bewusst nicht gelöst, dokumentierte Lücke:** Ein Remote-Label wird nicht gegen die *semantische Bedeutung* bestehender lokaler Kategorie-Keys abgeglichen (z.B. Remote-Label "Menschen" clustert nicht automatisch mit dem lokalen `category_key="people"` zusammen) — die Ähnlichkeits-Zusammenfassung (Punkt 4) clustert Remote-Labels nur *untereinander*, nicht gegen die Registry. Ein Foto kann dadurch theoretisch sowohl lokal als `"people"` als auch remote als eigene Kategorie `"menschen"` geführt werden. Für die Kandidatenmenge dieses Projekts (Deutsch als durchgängige App-Sprache, Registry-Keys sind technische, nicht notwendig deutsche Strings) als seltener Grenzfall akzeptiert, keine Lösung Teil dieser Spec — ein späterer Wunsch, Remote-Labels gezielt auf bestehende Registry-Kategorien zu mappen, wäre eine eigene, neue ADR.

### 2. Datenmodell

- **Migration a) — Umbenennung statt neuer Schalter:** `Project.cloud_landmark_detection_enabled`/`.cloud_landmark_consent_at` → `Project.cloud_vision_detection_enabled`/`.cloud_vision_consent_at` (reines `ALTER TABLE ... RENAME COLUMN`, keine Wertänderung), Endpunkt `PUT /projects/{id}/cloud-landmark-consent` → `PUT /projects/{id}/cloud-vision-consent`. Unverändert gegenüber der vorherigen Fassung — Begründung siehe dort: ein zweiter Consent-Schalter wäre für strukturell dieselbe Art Cloud-Verarbeitung nicht sinnvoll unterscheidbar, Daniel hat die Mitnutzung explizit vorgegeben.
- **Migration b) — additiv `PhotoScore.category_override: str | None`** (Default `NULL`): unverändert gegenüber der vorherigen Fassung im Zweck (dauerhafte, manuelle Übersteuerung des sonst automatisch abgeleiteten `category_key`, wirkt auch über künftige volle Re-Scoring-Läufe hinweg: `category_key = score.category_override or derive_category_key(...)`). Der Wertebereich ändert sich faktisch (kann jetzt ein `canonical_key` aus der neuen Label-Registry sein, nicht mehr zwingend eines von drei festen Werten) — das Feld selbst bleibt ein freier String, keine Migrationsänderung nötig.
- **Migration c1) — neue Tabelle `category_labels`** (kanonische Label-Registry, **projektübergreifend, kein `project_id`-Bezug** — bewusste Vereinfachung, siehe Begründung): `id` (PK), `canonical_key: str` (`UNIQUE`, URL-/Key-sicherer Slug, z.B. `"hund"`), `display_name: str` (der zuerst gesehene Roh-Label-Text in Originalschreibweise, z.B. `"Hund"` — reine Anzeige-Hilfe, keine kuratierte Übersetzung, keine eigene Pflege-UI in dieser Spec), `embedding: JSON` (Liste von `float`, 384-dimensionaler Vektor, siehe Punkt 4), `created_at`.
- **Migration c2) — neue Tabelle `photo_category_detections`** (Struktur-Neufassung gegenüber der vorherigen ADR-Fassung: **1:N statt 1:1 zu Photo**, da jetzt bis zu drei Label pro Foto möglich sind): `id` (PK), `photo_id` (FK `photos.id`, **kein** Primary Key mehr), `category_label_id` (FK `category_labels.id`), `raw_label: str` (der ungekürzte, vom Vision-LLM gelieferte Text, wie zurückgeliefert — Audit-/Debug-Spur, welche konkrete Formulierung auf welchen `canonical_key` gemappt wurde), `confidence: float`, `provider: str` (analog `photo_landmark_detections.provider`, ADR 0031 Punkt 5, ohne Python-Default — Tabelle ist neu, kein Altbestand vor dieser Spalte), `computed_at`. `UniqueConstraint(photo_id, category_label_id)` — verhindert zwei Zeilen für dasselbe Foto×kanonisches-Label-Paar (relevant, falls zwei der bis zu drei Roh-Labels eines Fotos auf denselben `canonical_key` clustern, siehe Punkt 4: dann wird die Zeile mit der höheren `confidence` behalten, kein Duplikat geschrieben). Immer 1-3 Zeilen pro erfolgreich klassifiziertem Foto (nie 0 — der Prompt erzwingt mindestens ein Label, kein "nichts erkannt"-Fall, unverändert gegenüber der vorherigen Fassung). `Photo.category_label_detections: list[PhotoCategoryDetection]` (statt vormals `Photo.category_detection: PhotoCategoryDetection | None`), `cascade="all, delete-orphan"`.
  - **Begründung projektübergreifend statt projektgebunden:** `category_labels` speichert reine Vokabular-Einträge ("hund" ist kein personenbezogenes/projektspezifisches Datum), keine Fotoinhalte. Eine projektgebundene Registry würde bei mehreren Projekten (Familienarchiv typischerweise mehrere Reisen/Zeiträume als getrennte Projekte) identische Label wiederholt neu anlegen und die Cluster-Qualität unnötig verschlechtern (weniger Beispiele pro Cluster). Für dieses Zwei-Personen-Familienprojekt (keine Mandantentrennung zwischen Projekten nötig) eine bewusste, dokumentierte Vereinfachung — bei einem späteren Bedarf an harter Mandantentrennung zwischen Projekten wäre das eine neue, eigene ADR (analog der bereits in ADR 0023 etablierten Konvention für Revisionen).
- **Migration d) — neue Tabelle `remote_category_classification_runs`** — unverändert gegenüber der vorherigen Fassung (Run-Tracking-Tabelle analog `ScoringRun`/`CriterionScoringRun`, `last_progress_at`-Watchdog-Spalte, `worker.py::reap_stalled_runs` bekommt einen vierten, eigenständigen Block, kein `scoring_run_id`-FK, kein `409`-Staleness-Guard, kein Ausschuss-Gate-Erfordernis — Begründung unverändert: dieser Job schreibt ausschließlich in `photo_category_detections`/`category_labels`, berührt weder `cluster_key` noch `PhotoRanking` direkt).

### 3. Neues Modul `remote_classification.py` + Extraktion von `cloud_vision.py` — unverändert im Grundmuster, Antwortschema erweitert

Wie in der vorherigen Fassung: **neues, gemeinsames, niedrigstufiges Modul `cloud_vision.py`** (URLs/Modell-IDs/Timeout/Response-Parsing-Helfer, aus `landmark.py` extrahiert, providerneutral, kein neues Secret) + **neues Modul `remote_classification.py`** (Protocol + zwei konkrete `httpx`-Clients + Dispatch-Factory, strukturell analog `landmark.py`). Geändert ist das Antwortschema:

- `CategoryLabelDetection` (`@dataclass(frozen=True)`: `label: str`, `confidence: float`) statt vormals `CategoryDetection` (einzelner Kategorie-Wert) — ein Roh-Label + Konfidenz.
- `CategoryDetectionClientLike(Protocol)`: `async def classify(self, image_bytes: bytes, mime_type: str) -> list[CategoryLabelDetection]` (Rückgabe jetzt eine Liste, 1-3 Einträge, statt eines einzelnen Werts).
- **`REMOTE_CATEGORY_LABELS`-Allow-Liste entfällt ersatzlos** (war die zentrale Annahme der vorherigen Fassung: geschlossenes Vokabular) — Validierung ist jetzt strukturell statt inhaltlich: `_category_labels_from_json(parsed) -> list[CategoryLabelDetection]` prüft (a) `parsed["labels"]` ist eine Liste mit `MIN_REMOTE_LABELS_PER_PHOTO <= len(...) <= MAX_REMOTE_LABELS_PER_PHOTO` (`1`/`3`, neue Modul-Konstanten), (b) jedes Element hat ein nicht-leeres, getrimmtes `label: str` mit höchstens `MAX_REMOTE_LABEL_LENGTH = 60` Zeichen (defensive Obergrenze gegen eine entartete Modellantwort, verhindert einen übermäßig langen `canonical_key`/`display_name`), (c) `confidence` ist zu `float` konvertierbar und wird auf `[0, 1]` geklemmt (identisches Muster zu `_landmark_detection_from_json`). Jede Verletzung → `RemoteCategoryClassificationApiError`, best-effort für dieses eine Foto übersprungen (identische Fehlerbehandlungs-Philosophie wie zuvor, keine Verhaltensänderung an dieser Stelle).
- Prompt (`_PROMPT`, Modul-Konstante): fordert 1-3 kurze, prägnante deutsche Schlagworte (bevorzugt Substantive, z.B. Ereignis/Ort/Motiv/Tier — bewusst offen, keine Beispiel-Kategorie-Liste im Prompt, um das Modell nicht implizit auf ein Quasi-Vokabular festzulegen) mit je einer Konfidenz, exakt als JSON `{"labels": [{"label": "...", "confidence": 0.0-1.0}, ...]}`. Akzeptiert stillschweigend auch fremdsprachige Modellantworten (keine harte Sprachprüfung) — die Ähnlichkeits-Zusammenfassung (Punkt 4) ist die strukturelle Antwort auf sprachliche Varianz, nicht eine Prompt-seitige Erzwingung.
- `_MAX_RESPONSE_TOKENS` bleibt bei `256` (weiterhin ausreichend für ein JSON-Array mit bis zu drei kurzen Objekten).

### 4. Label-Normalisierung + Ähnlichkeits-Zusammenfassung: neues lokales Embedding-Modul `label_embedding.py`, neue externe Abhängigkeit

**Ablauf pro rohem Remote-Label** (reine Funktion `remote_classification.py::resolve_canonical_label`, aufgerufen von `worker.py::run_remote_category_classification` sequentiell nach jedem asyncio.gather-Batch — siehe Punkt 5, keine Nebenläufigkeits-Race zwischen zwei gleichzeitig neu angelegten, eigentlich identischen kanonischen Labeln):

1. **Text-Normalisierung** (`_normalize_label_text`, reine String-Funktion, kein Modell-Aufruf): `unicodedata.normalize("NFKC", raw).strip().casefold()`.
2. **Exakter Fast-Path:** stimmt die normalisierte Form mit der normalisierten `display_name` eines bereits bestehenden `category_labels`-Eintrags überein ("Hund" vs. "hund" vs. "HUND"), wird dieser wiederverwendet — **kein** Embedding-Aufruf nötig (spart Rechenzeit für den Hauptfall exakter/nahezu-exakter Wiederholungen).
3. **Ähnlichkeits-Fallback über Embeddings:** sonst wird die normalisierte Form über das neue lokale Embedding-Modell (`label_embedding.py`, siehe unten) in einen 384-dimensionalen Vektor umgewandelt und die Kosinus-Ähnlichkeit gegen **alle** bereits bestehenden `category_labels`-Einträge berechnet (kleine, langsam wachsende Menge — projektübergreifend über die Zeit vermutlich niedrige Hundert Einträge, ein voller Scan ist unproblematisch, kein Vektor-Index/keine `pgvector`-Erweiterung nötig). Übersteigt die höchste gefundene Ähnlichkeit `CATEGORY_LABEL_SIMILARITY_THRESHOLD`, wird der zugehörige bestehende Eintrag wiederverwendet.
4. **Sonst: neuer kanonischer Eintrag.** `canonical_key` wird aus der normalisierten Form geschlagwortartig geslugt (`_slugify`: Kleinbuchstaben, Leerzeichen/Sonderzeichen zu `_`, doppelte `_` reduziert — dieselbe Klasse einfacher, reiner Textfunktion wie andernorts im Projekt, keine neue Bibliothek). `display_name` = der Roh-Label-Text wie zuerst geliefert (Originalschreibweise). `embedding` = der in Schritt 3 bereits berechnete Vektor (kein zweiter Modell-Aufruf).

```python
# Dokumentiert-unkalibrierter Startwert (developer verifiziert/kalibriert mit ein paar echten
# Test-Label-Paaren wie "Hund"/"Hunde"/"dog" vs. "Katze"/"Hund" vor dem Festschreiben - gleiche
# Klasse wie CATEGORY_ACTIVE_THRESHOLD_FRACTION/SHARPNESS_NORMALIZATION_CEILING, kein
# Fotokorpus/Label-Korpus im Repo zur Kalibrierung).
CATEGORY_LABEL_SIMILARITY_THRESHOLD = 0.78
```

**Neues, isoliertes Modul `label_embedding.py`** (analog `aesthetics.py`: ein neues lokales ML-Modell bekommt ein eigenes Modul, damit die schwere Abhängigkeit auf genau den Importpfad begrenzt bleibt, der sie tatsächlich braucht):

- `LabelEmbedderLike(Protocol)`: `def embed(self, text: str) -> list[float]` — bewusst **synchron** (reine, schnelle CPU-Inferenz auf kurzen Texten, kein Netzwerk, analog `AestheticsModelLike.predict`/`FaceDetectorLike`), erlaubt ein Fake in Unit-Tests ohne echtes Modell.
- `build_label_embedder() -> LabelEmbedderLike` — echte Implementierung, lädt ein gepinntes, im Repository eingecheckte Asset-Paar (`assets/label_embedder.onnx` + `assets/label_embedder_tokenizer.json`, je mit eigener SHA256-Konstante + Verifikationstest, analog dem bestehenden `.tflite`/`.hdf5`/`.task`-Muster), tokenisiert über `tokenizers.Tokenizer`, führt eine `onnxruntime.InferenceSession`-Inferenz aus, mean-poolt die Token-Embeddings über die Attention-Maske und normiert L2 (Standard-Rezept für Sentence-Transformer-Modelle dieser Familie) — läuft **wie `build_aesthetics_model`**, d.h. **wird** in Tests exercised (über ein Fake, plus ein dedizierter SHA256-/Ausgabe-Dimension-Sanity-Test des echten Assets), anders als die nie automatisiert aufgerufenen Cloud-Client-Factories (`build_landmark_client`/`build_category_classification_client`).

**Modellwahl (recherchiert, `research-engineer`, 2026-08-23):** `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (Basis: `microsoft/Multilingual-MiniLM-L12-H384`, MIT; Sentence-Transformers-Finetune, Apache-2.0 — beide Lizenzen unproblematisch für dieses private, nicht-kommerzielle Projekt, konsistent mit dem bereits etablierten Apache-2.0-Präzedenzfall NIMA/`aesthetics.py`), ausgeführt über eine **int8-quantisierte ONNX-Variante via `onnxruntime`+`tokenizers`** — **explizit nicht** `sentence-transformers`/`transformers`/`torch` (kein PyTorch im Image) **und explizit nicht** die TensorFlow-Hub-Alternative (Universal Sentence Encoder Multilingual), obwohl `tensorflow` bereits im Image vorhanden ist:

- Das Modell ist **spezifisch auf Paraphrase-Erkennung kurzer Textstücke trainiert** (trifft "Hund"/"Hunde"/"dog"-Clustering direkter als USE Multilingual, dessen offizielle Doku sich ausdrücklich auf "sentences, phrases or short paragraphs" bezieht, ohne belegte Qualitätsaussage für Ein-Wort-Eingaben).
- Die TF-Hub-Route würde zusätzlich `tensorflow_text` erfordern (SentencePiece-Tokenizer-Op), dessen Releases eng an eine exakte `tensorflow`-Version gekoppelt sind — ein zusätzliches, im offenen `tensorflow>=2.16`-Versionsraum riskantes Pinning-Problem (recherchiert belegt über mehrere GitHub-Issues), das den vermeintlichen "passt zum bestehenden Framework"-Vorteil in der Praxis teilweise aufhebt.
- Die ONNX-Route vermeidet dieses Risiko vollständig UND vermeidet eine zweite schwere ML-Runtime (PyTorch) — `onnxruntime` ist ein kleines, reines CPU-Wheel ohne CUDA-Anteil in der Standardinstallation.
- 384-dimensionale Embeddings, 50+ Sprachen inkl. Deutsch/Englisch (explizit cross-lingual ausgerichtet — deckt Daniels "ggf. sprachübergreifend"-Anforderung ab).

**Offene, vom `developer`-Agenten beim TDD-Einstieg zu verifizierende Punkte** (analog zur bereits etablierten Pflicht, Modell-Details vor dem Festschreiben zu verifizieren, ADR 0025/0031/0022-Nachtrag): die recherchierte fp32-Größe des Basis-Modells ist mit 471 MB belegt, die tatsächliche Größe der quantisierten ONNX-Datei ist nur grob geschätzt (Faustregel ~100-150 MB) und **vor dem Commit des Assets real zu messen** (analog dem bereits etablierten "Docker-Image-Wachstum real gemessen, nicht nur geschätzt"-Präzedenzfall, ADR-0022-Nachtrag) — sollte der reale Footprint deutlich über der Schätzung liegen, ist das dem Daniel zurückzumelden, bevor das Asset committet wird. `onnxruntime`/`tokenizers`-Paketgrößen sind ebenfalls vor dem Festschreiben in `backend/Dockerfile`/`pyproject.toml` zu prüfen (grobe Erwartung: niedriger zweistelliger MB-Bereich, deutlich unter dem `tensorflow`/`mediapipe`-Fußabdruck).

**Neue Backend-Abhängigkeiten:** `onnxruntime>=1.19`, `tokenizers>=0.20` (beide reine CPU-/Rust-Pakete, kein GPU-Anteil, keine transitive PyTorch-/zweite-TensorFlow-Version-Abhängigkeit). Modell-Assets werden wie die bestehenden `.tflite`/`.hdf5`/`.task`-Dateien einmalig beim Commit heruntergeladen und SHA256-verifiziert eingecheckt — **kein Laufzeit-/Build-Zeit-Download von Hugging Face**, identische Sicherheitshaltung wie bei allen bisherigen lokalen Modell-Assets (kein unerwarteter Netzwerkzugriff, keine mutable, nachträglich austauschbare Gewichtsquelle).

### 5. Eigener Job `classify_categories_remote`, kein Teil von `run_criterion_scoring` — unverändert

Wie in der vorherigen Fassung: eigenständiger, expliziter Trigger (`run_remote_category_classification`/`classify_categories_remote`), identische Kandidatenmenge (kompletter Ausschuss-Überlebender-Bestand, kein Vorfilter, ADR 0021), identisches Skip-Verhalten bereits klassifizierter Fotos (jetzt geprüft über "existiert **mindestens eine** `photo_category_detections`-Zeile für dieses Foto", nicht mehr "existiert die eine Zeile"), identisches Nebenläufigkeits-Setting `settings.remote_category_classification_concurrency` (Default `2`), identische Fehlerbehandlung (best-effort, kein Retry, kein Laufabbruch).

**Neu, pro erfolgreichem Cloud-Aufruf:** statt eines einzelnen Upserts jetzt für jedes der 1-3 zurückgelieferten Labels ein Aufruf von `resolve_canonical_label` (Punkt 4) gegen den aktuellen In-Memory-Snapshot der `category_labels`-Tabelle (zu Laufbeginn einmal geladen, bei jedem neu angelegten kanonischen Label sofort lokal ergänzt — kein erneutes `SELECT`), danach ein Upsert der zugehörigen `photo_category_detections`-Zeile. Werden zwei der bis zu drei Roh-Labels eines Fotos auf denselben `canonical_key` aufgelöst, wird nur eine Zeile geschrieben (höhere `confidence` gewinnt, Punkt 2c2).

### 6. Endpunkte — Override auf mehrere Kandidaten erweitert

Vier neue Endpunkte, wie zuvor, aber Override-Endpunkte substanziell angepasst:

1. **`GET /projects/{id}/classify-categories-remote/estimate`** — unverändert im Vertrag (`candidate_count`/`provider`/`price_per_image_usd`/`estimated_cost_usd`, `200` immer, auch bei `candidate_count=0`, unabhängig vom Consent-Schalter). `price_per_image_usd` leicht angepasst (Punkt 8, Kostenschätzung).
2. **`POST /projects/{id}/classify-categories-remote`** — unverändert (`202`, `403` ohne Consent, `409` ohne erfolgreichen `ScoringRun`).
3. **`PUT /photos/{id}/category-override`** — **geändert:** nimmt jetzt einen Body `{"category_key": "<canonical_key>"}` entgegen (`CategoryOverrideIn`, ein Pflichtfeld). **Weiterhin kein Freitext-Sicherheitsrisiko:** der Wert wird serverseitig ausschließlich gegen die Menge der für **dieses konkrete Foto** bereits persistierten `photo_category_detections.category_label.canonical_key`-Werte geprüft (ein einfacher Existenz-`SELECT`, kein Ähnlichkeits-/Embedding-Aufruf zur Anfragezeit nötig) — ein beliebiger, nicht für dieses Foto erkannter String bleibt weiterhin unmöglich, es wird nur nicht mehr zwingend "die eine" Remote-Kategorie akzeptiert, sondern eine von bis zu drei. `404` Foto/Projekt, `409` falls `category_key` zu keiner vorhandenen Erkennung dieses Fotos passt, `409` falls keine `PhotoRanking`-Zeile im aktuellen Lauf existiert. Antwort `200` mit `CategoryOverrideOut { photo_id: int, category_key: str }` (Konvention `PUT /photos/{id}/rating`, nicht `204` — der gesetzte Wert wird direkt zurückgegeben).
4. **`DELETE /photos/{id}/category-override`** — unverändert im Vertrag (setzt zurück, `204`, idempotent), aber die interne Rekonstruktion des automatisch abgeleiteten `category_key` (Punkt 7) muss jetzt zusätzlich die zur-Laufzeit-entdeckten Remote-Label des vollen Kandidatenpools mit rekonstruieren (dieselbe Merge-Logik wie in `run_criterion_scoring`, Punkt 1 — als kleine, gemeinsam genutzte Hilfsfunktion `worker.py::_merge_remote_category_labels(session, candidate_values) -> frozenset[str]` extrahiert, DRY zwischen den beiden Aufrufstellen).

`ProjectOut` bekommt weiterhin `last_remote_category_classification_run`. `PhotoOut` bekommt **`remote_category_labels: list[RemoteCategoryLabelOut]`** (statt vormals eines einzelnen optionalen Felds — immer eine Liste, nie `None`, analog `ratings`/`criterion_scores`, 0-3 Einträge; `RemoteCategoryLabelOut`: `canonical_key`, `display_name`, `raw_label`, `confidence`, `provider`) und weiterhin `category_override: str | None`.

### 7. Sofortige Wirkung des Overrides: gezielte Partitions-Neusortierung statt vollem Re-Scoring — unverändert im Mechanismus

Wie in der vorherigen Fassung: `worker.py::reassign_photo_category(session, criterion_scoring_run_id, photo_id, cluster_key, new_category_key)`, synchron aus beiden Override-Endpunkten aufgerufen, ruft `ranking.py::rank_photos` (ADR 0021) nur für die zwei betroffenen `(cluster_key, category_key)`-Partitionen erneut auf — kein neuer Ranking-Algorithmus. Für `PUT` ist `new_category_key = body.category_key` (bereits validiert, Punkt 6.3). Für `DELETE` wird `new_category_key` über die neue gemeinsame Hilfsfunktion `_merge_remote_category_labels` + einen frischen `derive_active_categories`/`derive_category_key`-Aufruf (jetzt inkl. `dynamic_keys`) über den vollständigen Kandidatenpool des Laufs rekonstruiert.

**Bewusst weiterhin zugelassen:** ein manueller Override kann eine Partition erzeugen, die die 15%-Schwelle sonst nicht erreicht hätte (ADR 0023) — unverändert. **Bewusst weiterhin nicht abgesichert:** kein `409`-Staleness-Guard gegen einen zeitgleich neu gestarteten `score-criteria`-Lauf — unverändert, gleiche Risikoklasse wie `confirm-ausschuss-gate`.

### 8. Kostenschätzung: Konstante bleibt, Wert leicht angepasst wegen größerer strukturierter Antwort

Der grundlegende Ansatz bleibt: `remote_classification.py::COST_PER_IMAGE_USD: dict[Literal["anthropic","mistral"], float]`, dokumentiert-unkalibriert, `developer` verifiziert vor dem Festschreiben. **Angepasst gegenüber der vorherigen Fassung:** die Antwort ist jetzt ein JSON-Array mit bis zu drei `{label, confidence}`-Objekten statt eines einzelnen `{name, confidence}`-Objekts — mehr Output-Tokens (grob 80-160 statt vormals 30-60 bei Anthropic), bei einem im Output-Preis dominanten Modell (`claude-haiku-4-5`: $5/MTok Output vs. $1/MTok Input) eine spürbare, wenn auch nicht dominante Verschiebung. Grobe Neuschätzung: Anthropic ≈ **$0,0020-0,0028/Bild** (vormals $0,0019, Bildtoken-Anteil ~$0,0016 unverändert dominant), Mistral ≈ **$0,0002-0,0010/Bild** (Bandbreite proportional verbreitert, Basis weiterhin unsicher, siehe vorherige Fassung). Beide Werte weiterhin `developer`-Verifikationspflicht vor Festschreiben (ADR 0025/0031-Präzedenzfall), inkl. eines echten Testaufrufs für Mistral zur Ermittlung der tatsächlichen `usage`-Tokenzahl.

## Begründung

- Löst das eigentliche Ziel der Kurskorrektur strukturell: Kategorien entstehen aus tatsächlich beobachteten, offenen Remote-Ergebnissen, nicht aus einer vorab im Prompt/Code festgelegten Werteliste — konsistent mit dem bereits in ADR 0023 etablierten Grundsatz ("Kategorie-Fähigkeit als Registry-/Häufigkeits-Eigenschaft, nicht als Code-Prioritätskette"), hier auf zur Laufzeit entdeckte Label erweitert, ohne die bestehende, gut getestete Registry-Logik für die acht heutigen Kriterien zu verändern (nur additiv erweitert).
- Ein `frozenset[str]` aus Pseudo-Keys statt eines neuen Dataclass-Typs hält die Erweiterung minimal — kein zweites Konzept neben `CriterionDefinition`, nur ein zusätzlicher, klar abgegrenzter Präfix-Namensraum (`"remote:"`).
- Die Ähnlichkeits-Zusammenfassung ist bewusst pragmatisch (Nearest-Neighbor gegen eine wachsende, im Speicher gehaltene Menge, kein echtes Offline-Clustering/keine Vektor-Datenbank) — für die zu erwartende Größenordnung (ein Familienarchiv, keine Millionen unterschiedlicher Label) ausreichend, ohne eine weitere Infrastruktur-Abhängigkeit (`pgvector` o.ä.) einzuführen.
- Die Modellwahl (ONNX statt PyTorch, statt TF-Hub) minimiert den Abhängigkeits-Zuwachs bewusst gegen zwei konkret identifizierte Risiken (PyTorch-Fußabdruck, `tensorflow_text`-Versions-Pinning) statt der naheliegenden, aber jeweils riskanteren Standardwahl.
- Wiederverwendet weiterhin drei bereits etablierte Muster vollständig: Provider-Dispatch/Consent/Nebenläufigkeit (ADR 0025/0031), `rank_photos`/`PhotoRanking`-Partitionierung (ADR 0021), `derive_active_categories`/`derive_category_key` (ADR 0023) — nicht mehr nur bei der Override-Rücknahme, sondern jetzt als zentraler, unveränderter Integrationspunkt für die gesamte Kurskorrektur.

## Konsequenzen

- **Neue Backend-Abhängigkeiten:** `onnxruntime>=1.19`, `tokenizers>=0.20` (beide CPU-only, kein GPU-Anteil) — die einzige inhaltlich neue externe Abhängigkeit dieser ADR (der Cloud-Vision-Teil selbst bringt weiterhin keine neue Abhängigkeit, reiner `httpx`-Aufruf).
- **Neue Modell-Assets:** `assets/label_embedder.onnx` + `assets/label_embedder_tokenizer.json`, SHA256-gepinnt, einmalig bei Commit heruntergeladen (kein Laufzeit-Download) — reale Größe vor Commit zu verifizieren (siehe Punkt 4).
- **Neues Secret:** keines.
- **Neue Migration(en):** (a) Umbenennung zweier `Project`-Spalten, (b) additiv `PhotoScore.category_override`, (c1) neue Tabelle `category_labels`, (c2) neue Tabelle `photo_category_detections` (1:N, Struktur-Neufassung gegenüber der vorherigen ADR-Fassung dieser Datei — da diese nie gemerged wurde, keine reale Migrationshistorie zu bereinigen), (d) neue Tabelle `remote_category_classification_runs`.
- **`worker.py::reap_stalled_runs`** braucht einen vierten Tabellen-Block (unverändert gegenüber der vorherigen Fassung).
- **Docker-Image-Wachstum:** zusätzlich zum bereits gemessenen `tensorflow`/`mediapipe`-Wachstum (ADR 0022-Nachtrag, +2,9 GB) ein weiterer, deutlich kleinerer Zuwachs durch `onnxruntime`+Modell-Asset — real zu messen (analog ADR-0022-Nachtrag-Präzedenzfall), nicht nur zu schätzen, bevor das Asset committet wird.
- **`docs/architecture.md`/`README.md`/`docs/setup.md`** (Owner `architect`) werden nach Umsetzung um `remote_classification.py`, `cloud_vision.py`, `label_embedding.py`, die fünf Datenmodell-Änderungen (inkl. der beiden neuen/geänderten Tabellen `category_labels`/`photo_category_detections`), `REMOTE_CATEGORY_CLASSIFICATION_CONCURRENCY`, die vier Endpunkte und die zwei neuen Assets ergänzt.
- **`specs/architecture/0003-securitykonzept.md`** braucht eine Ergänzung (Zuständigkeit `security-engineer`) — zweiter produktiver `CriterionSource`-unabhängiger Cloud-Datenfluss im Projekt, jetzt zusätzlich mit einem lokalen Text-Embedding-Modell als neuer, wenn auch rein lokal laufender Bestandteil (kein neuer Netzwerk-Vertrauensrand, aber ein neues Drittanbieter-Modell-Asset mit eigener Integritätsprüfung).
- **`specs/architecture/0002-testkonzept.md`/`specs/architecture/0004-design-system.md`** brauchen jeweils eine Anpassung an die geänderte Override-Endpunkt-Form (Body statt parameterlos) und die neue Mehrfach-Label-Anzeige — Zuständigkeit `test-engineer`/`ux-ui-designer`, siehe Rückmeldung an den Aufrufer.
- Ein späterer, generischer "Remote-Label gezielt auf bestehende lokale Kategorie-Keys mappen"-Wunsch (siehe dokumentierte Lücke, Punkt 1) bliebe architekturrelevant und bräuchte eine eigene, neue ADR.
- Ein späterer Wunsch nach harter Mandantentrennung der `category_labels`-Registry zwischen Projekten (siehe Punkt 2, projektübergreifende Begründung) wäre ebenfalls eine eigene, neue ADR.
