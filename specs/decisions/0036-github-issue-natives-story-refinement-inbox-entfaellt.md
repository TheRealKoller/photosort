# 0036 - GitHub-Issue-natives Story-Refinement: `capture` legt Issues an, `story-refiner` übernimmt das fachliche Schärfen, lokale Inbox entfällt

**Status:** Accepted
**Datum:** 2026-08-26
**Bezug:** `specs/inbox/0033-status-lifecycle-ueberarbeiten.md` und `specs/inbox/0034-inbox-direkt-als-github-issue.md` (beide durch diese ADR/die zugehörige Spec [`0059`](../features/0059-story-lebenszyklus-github-issues.md) inhaltlich aufgelöst, Dateien werden gelöscht), ADR [`decisions/0017-github-projects-v2-spec-sync.md`](./0017-github-projects-v2-spec-sync.md) (bleibt vollständig unverändert gültig — betrifft ausschließlich `specs/features/*.md`), ADR [`decisions/0030-github-sync-natives-status-feld-inbox-einbindung.md`](./0030-github-sync-natives-status-feld-inbox-einbindung.md) (Abschnitte 4, 5, 7, 8 hiermit abgelöst, soweit sie den Inbox-Pfad betreffen; Abschnitte 1–3 und 6 bleiben für Feature-Specs unverändert gültig — siehe Nachtrag dort), `architect`-Konsultation im `idea-sharpener`-Ablauf für Spec 0059 am 2026-08-26.

**Nachtrag (2026-08-27):** Abschnitt 2 (der 5-Werte-Status-Lebenszyklus `Unrefined`/`Story`/`Proposed`/`Accepted`/`Implemented`) ist durch ADR [`decisions/0037-status-lebenszyklus-umsetzungsfortschritt-pr-merge-erkennung.md`](./0037-status-lebenszyklus-umsetzungsfortschritt-pr-merge-erkennung.md) abgelöst — neuer 6-Werte-Lebenszyklus `Unrefined`/`Ready`/`Todo`/`In Progress`/`Review`/`Done` mit granularerem Umsetzungsfortschritt für Feature-Specs. Alle übrigen Abschnitte dieser ADR (1, 3–7) bleiben unverändert gültig, diese ADR bleibt `Accepted`. Reiner Verweis, kein nachträgliches Editieren der ursprünglichen Entscheidung/Begründung unten.

## Kontext

Seit PR #173 (Spec 0052/ADR 0030) läuft ein echter bidirektionaler Sync für `specs/inbox/*.md` gegen das GitHub Project — jeder Inbox-Eintrag existiert als lokale Datei *und* als GitHub-Issue, mit Hash-Vergleich zur Konflikterkennung. Daniel möchte diese Zweigleisigkeit für die Vorstufe vor einer technischen Feature-Spec auflösen:

- `capture` soll eine neue Idee/einen Bug direkt als GitHub-Issue anlegen, keine lokale Datei mehr.
- Ein neuer, von `idea-sharpener` getrennter Skill übernimmt das rein fachliche Schärfen (Verständnis, Roadmap-Einordnung, Code-/Spec-Konfliktprüfung, Devil's Advocate) und schreibt das Ergebnis — Ziel, User Story, Akzeptanzkriterien — direkt und ausschließlich in den GitHub-Issue-Body. Keine lokale Zwischendatei, kein bidirektionaler Datei-Sync für diese Stufe.
- `specs/roadmap.md` bekommt Priorität/Status bereits auf dieser "Story"-Stufe, referenziert dabei die GitHub-Issue-Nummer statt einer Spec-Datei.
- Erst wenn eine Story umgesetzt werden soll, entsteht über einen stark reduzierten `idea-sharpener` (nur noch Architektur/UX/Test/Security + Spec-Anlage) ein technisches Spec-File unter `specs/features/NNNN.md`.
- Bestehende Inbox-Einträge werden migriert: `0033`/`0034` werden durch diese Umsetzung selbst aufgelöst (Dateien gelöscht); `0004`, `0016`, `0029`, `0035`, `0036`, `0037`, `0040`, `0041` werden einmalig als neue GitHub-Issues nachgezogen (Dateien danach gelöscht); `0027` und `0031` bleiben ausdrücklich unangetastet liegen (nicht Teil dieser Entscheidung).

Entscheidender struktureller Punkt, der die gesamte Lösung trägt: Solange eine Story ausschließlich im GitHub-Issue lebt (keine lokale Kopie), gibt es keine zwei Quellen mehr, die auseinanderlaufen könnten — das bidirektionale Hash-/Konflikt-Modell aus ADR 0017/0030 existiert exakt deshalb, weil dort *zwei* Kopien (Datei + Issue) über die Zeit divergieren können. Für die Story-Stufe entfällt dieses Problem strukturell, nicht nur organisatorisch: `gh issue view` *ist* bereits die aktuelle Wahrheit, ein "Pull" ist nichts anderes als ein Lesezugriff.

Diese ADR ist wie 0017/0030 eine Prozess-/Tooling-Entscheidung für den KI-Entwicklungsprozess selbst, keine Änderung an PhotoSorts eigenem Technologie-Stack/Datenmodell — wird aber als ADR festgehalten, weil sie eine bereits als architekturrelevant markierte Grundsatzentscheidung (ADR 0030, Inbox-Einbindung) revidiert und ein neues Lebenszyklus-/Datenmodell (Status `Story`, issue-basierte Identität ohne lokale Datei) einführt.

## Entscheidung

### 1. Identität ab der Story-Stufe ist die GitHub-Issue-Nummer selbst — kein Marker-Kommentar, kein eigener Nummernkreis

Anders als bei Feature-Specs/dem heutigen Inbox-Mechanismus (zwei unabhängige, potenziell kollidierende lokale Nummernkreise, deshalb Marker-Kommentare `photosort-spec`/`photosort-inbox` zur robusten Identifikation, siehe ADR 0030 Abschnitt 4) gibt es für eine frisch erfasste Idee/einen Bug ab sofort **keine lokale Datei und keinen eigenen Nummernkreis mehr** — die GitHub-Issue-Nummer selbst ist die einzige, bereits eindeutige Identität. Kein Marker-Kommentar im Issue-Body nötig, solange die Nummer ausschließlich issue-basiert adressiert wird (`--only issue:NNN`, siehe Abschnitt 5).

Erst wenn eine Story zu einer technischen Feature-Spec wird, bekommt sie zusätzlich eine *eigene*, vom Issue unabhängige Spec-Dateinummer (`specs/features/NNNN.md` mit eigenem Nummernkreis) — das war laut Daniels expliziter Randbedingung nicht Gegenstand dieser Entscheidung (`specs/inbox/0031-spec-nummern-github-projekt-angleichen.md` bleibt unangetastet, eine spätere Angleichung der Nummernkreise ist eine eigenständige, hier bewusst nicht vorweggenommene Entscheidung). Für diesen Übergang wird ab jetzt ein Marker-Kommentar (`<!-- photosort-spec: NNNN -->`) neu ins bestehende Issue geschrieben — exakt wie beim heutigen `created`-Fall, nur dass kein neues Issue entsteht, sondern ein bereits bestehendes "adoptiert" wird (siehe Abschnitt 6).

### 2. Erweiterter Status-Lebenszyklus im nativen `Status`-Feld: `Unrefined` → `Story` → `Proposed`/`Accepted` → `Implemented`

Das bestehende native Single-Select-Feld `Status` (ADR 0030 Abschnitt 1) bekommt einen neuen Zwischenwert `Story`, eingefügt zwischen `Unrefined` und `Proposed`:

```
STATUS_OPTIONS = ["Unrefined", "Story", "Proposed", "Accepted", "Implemented"]
```

- `Unrefined`: frisch per `capture` erfasstes Issue, roher Text, keine Priorität.
- `Story`: fachlich verfeinert (Ziel/User Story/Akzeptanzkriterien stehen strukturiert im Issue-Body), von Daniel im Schärfen-Gespräch bestätigt (das Gespräch *ist* die Freigabe, analog zum bestehenden Prinzip bei Feature-Specs) — bekommt ab hier eine Priorität und eine Zeile in `specs/roadmap.md`.
- `Proposed`/`Accepted`/`Implemented`: unverändert der bestehende Feature-Spec-Lifecycle (`specs/README.md`), unangetastet durch diese ADR.

`gh` (weiterhin kein `field-edit`, siehe ADR 0030 Kontext) erzwingt für das Hinzufügen der neuen Option denselben einmaligen, manuellen Migrationsschritt wie in ADR 0030 Abschnitt 3 (Feld löschen, mit den fünf neuen Optionen neu anlegen, danach ein voller Sync-Lauf) — bewusst kein automatischer Dauerbetrieb-Reparaturpfad, identische Begründung wie dort.

`Superseded` bleibt unverändert ein Label (nicht Feldwert, ADR 0030 Abschnitt 2) und wird jetzt bewusst auch für eine verworfene Story wiederverwendet (Feld leeren + Label setzen + Issue schließen) — kein neuer Mechanismus, reine Anwendung des bereits etablierten Musters auf eine frühere Lebenszyklus-Stufe.

### 3. Zwei getrennte Skills statt eines: `story-refiner` (fachlich) und ein stark reduzierter `idea-sharpener` (technisch)

Der heutige `idea-sharpener` wird an der bestehenden Naht zwischen fachlicher und technischer Arbeit zerschnitten:

- **Neuer Skill `.claude/skills/story-refiner/SKILL.md`** übernimmt die heutigen Schritte 0–5 (Herkunft/Verständnis, Roadmap-Einordnung via `requirements-engineer`, Code-/Spec-Konfliktprüfung, Nachfragen, Devil's Advocate) — inhaltlich nahezu unverändert, aber mit GitHub-Issue statt Inbox-Datei als Ein-/Ausgabe: liest ein bestehendes, per `capture` erfasstes Issue (`gh issue view NNN --json body,title,labels,state`) oder legt bei einer komplett neu im Chat geäußerten Idee selbst zuerst ein Issue an (identischer Mechanismus wie `capture`, siehe Abschnitt 4). Schreibt das Ergebnis als strukturierten Issue-Body (`## Ziel`, `## User Story`, `## Akzeptanzkriterien`) direkt zurück, setzt das `Status`-Feld auf `Story` und legt/aktualisiert die Prioritäts-Zeile in `specs/roadmap.md` (via `requirements-engineer`, wie heute). Übernimmt außerdem alle bisherigen Trigger-Phrasen von `idea-sharpener` ("ich hab da eine Idee", "was hältst du davon wenn...") — das ist ab jetzt der Einstiegspunkt für eine neue Idee, nicht mehr `idea-sharpener`.
- **`idea-sharpener` wird auf die heutigen Schritte 6–9 reduziert** (Architektur, UI/UX, Test/Security, Spec-Anlage) und bekommt einen neuen Trigger ("setz Story #NNN um", "mach aus Issue #NNN eine Spec"). Liest die Story ausschließlich aus dem GitHub-Issue (`gh issue view NNN --json body`) — kein lokales File. Prüft vor Beginn per Statusabfrage (Abschnitt 5, `--show-status`), dass das Issue tatsächlich im Status `Story` ist; ist das nicht der Fall, bricht er ab und verweist auf `story-refiner` (analog zum heutigen `aborted_reason`-Prinzip für einen unerwarteten Status).

Begründung gegen "ein Skill bleibt für beides zuständig": die fachliche Schärfung (ist die Idee gut, für wen, im Konflikt mit Bestehendem) und die technische Umsetzungsplanung sind bereits heute inhaltlich klar getrennte Phasen mit unterschiedlichen Konsultierten (`requirements-engineer` vs. `architect`/`ux-ui-designer`/`test-engineer`/`security-engineer`) — die Trennung in zwei Skills macht diese bereits bestehende Zäsur nur explizit und erlaubt, dass eine Story tagelang "auf Halde" liegen kann (Status `Story`, priorisiert, aber noch nicht technisch geplant), ohne dass ein einziger, monolithischer Skill-Lauf das erzwingt.

### 4. `capture`: legt direkt ein GitHub-Issue an, über dieselbe Python-Komponente wie der bestehende Sync

`capture` ruft künftig `scripts/github-project-sync` im neuen, dateilosen Erzeugungsmodus auf (siehe Abschnitt 5, `--create-issue`) statt eine lokale Markdown-Datei zu schreiben. Begründung gegen "roher `gh issue create`/`gh project item-add`-Aufruf direkt in der Skill-Datei": `ensure_project`/`ensure_fields`/`ensure_label`/`add_item_to_project` sind bereits als getestete, deterministische Funktionen in `gh_adapter.py` vorhanden — sie in `capture`s SKILL.md als Ad-hoc-Bash zu duplizieren widerspräche der in ADR 0017 Abschnitt 5 explizit begründeten Entscheidung, genau diese Art von Logik nicht ungetestet in eine Skill-Datei zu legen. `capture` bleibt bewusst schnell/ungefiltert (keine Rückfragen, keine Recherche) — nur der Speicherort ändert sich von "lokale Datei" zu "GitHub-Issue", die redaktionelle Zurückhaltung des Skills bleibt unverändert.

### 5. Erweiterung von `scripts/github-project-sync`: neuer dateiloser Modus für die Story-Stufe, kein bidirektionaler Inbox-Pfad mehr

Der bestehende CLI-Einstiegspunkt (`cli.py`) wird um issue-basierte, dateilose Operationen erweitert, die **kein** Pull/Konflikt-Handling brauchen (Begründung siehe Kontext — es gibt nur eine Kopie der Wahrheit):

- **`--create-issue --type {idee,bug} --title TITLE --body-file PATH`**: legt ein neues Issue an, fügt es dem Project hinzu, setzt `Status=Unrefined` sowie das `idee`/`bug`-Label (Wiederverwendung der bestehenden `ensure_label`/`set_issue_labels`-Bausteine aus ADR 0030 Abschnitt 6), legt einen minimalen Eintrag im neuen `stories`-Namensraum der Zustandsdatei an (`{issue_number: {item_id, last_synced_at}}` — bewusst **ohne** Hash-Felder, da nichts zu vergleichen ist). Gibt `{"issue_number": NNN}` zurück. Verwendet von `capture` und der einmaligen Alteintrags-Migration (Abschnitt 7).
- **`--only issue:NNN [--status Story] [--body-file PATH]`**: adressiert ein bestehendes Story-Issue rein über seine Nummer (Lookup im `stories`-Namensraum der Zustandsdatei, kein `create_issue`-Aufruf). Optional wird der Issue-Body ersetzt (`edit_issue_body`) und/oder das `Status`-Feld gesetzt. Berechnet bei jedem Aufruf die Priorität neu aus `specs/roadmap.md` (siehe unten) und pusht sie — exakt dieselbe Einbahnstraßen-Logik wie für Feature-Specs (ADR 0017 Abschnitt 4), nur ohne lokale Datei als Quelle. Verwendet von `story-refiner` am Ende der Verfeinerung.
- **`--only issue:NNN --show-status`** (rein lesend): liefert `{"status": "<aktueller Wert>"}` des nativen `Status`-Felds, ohne etwas zu verändern. Verwendet vom reduzierten `idea-sharpener` als Vorbedingungs-Check (Abschnitt 3).
- **Voller Lauf ohne `--only`**: synct weiterhin alle `specs/features/*.md` unverändert (ADR 0017/0030) und pusht zusätzlich die Priorität für jede `issue:`-referenzierte Zeile aus `specs/roadmap.md` (Batch-Äquivalent zum Prioritäts-Teil von `--only issue:NNN`, ohne Status/Body anzufassen) — fängt manuelle Prioritäts-Änderungen in `roadmap.md` zwischen gezielten Aufrufen ab.

**Priorität für Stories kommt aus `roadmap.md`, nicht aus einem neuen Feld/Modus (beantwortet die offene Frage zugunsten von Option a):** `roadmap_parser.py` bekommt eine zweite Erkennungs-Regel für Tabellenzeilen der Form `[#NNN](<Issue-URL>)` (statt der bestehenden `[NNNN](./features/...)`-Form) innerhalb derselben `### Offen — <Priorität>`-Unterabschnitte, Ergebnis-Keys mit `issue:`-Präfix (kollisionsfrei zu den bestehenden vierstelligen Spec-Keys). Begründung gegen Alternative (b) ("Priorität direkt auf dem Board pflegen, `roadmap.md` spiegelt nur"): das hätte die in ADR 0017 Abschnitt 4 bewusst getroffene Grundsatzentscheidung durchbrochen, dass Status/Priorität *immer* Einbahnstraße von der lokalen Quelle der Wahrheit zum Board sind, nie umgekehrt — für Stories bleibt `roadmap.md` (weiterhin vom `requirements-engineer` gepflegt) exakt diese lokale Quelle, nur eben ohne dass zusätzlich eine Spec-Datei existieren muss.

**Was mit `inbox_parser.py` und dem bidirektionalen Inbox-Pfad passiert (beantwortet die offene Frage):** beides wird ersatzlos entfernt, nicht wiederverwendet. `inbox_parser.py` existiert ausschließlich, um `specs/inbox/*.md` zu lesen — diese Dateien gibt es nach dieser Entscheidung nicht mehr (neu). Der bidirektionale Pull/Konflikt-Pfad für Inbox in `sync.py`/`cli.py` (`--only inbox:NNNN`, `--supersede-inbox`) wird ebenfalls entfernt — er löste ein Problem (zwei divergierende Kopien), das für die Story-Stufe strukturell nicht mehr existiert (siehe Kontext). Die generische H1/Status/Inhalts-Zone-Erkennung in `spec_parser.py`, die `inbox_parser.py` bisher wiederverwendet hatte, bleibt unverändert für Feature-Specs bestehen.

**Wie der reduzierte `idea-sharpener` die Story liest (beantwortet die offene Frage):** direkt per `gh issue view NNN --json body` und eigenem Lesen/Verständnis des Markdown-Inhalts (`## Ziel`/`## User Story`/`## Akzeptanzkriterien`) — **keine** neue Parsing-Komponente im Python-Package dafür. Begründung: anders als der maschinelle Sync-Abgleich (Hashes, Feld-Werte, Marker) ist das Lesen einer Story durch den Agenten selbst reine Textverständnis-Arbeit, für die ein LLM ohnehin geeigneter ist als eine weitere Regex-Parsing-Funktion — eine dedizierte `story_reader.py` wäre Komplexität ohne Mehrwert (der Agent liest den Issue-Body ohnehin vollständig, um daraus die Spec zu schreiben).

### 6. Übergang Story → Feature-Spec: bestehendes Issue wird adoptiert, nicht ersetzt

`--only NNNN --adopt-issue MMM` (bare `NNNN` = Feature-Spec-Scope wie heute, `--adopt-issue MMM` ersetzt `--supersede-inbox`): bei der erstmaligen Anlage der Spec-Datei `NNNN` wird **kein neues Issue erzeugt** — stattdessen wird der bestehende `stories`-Zustandseintrag für Issue `MMM` (inkl. `item_id`, keine erneute `add_item_to_project`-Anfrage nötig) in den `features`-Namensraum unter dem Schlüssel `NNNN` überführt, danach läuft der reguläre, bereits bestehende `pushed`-Pfad (schreibt jetzt erstmals den Marker-Kommentar `<!-- photosort-spec: NNNN -->` plus den vollen Spec-Inhalt in den Issue-Body, setzt `Status=Accepted`). Ab diesem Zeitpunkt ist Issue `MMM`/Spec `NNNN` vollständig unter der bestehenden, unveränderten bidirektionalen Feature-Spec-Logik aus ADR 0017 — Story-Scope-Befehle (`--only issue:MMM`) sind für diese Nummer danach nicht mehr gültig (kein Zustandseintrag mehr im `stories`-Namensraum).

Begründung gegen "neues Feature-Issue anlegen + altes Story-Issue mit `--supersede-inbox`-artigem Kommentar schließen" (das heutige Muster für den Inbox→Spec-Übergang): der einzige Grund für dieses Muster war die heutige Notwendigkeit, zwei getrennte, potenziell kollidierende Nummernkreise (Inbox-Datei-Nummer vs. Feature-Spec-Nummer) technisch zu entkoppeln. Diese Kollisionsgefahr existiert für die Story-Stufe gar nicht mehr (Abschnitt 1) — Adoption des bestehenden Issues ist einfacher, verliert keine Historie/Kommentare/Labels, und erspart den Verlinkungs-Umweg über einen Schließ-Kommentar.

### 7. Migration bestehender Inbox-Einträge: einmalig, teils Löschen, teils Nachziehen als Issue

Kein automatischer Migrationscode, sondern ein einmaliger, manueller Ablauf (analog zum Rollout-Schritt in ADR 0030 Abschnitt 3):

- `specs/inbox/0033-status-lifecycle-ueberarbeiten.md` und `specs/inbox/0034-inbox-direkt-als-github-issue.md`: werden durch die Umsetzung dieser ADR inhaltlich aufgelöst, Dateien gelöscht (kein Issue nötig — ihr Inhalt lebt jetzt als diese ADR/Spec 0059 weiter, exakt das bestehende Prinzip "nach erfolgreicher Verfeinerung wird die Inbox-Datei gelöscht", `capture`-Skill).
- `specs/inbox/0004`, `0016`, `0029`, `0035`, `0036`, `0037`, `0040`, `0041`: je ein `--create-issue`-Aufruf mit Typ/Titel/Rohtext aus der jeweiligen Datei, danach Datei löschen. Kein neuer `capture`-Aufruf im eigentlichen Sinn (die Ideen wurden ja bereits erfasst), sondern eine reine Trägerwechsel-Migration.
- `specs/inbox/0027-ai-workflow-ueberarbeiten.md` und `specs/inbox/0031-spec-nummern-github-projekt-angleichen.md`: bleiben unangetastet liegen, wie von Daniel explizit bestätigt. Das bedeutet: ihre alten, per ADR 0030 angelegten GitHub-Issues (Marker `photosort-inbox: 0027`/`photosort-inbox: 0031`) werden ab Inkrafttreten dieser ADR **nicht mehr** vom Sync-Code berührt (der `inbox`-Pfad, der sie bisher aktuell hielt, existiert nicht mehr) — sie frieren auf ihrem letzten synchronisierten Stand ein, bis sie irgendwann eigenständig durch `story-refiner`/eine künftige Entscheidung aufgegriffen werden. Das ist eine bewusst akzeptierte, hier explizit benannte Nebenwirkung, keine stillschweigende Inkonsistenz.

## Begründung

- **Keine lokale Kopie mehr ab der Story-Stufe:** löst das bidirektionale Hash-/Konflikt-Problem strukturell auf, statt es weiter zu verwalten — weniger Code (kein `inbox_parser.py`, keine Konflikterkennung, keine State-Migration für diese Stufe), weniger Fehlerfläche, ohne Funktionsverlust (Daniel kann ein Issue jederzeit direkt auf GitHub lesen/kommentieren, das war vorher genauso der Fall).
- **Story-Refiner/`idea-sharpener`-Trennung entlang der bestehenden fachlich/technisch-Naht:** keine künstliche neue Grenze, sondern Explizitmachen einer bereits im heutigen Skill vorhandenen Zäsur (unterschiedliche Konsultierte, siehe Abschnitt 3).
- **Priorität weiterhin aus `roadmap.md`, nie vom Board zurückgelesen:** konsistent mit der in ADR 0017 Abschnitt 4 getroffenen, bewusst nicht revidierten Grundsatzentscheidung.
- **Issue-Adoption statt Supersede-Kommentar beim Story→Spec-Übergang:** einfacher, weniger Datenverlust (Historie/Labels bleiben erhalten), und die Kollisionsgefahr, die den heutigen Supersede-Mechanismus überhaupt nötig gemacht hat, existiert für Issues nicht (jede Issue-Nummer ist bereits global eindeutig).
- **`capture` nutzt weiterhin das getestete Python-Package statt Ad-hoc-`gh`-Bash:** konsistent mit der in ADR 0017 Abschnitt 5 getroffenen Grundsatzentscheidung gegen ungetestete Sync-/Board-Logik in Skill-Dateien.
- **Migration einmalig/manuell statt Auto-Heal-Codepfad:** konsistent mit dem in ADR 0030 etablierten Prinzip, Board-/Daten-Migrationen nicht in einen dauerhaften, automatisch laufenden Code-Pfad zu gießen.
