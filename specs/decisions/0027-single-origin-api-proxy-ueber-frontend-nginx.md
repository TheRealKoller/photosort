# 0027 - Single-Origin-Exposure: Frontend-nginx proxied API-Requests intern an das Backend

**Status:** Accepted
**Datum:** 2026-08-19
**Bezug:** `specs/inbox/0018-nur-frontend-nach-aussen-exposen.md` (Idee, nach Aufnahme in die zugehörige Feature-Spec zu löschen); revidiert bewusst die in [`specs/features/0016-spa-fallback-frontend-nginx.md`](../features/0016-spa-fallback-frontend-nginx.md) explizit gezogene Scope-Grenze ("Out of Scope: eigener Reverse-Proxy ... Änderungen am Backend-Routing", Akzeptanzkriterium 7 "kein Reverse-Proxy über denselben nginx"); baut auf `frontend/nginx.conf` (Spec 0016) und dem expliziten IPv4-only-Default-Netzwerk auf ([`specs/features/0010-explicit-ipv4-only-network.md`](../features/0010-explicit-ipv4-only-network.md)).

## Kontext

Daniel muss aktuell im externen Reverse Proxy seines Homeservers (nicht Teil dieses Repos, siehe `docs/architecture.md`, "Bewusste Annahmen": "Kein eingebauter Reverse Proxy/TLS in `docker-compose.yml`") zwei Routen pflegen — eine auf `frontend:8080` (nginx, statisches Build), eine auf `backend:8000` (FastAPI) — weil der Browser die API aktuell cross-origin direkt anspricht (`VITE_API_BASE_URL`, zur Build-Zeit ins Bundle eingebacken, `CORS_ALLOWED_ORIGINS` im Backend). Mit Daniel geklärt: Das Frontend-nginx soll API-Requests stattdessen intern über das Docker-Netzwerk an den `backend`-Service weiterleiten (`proxy_pass`), sodass der Browser nur noch eine Origin sieht; `BACKEND_PORT` in `docker-compose.yml` soll dabei komplett entfallen.

Zwei Fallstricke, die eine naive Umsetzung brechen würden:

1. **Pfad-Kollision.** Die Backend-Router haben kein gemeinsames `/api`-Präfix (`/auth`, `/projects`, photo-/rating-spezifische Pfade direkt). Das Frontend hat aber die SPA-Client-Route `/projects/:projectId`. Ein naives "alles unter `/projects` geht ans Backend" würde mit `/projects/3` als Frontend-Route kollidieren.
2. **Docker-DNS-Caching.** nginx löst einen literalen Hostnamen in `proxy_pass` standardmäßig nur beim Start/Reload auf. Wird der `backend`-Container neu erstellt (z.B. Code-Deploy nur für Backend, `frontend` bleibt unverändert laufen und wird nicht neu gestartet), bekommt er eine neue interne IP — der `frontend`-Container würde bis zu seinem eigenen nächsten Neustart gegen die alte, tote IP proxyen.

## Entscheidung

1. **`/api`-Präfix-Strip in `frontend/nginx.conf`**, kein `/api`-Präfix im Backend selbst: neue `location /api/ { proxy_pass http://$backend_upstream/; }` (abschließendes `/` sowohl in der Location als auch im proxy_pass-Ziel strippt den `/api`-Anteil beim Weiterleiten). Der Browser ruft `/api/projects` auf, nginx leitet an `http://backend:8000/projects` weiter — identisch zum bestehenden Backend-Routing, **keine** Backend-Code-Änderung. Verworfene Alternative: `/api`-Präfix stattdessen im Backend selbst einführen (`APIRouter(prefix="/api")` an jedem Router) — hätte den Vorteil, dass auch ein direkter, nicht-proxyter Zugriff aufs Backend (Tests, künftige Nicht-Browser-Clients) konsistent `/api` nutzt, ist aber ein unnötig breiter Code-Eingriff für ein reines Netzwerk-/Exposing-Problem. Die Umsetzung im nginx bleibt lokal auf eine Datei begrenzt.

2. **Dynamische DNS-Auflösung statt eines literalen Hostnamens im Proxy-Ziel**, gegen Fallstrick 2: `resolver 127.0.0.11 valid=10s;` (Docker-interner Embedded-DNS-Server) plus `set $backend_upstream backend:8000;` und `proxy_pass http://$backend_upstream/;` — die Verwendung einer Variablen statt eines literalen Hosts zwingt nginx, den Hostnamen mit der `resolver`-`valid`-Zeit periodisch neu aufzulösen, statt ihn dauerhaft aus der Start-Auflösung zu cachen. Bekannter nginx+Docker-Fallstrick, hier bewusst vorab vermieden statt erst als Production-Ausfall nach einem Backend-only-Redeploy entdeckt.

3. **`ports:` beim `backend`-Service in `docker-compose.yml` entfällt vollständig** (nicht nur Bindung auf `127.0.0.1`) — wie mit Daniel geklärt ("soll komplett entfallen"). Erwogene, verworfene Alternative: `"127.0.0.1:${BACKEND_PORT:-8000}:8000"` (weiterhin vom Host selbst, aber nicht LAN-weit erreichbar) hätte den bisherigen lokalen `npm run dev`-Workflow unverändert gelassen, widerspricht aber der expliziten Vorgabe.

4. **`VITE_API_BASE_URL`-Default (Docker-Compose-Build-Arg, `.env.example`, `.env.demo.example`) wechselt von `http://localhost:8000` auf `/api`** (relativ) — funktioniert unverändert sowohl für `localhost:8080` als auch für Daniels echte Domain hinter seinem externen Reverse-Proxy, ohne dass ein Hostname/Port ins Bundle eingebacken werden muss.

5. **CORS bleibt unverändert bestehen**, konfigurierbar über `CORS_ALLOWED_ORIGINS`. Für den `docker compose up`-Vollstack-Pfad wird es nicht mehr gebraucht (Browser sieht nur noch eine Origin), bleibt aber nötig für den lokalen Vite-Dev-Server (Port 5173, weiterhin potenziell cross-origin gegen eine Backend-Instanz) und für ein eigenständiges, containerloses `uvicorn`-Backend. Kein Abbau der CORS-Middleware — geringer Aufwand, nützliche zusätzliche Verteidigungslinie, keine architekturrelevante Änderung.

6. **Kein neuer Mechanismus für `npm run dev` gegen einen dockerisierten Backend-Container** (kein Vite-Dev-Server-Proxy, kein Eingriff in `vite.config.ts`). Wer diesen Workflow braucht, exposed sich den Backend-Port über eine **eigene, nicht eingecheckte** `docker-compose.override.yml` (von Docker Compose automatisch zusätzlich zu `docker-compose.yml` eingelesen) mit demselben `ports:`-Eintrag, der jetzt aus dem Haupt-File entfernt wird, plus `VITE_API_BASE_URL=http://localhost:8000` lokal gesetzt. `.gitignore` bekommt einen neuen Eintrag `docker-compose.override.yml`, damit ein solches persönliches Override nicht versehentlich eingecheckt wird. Erwogene, verworfene Alternative: ein `server.proxy`-Eintrag in `vite.config.ts`, der `/api` durch den ohnehin laufenden `frontend`-Container hindurch an `backend` weiterreicht — koppelt den Dev-Workflow unnötig an einen zusätzlich laufenden `frontend`-Container für denselben Effekt, den ein einzeiliges persönliches Compose-Override einfacher erreicht.

7. **CI (`ci.yml`)**: Der bestehende Login-Funktionstest im Schritt "single-service migration ownership" (Spec 0013) darf nicht länger den entfallenden Host-Port ansprechen — wechselt auf einen internen Check innerhalb des `backend`-Containers (`docker compose exec -T backend python -c "..."` mit `urllib.request`, analog zum bestehenden Healthcheck-Muster; kein `curl` im schlanken Backend-Image installiert). Zusätzlich neuer, eigenständiger CI-Schritt "Functional check - single-origin API proxy via frontend nginx (spec 0018)": startet `backend`+`worker`+`frontend`, wartet auf Bereitschaft, ruft `http://localhost:${FRONTEND_PORT:-8080}/api/auth/login` vom Runner-Host per `curl` auf und erwartet `200` + `access_token` im Body (verifiziert den künftig einzigen produktionsrelevanten Pfad Browser → Frontend-Origin → intern zum Backend end-to-end), plus eine Negativ-Assertion, dass eine Verbindung zu `localhost:${BACKEND_PORT:-8000}` fehlschlägt — belegt aktiv, dass "kein Backend-Port mehr exponiert" auch tatsächlich eingehalten wird.

## Begründung

- Reduziert Daniels operativen Aufwand im externen Reverse Proxy exakt wie gewünscht (eine Route/eine Origin statt zwei), ohne neue Technologie (nginx ist bereits im Einsatz, Spec 0016) und ohne Backend-Code-Änderung.
- Revidiert eine zuvor bewusst gezogene Scope-Grenze (Spec 0016, AC 7) explizit statt sie stillschweigend zu unterlaufen — genau der Fall, für den ADRs/Spec-Historie da sind.
- Die beiden am leichtesten übersehbaren Fallstricke (Pfad-Kollision `/projects`, Docker-DNS-Caching bei einem Backend-only-Redeploy) sind hier vorab identifiziert und strukturell gelöst statt erst als Production-Bug entdeckt zu werden.
- Der lokale Entwicklungsworkflow bleibt vollständig erhalten, ohne dass das Hauptrepository dafür dauerhaft einen Sonderfall (offener Port, Dev-Server-Proxy-Konfiguration) mitschleppen muss — der Bedarf ist individuell/optional und gehört deshalb in ein persönliches, nicht versioniertes Override statt ins committete `docker-compose.yml`.

## Konsequenzen

- Geänderte Dateien: `frontend/nginx.conf`, `docker-compose.yml`, `.env.example`, `.env.demo.example`, `.gitignore`, `.github/workflows/ci.yml` (siehe Feature-Spec, Abschnitt "Architektur / Umsetzung", für die genaue Reihenfolge).
- `docs/architecture.md` (Owner: `architect`) wird nach Umsetzung um den neuen internen API-Proxy-Pfad und den Wegfall des Backend-Host-Ports ergänzt. Der bestehende Eintrag unter "Bewusste Annahmen" ("Kein eingebauter Reverse Proxy/TLS in `docker-compose.yml`") bleibt inhaltlich korrekt und unverändert — er betrifft weiterhin nur einen fehlenden *externen*, TLS-terminierenden Reverse Proxy für die gesamte Anwendung, nicht den neuen *internen* API-Proxy innerhalb des bereits vorhandenen Frontend-nginx-Containers.
- `docs/setup.md` (Owner: `architect`) wird um den geänderten Zugriffsweg (kein `http://localhost:8000` mehr im Vollstack-`docker compose up`-Betrieb) und die neue Override-Anleitung für `npm run dev` gegen einen dockerisierten Backend ergänzt.
- Test-Engineer-relevant (nicht Teil dieser ADR, aber direkte Konsequenz): der neue nginx-Proxy-Pfad braucht denselben Grad an CI-Funktionsnachweis wie der bestehende SPA-Fallback (Spec 0016); vom `test-engineer` im Testkonzept nachzuziehen, falls dort ein allgemeiner Eintrag zu nginx-Funktionschecks existiert.
