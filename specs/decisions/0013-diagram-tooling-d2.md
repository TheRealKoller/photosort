# 0013 - Diagramm-Tooling: D2 statt Mermaid

**Status:** Accepted
**Datum:** 2026-08-05

## Kontext

Bisher existiert genau ein Diagramm im gesamten Repository: das Workflow-Flowchart in `README.md` (zwei Subgraphs `Refine`/`Implement`, Mermaid-Syntax, live gerendert von GitHubs Markdown-Viewer über ` ```mermaid `-Codeblöcke). Auslöser dieser ADR (`specs/inbox/0003-bessere-diagramm-generierung-als-mermaid.md`): Daniel empfindet dieses Diagramm sowohl optisch als generisch als auch beim Rendern auf GitHub als zu groß/unhandlich.

Im Schärfungsgespräch wurde der Scope bewusst erweitert: statt nur das eine bestehende Diagramm zu überarbeiten, wird hier eine generelle Richtlinie samt Werkzeugwahl für **alle künftigen Diagramme** im Projekt getroffen (README, `specs/architecture/`, künftige Specs/ADRs) — mit der Begründung, dass sich das auszahlt, sobald weitere Diagramme dazukommen. Daniel hat außerdem explizit akzeptiert, dass vorgerenderte, eingecheckte Bilddateien (SVG/PNG) statt Live-Rendering im Markdown-Viewer eine gangbare Lösung sind.

Wichtiger Rahmen: PhotoSort wird ausschließlich von KI-Agenten (Claude Code) entwickelt und gepflegt. Jedes künftige Diagramm wird von einem Agenten aus einer Textbeschreibung heraus erzeugt/aktualisiert, nie von Daniel manuell in einem grafischen Editor nachbearbeitet. Das Werkzeug muss daher **vollständig reproduzierbar aus einem CLI-/Skript-Aufruf heraus generierbar** sein, ohne dass ein Mensch das Ergebnis grafisch nacharbeiten muss — das schließt rein GUI-basierte Tools (z.B. Excalidraw) von vornherein aus.

Geprüfte Kandidaten (alle text-zu-diagramm, alle CLI-fähig): **D2**, **PlantUML**, **Graphviz** (DOT), sowie — als Referenzpunkt für "was wir loswerden wollen" — das bisherige Mermaid.

Umgebungscheck (Node 22 + npm, Python 3.14, Java 17 sind im Entwicklungs-/Agenten-Environment bereits vorhanden; kein Go, kein `d2`/`dot`/`plantuml`-Binary):

- **D2** (`https://d2lang.com`): eigenständiges, statisch gelinktes Go-Binary. Kein offizielles npm- oder PyPI-Paket — die gleichnamigen Pakete `d2` auf npm (DHIS2-Frontend-Library) und PyPI (ein Python-ORM) sind fachfremde Namenskollisionen, verifiziert per `npm view d2` / `pip download d2`. Installation nur über das offizielle Install-Skript, ein GitHub-Release-Download oder Homebrew — nicht über die im Projekt bereits etablierten Paketmanager (`npm`, `uv pip`).
- **PlantUML**: benötigt eine JVM. Node-Wrapper `node-plantuml` (npm, bündelt das `.jar`) existiert und würde eine JVM-Abhängigkeit indirekt über npm reproduzierbar machen. Java ist im aktuellen Environment zwar vorhanden, aber im gesamten PhotoSort-Stack (Python + TypeScript, siehe `decisions/0001-tech-stack.md`) sonst nirgends ein Laufzeit-Bestandteil — ein dritter Sprach-/Laufzeit-Kontext ausschließlich für Doku-Tooling.
- **Graphviz/DOT**: über `@viz-js/viz` (npm, WebAssembly-Build von Graphviz) vollständig ohne externes Binary/JVM nutzbar, rein über `npm install` reproduzierbar — die sauberste Integration in die bestehende Toolchain. Visuelle Standardausgabe ist aber tendenziell noch "technischer"/kantiger als Mermaid, sofern nicht pro Diagramm mit Attributen (Farben, Rundungen, Schriftart) manuell nachgeschärft wird.

## Entscheidung

Wir verwenden **D2** als Standard-Werkzeug für alle Diagramme im Projekt (README, `specs/architecture/`, künftige Specs/ADRs), mit `--sketch` (handgezeichnete Optik) als Standard-Rendering-Modus.

## Begründung

- **Direkteste Antwort auf beide genannten Probleme:** D2 wurde explizit entwickelt, um das "generische Standard-Look"-Problem von Mermaid/Graphviz zu lösen (mehrere kuratierte Themes, `--sketch`-Modus für eine unverwechselbare, hand-gezeichnete Optik statt Mermaids Standard-Flowchart-Boxen) und bietet direkte Kontrolle über Layout-Richtung/Container-Kompaktheit — beides Stellschrauben gegen "zu groß beim GitHub-Rendering", zusätzlich zum ohnehin gewählten Weg über vorgerenderte SVGs (siehe Konsequenzen).
- **Kein Kompromiss beim Kernkriterium:** Wie PlantUML und Graphviz ist D2 vollständig CLI-/skriptgetrieben, keine manuelle Nacharbeit nötig — erfüllt die harte Anforderung, dass ein Agent das Ergebnis allein erzeugen kann.
- **PlantUML verworfen:** Löst keines der beiden genannten Probleme überzeugender als Mermaid (die Standardoptik für Aktivitäts-/Flow-artige Diagramme wirkt ähnlich "klassisch UML-artig") und würde eine dritte Laufzeitumgebung (JVM) ausschließlich für Doku-Tooling einführen, obwohl der bestehende Stack bewusst auf zwei Ökosysteme (Python + TypeScript, `decisions/0001-tech-stack.md`) begrenzt ist.
- **Graphviz (`@viz-js/viz`) verworfen, aber knapp:** Die sauberste Toolchain-Integration (reines `npm install`, kein externes Binary) ist ein echter Vorteil gegenüber D2 und wurde bewusst gegen den Optik-Vorteil von D2 abgewogen. Da Daniels Beschwerde explizit die Optik war ("nicht so super schön") und Graphviz' Standardlook dieses Problem ohne wiederkehrenden manuellen Styling-Aufwand pro Diagramm nicht zuverlässig löst, überwiegt hier D2s eingebaute, konsistente Optik den Nachteil der Installationsreibung.
- **Installationsreibung von D2 bewusst in Kauf genommen, nicht verdrängt:** Es gibt keinen npm-/pip-Wrapper. Das ist eine einmalige, dokumentierte Einrichtung pro Entwicklungsumgebung (Install-Skript/Release-Binary), kein wiederkehrender Aufwand pro Diagramm-Generierung, und betrifft ausschließlich lokales Doku-Tooling — nicht den App-Stack, nicht CI, nicht Docker Compose (siehe Konsequenzen). Vergleichbar mit anderen einmalig zu installierenden Werkzeugen (z.B. `docker`, `git`), nicht mit einer laufenden Produktivabhängigkeit.
- **Bewusst kein CI-Check auf "Bild ist aktuell zur Quelle":** Das würde ein D2-Binary in der CI-Umgebung voraussetzen, nur um eine Doku-Konsistenzprüfung zu erzwingen, für die aktuell kein konkretes Risiko dokumentiert ist (analog zur Begründung in `decisions/0012-single-service-migration-ownership.md`, Abschnitt "Advisory-Lock bewusst nicht zusätzlich umgesetzt": keine Infrastruktur für ein Problem, das noch nicht eingetreten ist). Sollte veraltete Diagramme in der Praxis zu einem wiederkehrenden Problem werden, ist ein CI-Check die naheliegende Ergänzung, dann per neuer ADR/Issue nachzuziehen.

## Konsequenzen

- **Speicherort:** Diagramm-Quelldateien liegen zentral unter `specs/diagrams/<kebab-case-name>.d2`, unabhängig davon, welches Markdown-Dokument sie einbettet (README, eine Architecture-Datei, eine Feature-Spec) — Name orientiert sich am Zweck des Diagramms, nicht am einbettenden Dokument, damit spätere Wiederverwendung an anderer Stelle keinen Umzug erfordert.
- **Gerenderte Bilder:** liegen neben der Quelldatei, gleicher Name, `.svg`-Endung (`specs/diagrams/<kebab-case-name>.svg`), z.B. `specs/diagrams/workflow-overview.d2` + `specs/diagrams/workflow-overview.svg`. SVG statt PNG, da verlustfrei skalierbar und von GitHubs Markdown-Renderer direkt eingebettet darstellbar. Beide Dateien (Quelle + Bild) werden eingecheckt, keine `.gitignore`-Ausnahme.
- **Generierung:** ein neues, eigenständiges Skript `scripts/render-diagrams.sh` (Bash, kein Python — reines Binary-Wrapping, gehört nicht zum bestehenden `scripts/`-Python-Paket/dessen `pyproject.toml`/CI-Job `demo-scripts`, das ein eigenständiges Anliegen — den Demo-Seed — bedient). Das Skript iteriert über `specs/diagrams/*.d2` und ruft für jede Datei `d2 --sketch <name>.d2 <name>.svg` auf; bricht mit klarer Fehlermeldung samt Link zur offiziellen D2-Installationsanleitung ab, falls `d2` nicht im `PATH` liegt (kein impliziter Auto-Download während der Generierung — Installation ist ein einmaliger, expliziter Setup-Schritt, nicht Teil des Render-Laufs).
- **Kein CI-Job, keine Docker-Compose-Integration** für Diagramm-Rendering — reines lokales Dev-/Doku-Tooling, konsistent mit der Randbedingung, dass Doku-Tooling keine Docker-Build-Voraussetzung braucht.
- **README/`specs/README.md`/`CLAUDE.md`:** die neuen Konventionen (Tool, Ablageort, Generierungsmechanismus, Checked-in-Bild statt Live-Rendering) werden bei Umsetzung der zugehörigen Feature-Spec dort kurz referenziert (Verweis auf diese ADR), nicht dupliziert.
- **Migration des bestehenden README-Diagramms** ist der erste Anwendungsfall dieser Richtlinie (Details siehe Feature-Spec) — kein rückwirkender Zwang, alle denkbaren künftigen Diagramme sofort zu erstellen, nur die eine bereits existierende Mermaid-Grafik wird migriert.
- **Voraussetzung für jede Entwicklungsumgebung, die Diagramme (neu) rendern soll:** ein lokal installiertes `d2`-Binary (siehe `https://d2lang.com/tour/install/`). Wird eine Umgebung genutzt, in der das nicht ohne Weiteres möglich ist, ist das ein Signal, diese Entscheidung per neuer ADR zu revidieren — nicht, sie stillschweigend zu unterlaufen (z.B. durch Rückfall auf Mermaid für einzelne Diagramme).
- Ein späterer Wechsel des Diagramm-Tools selbst (nicht nur Theme-/Flag-Anpassungen) bleibt architekturrelevant und braucht eine neue ADR, die diese hier als "Superseded" markiert.
