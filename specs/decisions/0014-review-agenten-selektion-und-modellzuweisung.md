# 0014 - Bedingte Review-Agenten und situative Modellzuweisung

**Status:** Accepted
**Datum:** 2026-08-07
**Bezug:** `specs/inbox/0005-agenten-nutzung-review-optimieren.md` (nach Aufnahme in diese ADR und die zugehörige Feature-Spec zu löschen); Feature-Spec wird im Anschluss an diese Architektur-Konsultation unter `specs/features/` angelegt (Nummer zum Zeitpunkt dieser ADR noch nicht vergeben).

## Kontext

Daniels Claude-Code-Nutzungskontingent (Subscription) ist ein hartes, spürbares Limit — `/status` zeigt Subagenten-Aufrufe als großen, aber nicht granular auf einzelne Agenten aufgeschlüsselten Verbrauchsposten. Der aktuelle Workflow ruft im `developer`-Agenten, Schritt 4 ("Review"), bei **jedem** Feature-Branch unbedingt vier Review-Agenten parallel auf (`test-engineer`, `security-engineer`, `architect`, `requirements-engineer`); `ux-ui-designer` ist bereits das einzige bedingte Beispiel (nur bei Frontend-/UI-Dateien im Diff). Zusätzlich erbt jeder Agenten-Aufruf projektweit (Review-Schritte, `idea-sharpener`-Konsultationen) bislang immer das Modell des aufrufenden Kontexts — kein Agenten-Frontmatter setzt `model:`, und kein Aufrufer übergibt je einen `model`-Parameter beim Agent-Tool-Aufruf.

Diese ADR ist eine reine **Workflow-/Prozess-Entscheidung** (wie Agenten im von KI betriebenen Entwicklungsprozess selbst eingesetzt werden), keine Änderung an Technologie-Stack, Datenmodell oder externer Abhängigkeit im engeren Wortsinn von `CLAUDE.md`. Sie wird dennoch als ADR festgehalten, weil sie — analog zu den bereits bestehenden Prozess-ADRs [`0007`](./0007-github-repo-access-hardening.md) (Issue-Freigabe-Policy) und [`0013`](./0013-diagram-tooling-d2.md) (Diagramm-Tooling) — eine dauerhafte, projektweite Regel für *jedes künftige Feature* setzt. Ohne eine einzige, bewusst getroffene und dokumentierte Regel würde genau die Inkonsistenz entstehen, die die `architect`-Rolle laut ihrer eigenen Existenzbegründung verhindern soll: Agent X wird bei Feature 7 übersprungen, weil es gerade praktisch schien, Agent Y nicht, ohne dass es je jemand entschieden hätte.

Bereits von `requirements-engineer`/Daniel geklärte, hier bindende Leitplanken (nicht mehr verhandelbar):
- Sicherheitsnetz: im Zweifel eher einen Agenten aufrufen als überspringen.
- Jede Skip-Entscheidung muss im `developer`-Abschlussbericht nachvollziehbar dokumentiert werden.
- Das bestehende `ux-ui-designer`-Verhalten (bedingt bei Frontend-Diff) bleibt unverändert und ist das Vorbild für die Mechanik.
- Die Modellwahl-Heuristik muss nachvollziehbar/dokumentiert sein.
- Review-Qualität darf durch eine günstigere Modellwahl nicht spürbar leiden (wird von `test-engineer` fortlaufend beobachtet, kein einmaliger Gate-Check).

**Zur Modellwahl-Kalibrierung:** Diese ADR trifft eine bewusst **konservative** Kalibrierung (siehe Entscheidung unten) statt einer aggressiveren Variante, die mehr Kontingent spart, aber mehr Qualitätsrisiko trägt. Der `architect`-Agent hatte zum Zeitpunkt der Entscheidung in seinem konkreten Ausführungskontext keinen Zugriff auf `AskUserQuestion`, konnte die Kalibrierung also nicht direkt mit Daniel abstimmen, und markierte sie deshalb vorläufig. **Nachträglich per Rückfrage im Hauptchat bestätigt (2026-08-07):** Daniel hat die konservative Kalibrierung ausdrücklich als richtig bestätigt ("Konservativ reicht") gegenüber der Alternative, auch `test-engineer`/`architect`-Review bei kleinen Diffs auf Haiku laufen zu lassen — die Tabelle unten ist damit nicht mehr nur ein vorläufiger Startpunkt, sondern eine bestätigte Entscheidung.

## Entscheidung

### Teil 1: Bedingte Review-Agenten in `developer`, Schritt 4

Der Mechanismus ist eine **feste, dokumentierte Diff-Heuristik pro Agent** (mechanisch aus `git diff --name-only main...HEAD` ableitbar), nicht eine freie Einzelfall-Entscheidung des `developer`-Agenten. Begründung siehe unten. Die vier bisher unbedingten Agenten werden dabei **nicht gleich behandelt** — zwei bleiben faktisch immer aktiv, zwei werden echt bedingt:

| Agent | Verhalten | Trigger (läuft, wenn mindestens einer zutrifft) |
|---|---|---|
| `test-engineer` | **Fast immer aktiv.** Skip nur im Entartungsfall. | Läuft immer, **außer** der Diff enthält ausschließlich Nicht-Code-Dateien (`specs/`, `docs/`, `*.md`, reine Config-Kommentare) und **keine** Datei unter `backend/src`, `backend/tests`, `frontend/src`, `frontend/tests` (oder Äquivalent). |
| `requirements-engineer` | **Immer aktiv, unverändert.** | Kein Skip-Pfad — siehe Begründung. |
| `security-engineer` | **Echt bedingt.** | Diff enthält mind. eine Datei unter `backend/src/photosort/api/`, `backend/src/photosort/opencloud/`; **oder** eine der explizit benannten Auth-/Secrets-tragenden Dateien `backend/src/photosort/main.py`, `security.py`, `rate_limit.py`, `config.py`, `seed.py`; **oder** eine neue Datei direkt unter `backend/src/photosort/` (nicht in einem bestehenden Unterordner — mechanischer Fallback für künftige neue Top-Level-Module, die die explizite Liste noch nicht kennt); **oder** eine Dependency-Datei (`backend/pyproject.toml`, `backend/uv.lock`, `frontend/package.json`, `frontend/package-lock.json`); **oder** `.env.example`; **oder** eine Datei unter `.github/workflows/**` (nicht nur Netzwerkkonfiguration — Workflows referenzieren Secrets und steuern Merge-/Push-Rechte); **oder** Docker-Compose-Netzwerkkonfiguration; **oder** eine Datei unter `frontend/src/auth/**` bzw. `frontend/src/api/client.ts` (Token-Handling/API-Client, unabhängig vom `ux-ui-designer`-Frontend-Trigger, der nur Design-System-Konformität prüft, keine Bedrohungsmodellierung). |
| `architect` | **Echt bedingt.** | Diff enthält neue Dateien/ein neues Modul; **oder** `specs/decisions/**`; **oder** Datenmodell-/Migrations-Dateien (`backend/alembic/**`); **oder** eine neue externe Abhängigkeit; **oder** der Abschnitt "Architektur / Umsetzung" der Spec ist nicht trivial (nicht "Wiederverwendung von X, 1–2 Dateien"). |
| `ux-ui-designer` | **Unverändert** (bestehendes Vorbild). | Diff enthält Dateien unter `frontend/`. |

**Sicherheitsnetz-Umsetzung:** Jede Bedingung ist als Oder-Liste formuliert; trifft auch nur ein Signal zu oder ist die Zuordnung unklar (z.B. eine neue Datei an unklarer Stelle), läuft der Agent — konsistent mit "im Zweifel eher aufrufen". Es gibt bewusst keine Bedingung, die auf reiner Diff-*Größe* (Zeilenzahl) beruht: Größe ist kein verlässlicher Proxy für Relevanz (ein Ein-Zeilen-Diff kann eine Auth-Prüfung entfernen).

### Teil 2: Situative Modellzuweisung

Zwei benannte Stufen, je Aufrufstelle fest zugeordnet (kein dynamisches Scoring zur Laufzeit):

- **Standard**: kein `model`-Parameter beim Agent-Tool-Aufruf (Vererbung vom aufrufenden Kontext, aktuell i.d.R. Sonnet).
- **Günstig**: `model: "haiku"`.

Zuordnungskriterium: **überwiegt beim jeweiligen Aufruf mechanischer Checklisten-Abgleich gegen bereits explizit dokumentierte Kriterien (Spec-Akzeptanzkriterien, Design-System-Tokens), bleibt Günstig vertretbar; überwiegt echtes fachliches Abwägen/Bedrohungsmodellierung/Trade-off-Urteil ohne feste Checkliste, bleibt es bei Standard.** Sicherheits- und architekturkritisches Urteilsvermögen wird nie herabgestuft; einmalige, folgenreiche Grundsatzentscheidungen (alle `idea-sharpener`-Konsultationen, da je Feature nur einmal aufgerufen und Grundlage für alles Folgende) ebenfalls nicht.

| Aufrufer → Ziel-Agent (Zweck) | Modell | Begründung |
|---|---|---|
| `developer` Schritt 1 → `architect` (Umsetzungsplanung, bei Bedarf) | Standard | Entwurfsentscheidung, kein Checklisten-Abgleich. |
| `developer` Schritt 4 → `test-engineer` (Review) | Standard | Ersetzt das gesamte generische Code-Review inkl. Bug-/Edge-Case-Urteil — kein reiner Abgleich. |
| `developer` Schritt 4 → `security-engineer` (Review) | Standard | Bedrohungsmodellierung; nie herabstufen. |
| `developer` Schritt 4 → `architect` (Review) | Standard | Pragmatiker-/Senior-Perspektiven sind explizit Abwägen, nicht Checkliste (auch wenn die Pedant-Perspektive für sich mechanisch wäre — der Aufruf liefert alle drei zusammen). |
| `developer` Schritt 4 → `requirements-engineer` (Review) | **Günstig (Haiku)** | Kern der Aufgabe ist Abgleich "Akzeptanzkriterium erfüllt: ja/nein" gegen eine bereits fixierte Liste — der am stärksten checklistenartige der fünf Review-Aufrufe. |
| `developer` Schritt 4 → `ux-ui-designer` (Review, bedingt) | **Günstig (Haiku)** | Überwiegend Abgleich gegen das dokumentierte Design-System; Projekt hat genau zwei Nutzer, entsprechend geringere Einsatzhöhe als bei `security-engineer`. |
| `idea-sharpener` Schritt 2 → `requirements-engineer` | Standard | Einmalig pro Feature, prägt Roadmap-Einordnung und AK-Erstfassung. |
| `idea-sharpener` Schritt 6 → `architect` | Standard | Grundsatzentscheidung, wirkt auf alle folgenden Schritte. |
| `idea-sharpener` Schritt 7 → `ux-ui-designer` | Standard | Grundsatzentscheidung (Ansatz, nicht Review). |
| `idea-sharpener` Schritt 8 → `test-engineer` / `security-engineer` | Standard | Grundsatzentscheidung (Strategie, nicht Review). |
| Hauptchat/Orchestrator → `developer` | Standard | Nie herabstufen — das ist die eigentliche Implementierungsarbeit. |
| `architect` (dieser Agent) → `AskUserQuestion` bei Kosten-/Produktentscheidungen | — | Kein Modell-Aspekt; siehe Kontext zur fehlenden Tool-Verfügbarkeit in diesem Lauf. |

Diese Tabelle ist die **einzige Quelle der Wahrheit** für Modellzuordnung; `docs/ai-workflow.md` bekommt eine gekürzte, für Außenstehende lesbare Zusammenfassung mit Verweis hierher, `.claude/agents/developer.md` und `.claude/skills/idea-sharpener/SKILL.md` tragen die konkreten `model`-Werte direkt an der jeweiligen Aufruf-Anweisung ein (nicht nur als Verweis), da sie zur Laufzeit unmittelbar ausführbar sein müssen, ohne eine externe Datei nachschlagen zu müssen.

### Teil 3: Bedingtes Copilot-Review in `developer`, Schritt 8

Nachträglich ergänzt (2026-08-07, direkte Anweisung von Daniel im Hauptchat, keine erneute idea-sharpener-Konsultation nötig, da eindeutig und ohne Produkt-Trade-off): Das automatisierte GitHub-Copilot-Review (`gh pr edit <PR> --add-reviewer "@copilot"`) wird **nur noch angefordert, wenn der PR mindestens eine Code-Datei ändert** — dieselbe Bedingung wie der `test-engineer`-Skip-Trigger aus Teil 1 (Diff enthält mind. eine Datei unter `backend/src`, `backend/tests`, `frontend/src`, `frontend/tests` oder Äquivalent). Enthält der PR ausschließlich Doku-/Spec-Dateien (`specs/`, `docs/`, `*.md`, reine Config-Kommentare), entfällt Schritt 8 vollständig — kein Anfordern, kein Warten, kein Auswerten.

**Begründung:** Copilot-Review prüft Code-Qualität/-Korrektheit; bei einem PR ganz ohne Code-Diff (z.B. Spec 0018, 0019, oder diese ADR selbst) gibt es strukturell nichts, was ein Code-Review dort finden könnte — ein angefordertes Review würde bestenfalls leer ausfallen, schlimmstenfalls Zeit mit Warten auf ein bedeutungsloses Ergebnis verschwenden. Bewusst dieselbe Bedingung wie `test-engineer` wiederverwendet statt einer eigenen Formulierung — ein PR ohne Code-Diff ist exakt der Fall, für den bereits eine geprüfte, dokumentierte Definition existiert; zwei leicht unterschiedliche Formulierungen für denselben Sachverhalt wären eine unnötige Inkonsistenzquelle.

## Begründung

- **Feste Diff-Heuristik statt freier `developer`-Einzelfallentscheidung (Teil 1):** Eine freie Entscheidung "prüfe, ob es diesmal nötig ist" ist genau das Muster, das über viele Features hinweg zu Drift führt (Feature 3 überspringt `architect` aus einem Grund, Feature 9 aus einem anderen, nie konsistent) — der exakt gleiche Grund, aus dem diese ADR und die `architect`-Rolle selbst existieren. Eine mechanische, im Voraus dokumentierte Bedingung ist außerdem für jedermann (auch Copilot-Review, spätere Audits) nachvollziehbar und ändert sich nur über eine bewusste ADR-Revision, nicht stillschweigend Lauf für Lauf.
- **`requirements-engineer` und `test-engineer` bleiben faktisch unbedingt:** Jeder `developer`-Lauf implementiert per Definition eine `Accepted`-Spec mit Akzeptanzkriterien (`requirements-engineer`s Kernprüfung) und erzeugt per striktem TDD-Zwang aus `CLAUDE.md` immer Code+Tests (`test-engineer`s Kernprüfung, der zugleich den generischen Code-Review-Schritt ersetzt). Eine erzwungene Skip-Bedingung hier zu konstruieren, nur damit "alle vier gleich bedingt aussehen", würde das Sicherheitsnetz ("im Zweifel eher aufrufen") künstlich unterlaufen — beide Agenten decken nahezu per Konstruktion jedes Mal etwas Prüfenswertes ab. Größere Einsparung liegt bei `security-engineer`/`architect`, die tatsächlich nur bei einer *Teilmenge* aller Diffs (sicherheitsrelevante Pfade bzw. neue/architektonisch relevante Strukturen) etwas zu prüfen haben.
- **Keine größenbasierte Heuristik:** Diff-Zeilenzahl korreliert schwach mit Risiko (siehe Kontext-Beispiel Ein-Zeilen-Auth-Änderung) und wäre schwerer zu dokumentieren/nachzuvollziehen als eine Pfad-/Datei-Bedingung.
- **Zwei Modellstufen statt granularem Scoring (Teil 2):** Ein Diff-Größen- oder Risiko-Score pro Aufruf, der das Modell dynamisch wählt, wäre selbst wieder eine Komponente mit Wartungsaufwand und eigenem Fehlerpotenzial (Pragmatiker-Einwand: löst ein Problem, das eine einfache, statische Tabelle pro Aufrufstelle bereits ausreichend löst). Die Aufrufstellen sind eine feste, kleine, bekannte Menge (ein Agent, eine Aufgabe, ein Zweck) — eine Tabelle mit einer Zeile pro Aufrufstelle ist einfacher zu pflegen und zu auditieren als Laufzeit-Logik.
- **Konservative Kalibrierung (nur `requirements-engineer`- und `ux-ui-designer`-Aufrufe auf Haiku):** Der größere Kontingent-Hebel ist ohnehin Teil 1 (ganze Aufrufe entfallen) — Teil 2 muss nicht aggressiv sein, um einen Beitrag zu leisten, und ein zu aggressiver Start (z.B. `security-engineer` pauschal auf Haiku) wäre schwerer vertretbar, falls sich die Qualitätsannahme als falsch herausstellt, als eine schrittweise Ausweitung von einer konservativen Basis aus.
- **`developer` selbst nie herabgestuft:** Er leistet die eigentliche TDD-Implementierungsarbeit; ein Qualitätsverlust hier wirkt sich direkt auf ausgelieferten Code aus, nicht nur auf einen nachgelagerten Prüfschritt mit eigenem Sicherheitsnetz.

## Konsequenzen

- `.claude/agents/developer.md`, Schritt 4, wird umgeschrieben: statt "starte alle zutreffenden Agenten" eine explizite Trigger-Tabelle je Agent (siehe oben) plus `model`-Angabe direkt an der jeweiligen Aufruf-Zeile. Die bestehende Doku-Pflicht ("Entscheidung, welche Agenten übersprungen wurden, muss dokumentiert werden") gilt unverändert und wird um "welches Modell je Aufruf verwendet wurde" ergänzt.
- `.claude/skills/idea-sharpener/SKILL.md`, Schritt 2/6/7/8: keine neue Skip-Logik (diese Aufrufe sind Konsultation, nicht Review, und laufen je Feature ohnehin nur einmal — vgl. Ursprungstext, der "Review" explizit von der Skip-Idee anspricht), aber `model`-Hinweis (Standard, explizit vermerkt statt stillschweigend) an jeder Aufrufstelle.
- `docs/ai-workflow.md`: neuer, kurzer Abschnitt (z.B. "Kosteneffiziente Agenten-Nutzung") mit einer gekürzten Fassung der Tabellen und Verweis auf diese ADR — qualifiziert für ein Update, da sich der Workflow/das Rollenmodell selbst ändert (`CLAUDE.md`, Abschnitt Doku-Pflege).
- `specs/diagrams/workflow-overview.d2`/`.svg`: der `review`-Knoten im `implement`-Subgraph listet aktuell alle fünf Review-Agenten mit einer Fußnote nur für `ux-ui-designer`. Die Fußnote wird erweitert/verallgemeinert, da jetzt auch `architect` und `security-engineer` bedingt laufen, `test-engineer`/`requirements-engineer` als (faktisch) unbedingte Basis kenntlich bleiben — sonst würde das Diagramm den neuen Zustand falsch darstellen. Neu rendern via `scripts/render-diagrams.sh` (ADR [`0013`](./0013-diagram-tooling-d2.md)).
- Kein Effekt auf `docs/architecture.md`/`docs/setup.md` — reine Prozess-/Workflow-Änderung, keine System-/Datenmodell-Änderung.
- **Wirksamkeits-/Qualitätsprüfung ist kein einmaliges Gate, sondern laufende Beobachtung:** `test-engineer` behält im Blick, ob die Review-Qualität durch die Haiku-Stufe spürbar leidet (z.B. offensichtlich zu oberflächliche `requirements-engineer`- oder `ux-ui-designer`-Reviews); fällt das auf, ist das ein Grund für eine neue, diese ADR ablösende ADR (z.B. Rückstufung einer Aufrufstelle auf Standard), nicht für ein stillschweigendes Unterlaufen der Tabelle.
- **`security-engineer`-Trigger nachgeschärft (2026-08-07, im Rahmen der Security-Konsultation des idea-sharpener-Ablaufs):** die ursprüngliche Formulierung "sonstiger Auth-/Secrets-Code" widersprach dem eigenen Anspruch dieser ADR auf eine rein mechanische, aus dem Diff ableitbare Heuristik — sie verließ sich auf eine freie Einschätzung des `developer`-Agenten, welche Dateien "irgendwie Auth-Code" sind. Ersetzt durch eine explizite Pfadliste (`main.py`, `security.py`, `rate_limit.py`, `config.py`, `seed.py`) plus mechanischen Fallback (neue Top-Level-Datei unter `backend/src/photosort/`). Zusätzlich zwei echte Abdeckungslücken geschlossen: CI-Workflow-Änderungen (`.github/workflows/**`, vorher nur "Netzwerkkonfiguration" — hätte z.B. den Fund aus Spec 0011 nicht getriggert) und Frontend-Auth-/API-Client-Code (`frontend/src/auth/**`, `frontend/src/api/client.ts` — vorher triggerte dort nur `ux-ui-designer`, der keine Bedrohungsmodellierung leistet).
- **Diese Kalibrierung wurde von Daniel bestätigt** (siehe Kontext, 2026-08-07) — eine spätere Anpassung der Tabelle bleibt trotzdem eine technische Detailentscheidung innerhalb dieser ADR-Richtung und erzeugt keine neue ADR, solange das Grundprinzip (feste Tabelle, Sicherheitsnetz "im Zweifel Standard") erhalten bleibt; nur ein Wechsel des Grundprinzips selbst (z.B. dynamisches statt statisches Scoring) würde eine neue, diese ablösende ADR erfordern.
- **`CLAUDE.md` (Konventionen-Abschnitt) und `.claude/agents/developer.md` Schritt 8 werden um die bedingte Copilot-Review-Regel aus Teil 3 ergänzt:** "immer ein Copilot-Review anfordern" wird zu "Copilot-Review anfordern, außer der PR ändert ausschließlich Doku-/Spec-Dateien".
