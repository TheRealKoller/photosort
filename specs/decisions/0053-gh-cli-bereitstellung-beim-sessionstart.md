# 0053 - `gh`-Bereitstellung beim Sessionstart: erste eingecheckte `.claude/settings.json`, Version entscheidet statt Umgebung

**Status:** Accepted
**Datum:** 2026-09-02
**Bezug:** GitHub-Issue [`#314`](https://github.com/TheRealKoller/photosort/issues/314) ("Remote-Session ohne Handgriff produktiv"), `specs/features/0314-gh-bereitstellung-remote-sessions.md`, ADR [`0052`](./0052-remote-lebenszyklus-diagnose-kommando-und-echter-board-preflight.md) (Abschnitt 4/5 — `gh-board.py` meldet, repariert nicht; Abschnitt 6 — kein zusätzliches Geheimnis), ADR [`0046`](./0046-pr-issue-verknuepfung-closing-keyword.md) (Abschnitt 5 — `closingIssuesReferences` als Vorbedingung von `finalize`), ADR [`0033`](./0033-modell-asset-download-statt-commit-label-embedder.md) (verifizierter Download statt Commit; `scripts/fetch-label-embedder-model.sh` als Muster für "der Wert wird dort gelesen, wo er gepflegt wird"), ADR [`0043`](./0043-spec-nummer-gleich-issue-nummer-sync-tool-entfaellt.md) (`gh-board.py` als einzige Board-Schreibstelle), `scripts/gh-board.py` (`MIN_GH_VERSION`), `specs/architecture/0003-securitykonzept.md`, `architect`-Konsultation für Story #314 am 2026-09-02 (inklusive `research-engineer`-Recherche zur Hook-/Cloud-Semantik).

## Kontext

Der Diagnoselauf aus Spec [`0309`](../features/0309-story-lebenszyklus-remote-sessions.md) hat den Remote-Befund belegt: In der geprüften Cloud-Session fehlte die GitHub-CLI vollständig (`[Errno 2] No such file or directory: 'gh'`), alle acht Lebenszyklus-Schritte waren blockiert. Die Authentifizierung war in Ordnung (`GH_TOKEN` **und** `GITHUB_TOKEN` gesetzt) — es fehlte das Werkzeug, nicht das Recht. `apt-cache policy gh` meldete dort als Candidate `2.45.0-1ubuntu0.3`, also selbst nach einer Installation aus der Distributions-Paketquelle eine Version **unter** der Grenze.

Sieben geprüfte Fakten bestimmen die Lösung. Die Punkte 4 bis 6 stammen aus der offiziellen Claude-Code-Dokumentation (`code.claude.com/docs/en/{hooks,hooks-guide,settings,permissions,cloud-environments}`) und, wo dort mehrdeutig, zusätzlich aus der eingebetteten Hook-Dokumentation des lokal ausgelieferten Binaries (Version 2.1.258) — geprüft statt angenommen, wie die Story es verlangt.

1. **Die Versionsgrenze ist nicht verhandelbar.** `MIN_GH_VERSION = "2.72.0"` (`scripts/gh-board.py:45`) steht dort, weil `gh pr view --json` erst ab dieser Version das Feld `closingIssuesReferences` kennt — die Vorbedingung, an der `finalize` laut ADR 0046 Abschnitt 5 die PR-Issue-Verknüpfung prüft. Ubuntus Paketquelle liegt 27 Minor-Versionen darunter; `apt install gh` löst das Problem also nicht, sondern verdeckt es (`gh` da, Lebenszyklus trotzdem blockiert).

2. **Die Voraussetzung steht nirgends geschrieben.** Weder `README.md` noch `docs/setup.md` noch `CLAUDE.md` erwähnen `gh` auch nur einmal, obwohl der gesamte Entwicklungsablauf darauf steht. Der Wert lebt heute als Konstante in `scripts/gh-board.py` und zusätzlich als Prosa-Zahl in `.claude/skills/github-board/SKILL.md` und `.claude/skills/ship-feature/SKILL.md`.

3. **Das Muster für einen verifizierten Bezug existiert im Projekt bereits.** `scripts/fetch-label-embedder-model.sh` (ADR 0033) lädt ein Asset, prüft es, ist idempotent und liest den erwarteten Wert per `sed` aus der Datei, in der er ohnehin gepflegt wird, statt ihn ein zweites Mal fest zu verdrahten. Genau diese Technik löst hier die Frage nach der einen pflegbaren Stelle.

4. **Hook-Semantik `SessionStart`.** Ohne `matcher` feuert ein Hook bei jedem Anlass (`startup`, `resume`, `clear`, `compact`, `fork`). Bei **Exit-Code 0 geht stdout in Claudes Kontext** — `SessionStart` ist eines der wenigen Ereignisse, für die das gilt; stderr eines mit 0 beendeten Hooks sieht Claude nie. `SessionStart` ist **nicht blockierbar**: Weder Exit-Code 2 noch ein anderer Code kann die Session verhindern, sie läuft in jedem Fall weiter. Gibt der Hook valides JSON aus, entscheidet das JSON und der Exit-Code wird ignoriert; wirksam sind für dieses Ereignis `systemMessage` (an den Nutzer) und `hookSpecificOutput.additionalContext` (an das Modell, zwingend verschachtelt — auf oberster Ebene wird es stillschweigend ignoriert). Hooks laufen per Default **blockierend** (`async: true` wäre das Gegenteil), und der Default-`timeout` für Kommando-Hooks beträgt **600 Sekunden**. `${CLAUDE_PROJECT_DIR}` steht zur Verfügung und löst auf die Repository-Wurzel auf.

5. **Settings-Semantik, insbesondere in Cloud-Sessions.** In einer Cloud-Session wird `.claude/settings.json` aus dem Repository **gelesen** (sie ist Teil des Klons), während `~/.claude/settings.json` **und** `.claude/settings.local.json` dort **nicht** gelesen werden. Und: Hooks aus Settings-Dateien laufen **vor** dem Vertrauensdialog — sie sind ausdrücklich nicht Teil dessen, was auf eine Freigabe wartet (das sind `permissions.allow` und `additionalDirectories`). Eine eingecheckte `.claude/settings.json` erreicht eine frische Remote-Session also ohne jeden Handgriff. Dieselbe Eigenschaft ist zugleich ihre Kehrseite: Sie führt ohne Bestätigung Code aus, in jeder Session, auch in jeder lokalen.

6. **Die Cloud-Umgebung hat zwei Eigenschaften, die dieser Entscheidung entgegenlaufen.**
   - Die Dokumentation der Cloud-Umgebungen führt `gh` unter den vorinstallierten Werkzeugen (neben `git`, `jq`, `yq`, `ripgrep`) — die Beobachtung aus 0309 widerspricht dem, und dieser Widerspruch ist ungeklärt.
   - Sie empfiehlt für genau diesen Fall ausdrücklich den anderen Weg: „Use a setup script to provision the VM itself: toolchains and CLI tools that aren't pre-installed. Use a SessionStart hook for project setup that should run everywhere, cloud and local."
   - Aller ausgehender Verkehr läuft über einen Proxy, und GitHub-Verkehr über einen eigenen mit **Repository-Scope**: „GitHub API and release-asset requests reach only repositories attached to the session, so a setup script that downloads release assets from an unattached repository gets a 403." `cli/cli` ist nicht das Session-Repository. Ein Download von dort kann in einer Anthropic-gehosteten Cloud-Session also am Proxy scheitern, obwohl `github.com` und `objects.githubusercontent.com` in der Standard-Allowlist stehen.

7. **Daniels Festlegung.** Die Vorkehrung soll im Repository liegen — versioniert, reviewbar, jede Umgebung automatisch erreichend — bewusst gegen das Setup-Script der Cloud-Oberfläche, obwohl dieses gecacht wird und keine Startlatenz kostet. Diese Festlegung ist Vorgabe dieser ADR, nicht ihr Ergebnis.

Diese ADR ist wie 0013/0016/0017/0033/0037/0042–0046/0052 eine Prozess-/Tooling-Entscheidung für die Entwicklungsumgebung selbst. Sie berührt PhotoSorts Laufzeitsystem, sein Datenmodell und seine Produktiv-Abhängigkeiten an keiner Stelle.

## Entscheidung

### 1. Die Vorkehrung ist ein `SessionStart`-Hook in der ersten eingecheckten `.claude/settings.json`

Das Repository bekommt seine erste `.claude/settings.json`. Sie enthält **genau einen** Eintrag: einen `SessionStart`-Hook, der `python3 "$CLAUDE_PROJECT_DIR/scripts/ensure-gh-cli.py"` ausführt, mit explizitem `timeout`. Keine `permissions`, keine `env`, kein `statusLine`, kein zweites Ereignis — jede weitere Einstellung wäre eine Regel, die ab sofort für jede Session in diesem Repository gälte, ohne dass diese Story sie verlangt hätte.

Der `matcher` bleibt leer, der Hook läuft also bei jedem Anlass. Eine Filterung auf `startup|resume` wäre möglich, spart aber nur den Schnellpfad aus Abschnitt 3 — ein Prozessstart — und kauft dafür eine Annahme über Anlassnamen ein, deren Verliererseite („der Hook läuft nie") teuer ist.

Der explizite `timeout` ist kein Detail: Der Default für Kommando-Hooks liegt bei 600 Sekunden, und ein hängender Proxy würde den Sessionstart ohne eigene Angabe zehn Minuten lang aufhalten. Der Wert wird auf zwei Minuten gesetzt, ergänzt um kürzere Zeitgrenzen am Download selbst.

Verworfen:

- **Setup-Script der Cloud-Umgebung.** Es wird in der Web-Oberfläche gepflegt, ist nicht versioniert, nicht reviewbar und erreicht keine andere Umgebung; für Daniel ist das die tragende Eigenschaft, und die Story macht sie zum Akzeptanzkriterium. Dass die Anbieter-Dokumentation für „CLI tools that aren't pre-installed" ausdrücklich diesen Weg empfiehlt (Kontext, Punkt 6), ist damit eine bewusst in Kauf genommene Abweichung — sie wird in Abschnitt 7 offen behandelt statt verschwiegen.
- **Ein `Setup`-Hook-Ereignis.** Das ausgelieferte Binary kennt neben `SessionStart` ein Ereignis für Repo-Setup mit den Auslösern `init`/`maintenance`, das inhaltlich besser passen würde (beim Einrichten der Umgebung statt bei jedem Start). In der offiziellen Dokumentation kommt es nicht vor, und ein nicht erkanntes Hook-Ereignis lässt eine Settings-Datei an der Validierung scheitern — in nicht-interaktivem Betrieb sogar stillschweigend. Der mögliche Gewinn (Millisekunden pro Start) steht gegen das Risiko, die ganze Datei und damit die eigentliche Vorkehrung zu verlieren.
- **Devcontainer / eigenes Dockerfile für die Entwicklungsumgebung.** Es gibt heute keines; die drei vorhandenen `Dockerfile` betreffen Backend, Frontend und Demo-Stack. Eine ganze Umgebungsdefinition einzuführen, um ein Binary bereitzustellen, ist ein Vielfaches der Aufgabe — und sie erreicht lokale Sessions ohne Container gar nicht.
- **`PATH` über `env` in der `settings.json` setzen.** Ein Wert, der `$HOME` enthalten muss, hängt an einer Interpolation, die für dieses Feld nicht belegt ist. Trägt sie nicht, steht dort ein literaler Unsinn als `PATH` — in **jeder** Session, auch jeder lokalen. Die Fehlerfolge ist schwerer als der Nutzen; Abschnitt 4 löst dieselbe Frage ohne dieses Risiko.
- **Das Binary ins Repository committen.** Es wäre proxy-fest (es käme mit dem Klon) und ist mit ~11 MB auch unterhalb jeder Grenze — aber es bläht jeden Klon dauerhaft auf, jede Anhebung von `MIN_GH_VERSION` legt eine weitere Kopie unwiderruflich in die Historie, und es widerspricht der in ADR 0033 getroffenen Linie („Assets werden bezogen, nicht committet"). Sollte sich der Proxy-Fall (Abschnitt 7) als Dauerzustand erweisen, ist der bessere Ausweg ein Asset an **unserem eigenen** Release, nicht ein Blob in der Historie — beides wäre eine neue ADR.

### 2. Die installierte Version entscheidet, nicht die Umgebung

Der Auslöser ist **ausschließlich** die Antwort auf „liegt `gh` in mindestens `MIN_GH_VERSION` vor?". `CLAUDE_CODE_REMOTE` wird **nicht** als Schalter benutzt, in keiner Richtung.

Das ist keine Aussage über die Variable: Sie ist offiziell dokumentiert, trägt in Remote-Web-Umgebungen den Wert `"true"` und ist lokal nicht gesetzt. Sie beantwortet nur die falsche Frage. Gebraucht wird „was fehlt hier?", geliefert wird „wo bin ich?" — und die beiden fallen nur zufällig zusammen. Der Unterschied zeigt sich in der Fehlerrichtung: Eine Umgebungs-Erkennung irrt **unsichtbar** (in einer Umgebungsvariante ist die Variable nicht gesetzt, die Vorkehrung greift nie, und niemand merkt es, bis wieder acht Lebenszyklus-Schritte blockiert sind — exakt der Zustand, den diese Story beendet). Eine Versionsprüfung irrt **sichtbar** (sie handelt einmal ohne Not, meldet es, und das ist harmlos). Bei gleichem Nutzen wählt man die sichtbare Fehlerart. Hinzu kommt: Die Latenz-Anforderung, für die man eine Umgebungsprüfung sonst brauchte, ist durch den Schnellpfad aus Abschnitt 3 schon erfüllt — der Schalter kaufte also nichts.

Damit ist auch die von Daniel übersprungene Vorprüfung entschärft, und zwar in beide Richtungen: Bringt eine frische Cloud-Umgebung `gh` bereits in ausreichender Version mit — was die Anbieter-Dokumentation behauptet und die Beobachtung aus 0309 bestreitet —, tut der Hook **nachweislich nichts**; er stellt eine Frage und schweigt. Bringt sie es nicht mit, handelt er. Der Entwurf ist unter beiden Befunden richtig, ohne dass der Befund vorliegen muss.

### 3. Lokale Folgenlosigkeit ist eine Eigenschaft des Schnellpfads, keine Zusicherung

Der Hook macht im Normalfall genau eines: `gh --version` aufrufen, die Zahl **numerisch** vergleichen (`parse_gh_version`-Semantik: `2.9.0` ist älter als `2.72.0`, ein Zeichenkettenvergleich behauptet das Gegenteil) und bei ausreichender Version **ohne jede Ausgabe** mit Exit-Code 0 enden. Ein Prozessstart, kein Netzwerk, keine Zeile im Kontext. Das ist die gesamte Belastung einer lokalen Session — auf Daniels Rechner liegt `gh 2.98.0`, der Schnellpfad greift dort also immer.

Schweigen im Erfolgsfall ist Teil der Entscheidung, nicht Kosmetik: Bei Exit-Code 0 wandert stdout in Claudes Kontext. Ein Hook, der bei jedem Sessionstart „alles in Ordnung" meldet, verbraucht Kontext für eine Nachricht ohne Informationsgehalt und trainiert das Wegsehen für den einen Fall, in dem er etwas zu sagen hat.

Handeln darf der Hook nur unter drei kumulativen Bedingungen, die zusammen die Anforderung „kein Eingriff in eine vorhandene, funktionierende Installation" tragen:

1. **Nur unterhalb von `$HOME`.** Zielverzeichnis ist `$HOME/.local/bin` (ersatzweise `$HOME/bin`, falls dieses im `PATH` liegt und jenes nicht). Nichts außerhalb des Heimatverzeichnisses wird je geschrieben.
2. **Niemals `sudo`, niemals ein Paketmanager.** Kein `apt`, kein `dnf`, kein `brew`. Eine paketverwaltete Installation wird nicht angefasst, nicht ersetzt und nicht entfernt.
3. **Nur, wenn die vorgefundene Version nicht genügt.** Eine ausreichende Installation wird nie überschrieben, unabhängig davon, wo sie liegt.

Eine zu alte `gh`-Installation ist von „funktionierend" nicht gedeckt — sie lässt `finalize` scheitern. Sie wird trotzdem nicht ersetzt, sondern nur durch eine neuere Datei im eigenen `$HOME`-Verzeichnis überlagert.

### 4. Der Hook prüft seinen eigenen Erfolg an derselben Frage, mit der er begonnen hat

Ein nach `$HOME/.local/bin` installiertes Binary nützt nichts, wenn dieses Verzeichnis nicht im `PATH` der Session liegt oder wenn ein älteres `gh` weiter vorne steht. Ein Hook kann den `PATH` seines Elternprozesses nicht ändern, und diese Grenze wird hier nicht mit Tricks umgangen — insbesondere wird **keine** Shell-Konfigurationsdatei des Nutzers (`~/.bashrc`, `~/.profile`) verändert.

Stattdessen ist der letzte Schritt des Hooks derselbe wie sein erster: `gh` über den `PATH` auflösen, Version lesen, vergleichen. Erst dieses Ergebnis wird gemeldet. Der Bericht sagt damit nie „installiert", sondern immer „in dieser Session nutzbar" oder „nicht nutzbar, und zwar aus diesem Grund" — inklusive der Fälle „installiert nach `<Pfad>`, aber `<Pfad>` liegt nicht im `PATH`" und „`<anderer Pfad>` verdeckt die Installation mit einer älteren Version".

### 5. Fehlschläge: immer Exit-Code 0, ein einziges JSON-Objekt, beide Empfänger

Aus Kontext-Punkt 4 folgt zwingend: Der Hook beendet sich **immer** mit Exit-Code 0 — auch und gerade beim Fehlschlag. Ein Exit-Code ≠ 0 würde stdout verwerfen und stderr bestenfalls dem Nutzer zeigen; der Agent, der unmittelbar danach `gh` benutzen will, erführe nichts. Die Session bricht ohnehin in keinem Fall ab — `SessionStart` ist nicht blockierbar —, dieser Exit-Code kauft also keine Sicherheit, sondern verkauft Sichtbarkeit.

Ist etwas zu melden, gibt der Hook **genau ein** JSON-Objekt auf stdout aus, mit zwei Feldern:

- `systemMessage` — die Meldung an Daniel in der Oberfläche,
- `hookSpecificOutput` mit `hookEventName: "SessionStart"` und `additionalContext` — dieselbe Aussage für den Agenten.

Erzeugt wird es mit `json.dumps`, nie durch Zeichenkettenverkettung. Eine unerwartete Ausnahme im Hook wird gefangen und ebenso gemeldet — kein Traceback, dieselbe Begründung wie in ADR 0052 (ein ungefangener Traceback gibt mit absoluten Pfaden und lokalem Benutzernamen mehr preis als eine Fehlermeldung).

### 6. Die Mindestversion bleibt an genau einer Stelle: `MIN_GH_VERSION`

Autoritativ ist und bleibt `MIN_GH_VERSION` in `scripts/gh-board.py` — die Datei, in der der Wert seine Wirkung entfaltet (ADR 0046 Abschnitt 5). Alles andere liest ihn von dort:

- **`scripts/ensure-gh-cli.py`** liest ihn zur Laufzeit per Regex aus der Datei — dieselbe Technik, mit der `scripts/fetch-label-embedder-model.sh` den SHA256 aus `label_embedding.py` zieht, statt ihn zu duplizieren (ADR 0033). Kein Import, keine Ausführung fremden Modulcodes; lässt sich der Wert nicht lesen, ist das ein gemeldeter Fehlschlag, kein stiller Rückfall auf eine geratene Zahl.
- **Ein Test hält die Kopplung fest**, indem er den herausgelesenen Wert gegen den echten Wert des geladenen `gh-board`-Moduls stellt. Damit ist „eine Stelle" keine Behauptung in einem Dokument, sondern eine in CI laufende Zusicherung: Wird der Wert dort geändert, zieht alles mit; wird die Konstante umbenannt oder umformatiert, wird der Lauf rot statt still falsch.
- **Auch die bezogene Version ist dieser Wert.** Es gibt keine zweite Konstante „welche Version installieren wir" — bezogen wird exakt die Mindestversion. Sie genügt per Definition, sie ist über den Release-Tag unveränderlich adressiert, und ein Wert, den es nicht gibt, kann nicht auseinanderlaufen. Die naheliegende Alternative „immer die neueste" wäre kein fester Punkt: Sie machte jeden Lauf von einem beweglichen Ziel abhängig, installierte in zwei Umgebungen zwei verschiedene Versionen und verlangte zusätzlich einen API-Aufruf zur Versionsermittlung, weil der Assetname die Version enthält.
- **`docs/setup.md` nennt die Zahl nicht**, sondern die Voraussetzung, ihre Begründung (Distributions-Paketquellen liegen darunter, `finalize` scheitert sonst) und den Ort, an dem sie gepflegt wird.
- **Die beiden `SKILL.md`-Stellen nennen die Zahl ab jetzt ebenfalls nicht mehr**, sondern verweisen auf die gepflegte Konstante. Sie beschreiben, wie eine Fehlermeldung zu deuten ist — und die Meldung selbst führt die Zahl bereits mit (`f"gh {MIN_GH_VERSION} ..."`), der Agent bekommt sie also im Moment des Bedarfs vom Werkzeug.

### 7. Bezogen wird ein einzelnes, versionsadressiertes Release-Asset — und der Proxy-Fall wird benannt, nicht kaschiert

Quelle ist `https://github.com/cli/cli/releases/download/v<MIN_GH_VERSION>/gh_<MIN_GH_VERSION>_linux_<arch>.tar.gz` (Tag mit `v`, Dateiname ohne), `<arch>` aus `uname -m` (`x86_64` → `amd64`, `aarch64`/`arm64` → `arm64`). Eine andere Architektur oder ein anderes Betriebssystem als Linux führt zu einer Meldung, nicht zu einem Versuch. Die Quelle ist **eine** Konstante im Skript, damit eine Folge-Story sie austauschen kann, ohne den Entwurf anzufassen.

- **Unauthentifiziert.** Der Bezug benutzt weder `GH_TOKEN` noch `GITHUB_TOKEN` noch sonst ein Credential, setzt keinen `Authorization`-Header und legt nichts an. Es entsteht kein zusätzliches dauerhaft abgelegtes Geheimnis — Akzeptanzkriterium der Story und deckungsgleich mit ADR 0052 Abschnitt 6. (In Cloud-Sessions tragen diese Variablen ohnehin nur einen Platzhalter, den der Proxy ersetzt; ein Skript, das sie ausliest, hielte nichts Brauchbares in der Hand.)
- **Integritätsprüfung gegen `gh_<version>_checksums.txt` aus demselben Release.** Ehrlich benannt: Diese Prüfung schützt gegen abgebrochene und verfälschte Übertragung, nicht gegen einen kompromittierten Ursprung — sie stammt von dort. Vertrauensanker ist TLS zu `github.com` plus das versionsfeste Release; derselbe Anker, an dem das gesamte Projekt ohnehin hängt (Repository, Releases, `gh` selbst). Signaturen liegen den Releases nicht bei.
- **Kein fest verdrahteter Hash wie in ADR 0033**, und der Unterschied ist inhaltlich: Dort zeigt die URL auf `resolve/main`, eine bewegliche Referenz, deren Inhalt sich unter derselben Adresse ändern kann — der gepinnte Hash ist dort die einzige Festlegung, *was* geladen wird. Hier ist die Adresse selbst schon die Festlegung. Ein zusätzlicher Hash machte die Aussage nicht stärker, führte aber eine zweite versionsabhängige Konstante ein, die bei jeder Anhebung von `MIN_GH_VERSION` synchron zu pflegen wäre — genau das, was Abschnitt 6 ausschließt.
- **Aus dem Archiv wird genau ein benanntes Mitglied gelesen** (`gh_<version>_linux_<arch>/bin/gh`) und selbst geschrieben, statt das Archiv zu entpacken. Kein Archivinhalt bestimmt einen Zielpfad; Pfad-Traversal ist damit strukturell ausgeschlossen statt nachträglich gefiltert.
- **Installiert wird atomar**: temporäre Datei im Zielverzeichnis, Rechte setzen, `os.replace`. Es gibt keinen Zeitpunkt, zu dem an der Zieladresse eine halb geschriebene oder nicht ausführbare Datei steht.
- **Der Proxy-Fall bekommt eine eigene Meldung.** In Anthropic-gehosteten Cloud-Sessions läuft GitHub-Verkehr über einen Proxy mit Repository-Scope, der Release-Assets fremder Repositories mit **403** abweist (Kontext, Punkt 6). Ein `403` beim Download wird deshalb nicht als generischer Netzwerkfehler gemeldet, sondern benennt diese Ursache und die beiden Auswege: `cli/cli` der Umgebung als zusätzliches Repository beigeben, oder die Installation im Setup-Script der Umgebung vornehmen. Die Meldung ist damit das, was der Hook in diesem Fall leisten kann — nicht die Bereitstellung, aber die richtige Diagnose statt einer irreführenden.

  Dass der Weg dennoch so gewählt wird, hat einen Grund, der ausgesprochen gehört, weil er eine Wahrscheinlichkeitsannahme ist und keine Gewissheit: Die beiden Ausfälle schließen sich vermutlich gegenseitig aus. Wo der Proxy den Download blockiert (Anthropic-gehostete Umgebung), ist `gh` laut derselben Dokumentation vorinstalliert und der Download findet gar nicht erst statt; wo `gh` fehlt, liegt vermutlich keine solche Umgebung vor. Die Beobachtung aus 0309 — eine Umgebung ohne `gh` — passt in keine der beiden Beschreibungen sauber, und genau deshalb wird hier nichts behauptet, sondern gemessen: Der Nachweisschritt der Story beantwortet die Frage in einer echten Session, und der Hook meldet in jedem Fall die Wahrheit über den erreichten Zustand.

### 8. Abgrenzung zu ADR 0052: die Board-Werkzeuge installieren weiterhin nichts

ADR 0052 hält fest, dass `gh-board.py` — insbesondere `doctor` — Zustände **meldet** und nichts repariert. Diese ADR ändert daran nichts und markiert ADR 0052 ausdrücklich **nicht** als `Superseded`.

Die Grenze ist nicht als Absichtserklärung formuliert, sondern an zwei mechanisch nachprüfbaren Merkmalen:

1. **An `scripts/gh-board.py` ändert sich keine Zeile.** Kein Aufruf des Installers, kein Selbstheilungspfad, kein neuer Codeweg. Die einzige Beziehung zwischen beiden Dateien ist lesend und einseitig: `ensure-gh-cli.py` liest `MIN_GH_VERSION`.
2. **Der Installer läuft nie als Folge eines Board-Befehls.** Sein einziger Auslöser ist der Sessionstart. Kein fehlgeschlagener `set-status`, kein rotes `doctor`-Ergebnis, kein `finalize`-Abbruch startet ihn.

Damit sind es zwei verschiedene Dinge zu zwei verschiedenen Zeitpunkten: Die Umgebung wird **vorbereitet**, bevor gearbeitet wird — und das Werkzeug **berichtet** über sie, während gearbeitet wird. `doctor` bleibt die einzige Instanz, die urteilt, und sein Urteil bleibt auch dann zutreffend, wenn die Vorkehrung fehlschlägt: `gh_binary`/`gh_version` sind dann rot, `abschluss-finalisieren` erscheint unter `blocked_lifecycle_steps`. Der Installer kann diesen Befund nicht beschönigen, weil er ihn nicht anfasst.

## Begründung

- **Warum überhaupt eine ADR:** Drei architekturrelevante Dinge fallen zusammen — die erste eingecheckte `.claude/settings.json`, also eine Datei, die ab sofort **jede** Session in diesem Repository beeinflusst, lokal wie remote; ein Hook, der bei jedem Sessionstart Code ausführt, und zwar nachweislich **ohne** Vertrauensdialog und ohne Bestätigung; und der Bezug eines fremden Binaries zur Laufzeit. Jedes für sich wäre nach `CLAUDE.md` schon eine externe Abhängigkeit bzw. eine neue Technologie; zusammen sind sie eine Entscheidung, die nicht nebenbei in einer Feature-Spec entstehen darf.
- **Warum die Vorkehrung überhaupt Code wird, statt in `docs/setup.md` als Anleitung zu stehen:** Die Story verlangt „ohne Handgriff vorab". Eine Anleitung ist ein Handgriff. Der Dokumentationsteil ist deshalb Ergänzung, nicht Alternative — und er bleibt selbst dann fällig, wenn sich herausstellt, dass keine Vorkehrung nötig gewesen wäre.
- **Warum die Zahl nicht in die Dokumentation wandert:** Eine Zahl an zwei Orten ist keine Dokumentation, sondern ein Termin für einen Widerspruch. Der Ort, an dem sie wirkt, ist der Ort, an dem sie gepflegt wird; alles andere liest von dort oder nennt sie gar nicht.
- **Warum der Hook lieber schweigt:** Sein Kanal im Erfolgsfall ist Claudes Kontext. Wer ihn bei jedem Start mit einer Erfolgsmeldung füllt, zahlt Kontext für null Information und macht die eine Meldung, die zählt, unauffälliger. Dieselbe Überlegung wie in ADR 0052 gegen die immer mitlaufende Preflight-Warnung.
- **Warum kein Eintrag in `~/.bashrc`:** Er würde die `PATH`-Frage vielleicht lösen und wäre trotzdem falsch — eine dauerhafte Änderung an der persönlichen Shell-Konfiguration des Nutzers, ausgelöst von einem Repository, das er gerade nur geöffnet hat. Die Anforderung „in lokalen Sessions ändert sich nichts Spürbares" meint genau solche Nebenwirkungen. Ein zutreffender Bericht ist die ehrlichere Antwort als eine stille Änderung an fremdem Eigentum.
- **Warum der Installer in Python geschrieben wird und nicht in Bash**, obwohl `render-diagrams.sh` und `fetch-label-embedder-model.sh` Bash sind und ausdrücklich keine Testsuite haben: Jene beiden umhüllen ein Binary bzw. einen Download — hier steckt echte Entscheidungslogik (numerischer Versionsvergleich, Zielverzeichnis-Wahl, Nachprüfung des eigenen Erfolgs, Fehlerklassifikation), und genau diese Logik trägt die Akzeptanzkriterien („liegt bereits eine ausreichende Version vor, wird nichts nachinstalliert"). Python macht sie ohne Netz und ohne echtes `gh` prüfbar, im bestehenden CI-Job `demo-scripts` und mit derselben Injektionstechnik wie `gh-board.py`. Eine neue Abhängigkeit entsteht dadurch nicht: `python3` ist bereits zwingend, `gh-board.py` ist Python.
- **Warum die Abweichung von der Anbieter-Empfehlung vertretbar ist:** Die Empfehlung „CLI-Werkzeuge gehören ins Setup-Script" optimiert Startlatenz und Cache-Nutzung. Sie kennt die Anforderung nicht, die hier den Ausschlag gibt — dass die Vorkehrung versioniert, reviewbar und in *jeder* Umgebung wirksam sein soll, auch in einer, die es heute noch nicht gibt. Der Preis der Abweichung ist bezifferbar und klein (ein Prozessstart pro Session im Normalfall), das Risiko ist benannt (Abschnitt 7), und der Rückweg steht offen: Erweist sich der Proxy-Fall als Dauerzustand, ist das Setup-Script als *Ergänzung* möglich, ohne diese Entscheidung zurückzunehmen.

## Konsequenzen

- **Neue Datei `.claude/settings.json`** (erste im Repository): genau ein `SessionStart`-Hook ohne Matcher, Kommando `python3 "$CLAUDE_PROJECT_DIR/scripts/ensure-gh-cli.py"`, expliziter `timeout` von 120 Sekunden. Keine weiteren Schlüssel. Sie gilt ab dem Merge für **jede** Session in diesem Repository, auch für alle lokalen, und läuft ohne Bestätigung.
- **Neue Datei `scripts/ensure-gh-cli.py`**: Schnellpfad (Version reicht → Ausgabe leer, Exit 0), `MIN_GH_VERSION`-Lesen aus `scripts/gh-board.py`, Architektur-/OS-Bestimmung, Bezug + Prüfsummenvergleich + atomare Installation nach `$HOME/.local/bin`, Nachprüfung über den `PATH`, Meldung als einzelnes JSON-Objekt mit `systemMessage` und `hookSpecificOutput.additionalContext`. Immer Exit-Code 0. Injizierbare Nahtstellen für Kommandoausführung und Download, damit alles ohne Netz testbar ist.
- **Neue Datei `scripts/tests/test_ensure_gh_cli.py`**, das Skript per Pfad geladen wie die übrigen Skripte mit Bindestrich im Namen. Verbindlich darunter: der Drift-Test gegen `gh_board.MIN_GH_VERSION`; der Nachweis, dass bei ausreichender Version **kein** Download stattfindet und die Ausgabe leer bleibt; der Nachweis, dass jeder Fehlschlag (kein Netz, HTTP 403, sonstiger HTTP-Fehler, Prüfsumme falsch, unbekannte Architektur, `MIN_GH_VERSION` nicht lesbar, unerwartete Ausnahme) mit Exit-Code 0 und einer Meldung endet; der Nachweis, dass niemals außerhalb von `$HOME` geschrieben und nie `sudo` oder ein Paketmanager aufgerufen wird.
- **`scripts/gh-board.py` bleibt unverändert** — keine Zeile. Das ist die tragende Zusicherung aus Abschnitt 8 und wird im Review am Diff geprüft.
- **`docs/setup.md`:** neuer Abschnitt zur GitHub-CLI als Voraussetzung des Entwicklungsablaufs — warum sie gebraucht wird, warum die Distributions-Paketquelle nicht genügt, wo die Mindestversion gepflegt wird, was der `SessionStart`-Hook tut, wie man ihn folgenlos macht (`gh` selbst in ausreichender Version installieren) und was zu tun ist, wenn er einen Fehlschlag meldet. Ohne Nennung der Zahl.
- **Root-`README.md`:** `.claude/` in der Projektstruktur-Tabelle, damit die neue, für jede Session wirksame Einstellungsdatei auffindbar ist statt in einem bislang unerwähnten Verzeichnis zu verschwinden.
- **`.gitignore`:** `.claude/settings.local.json` ergänzen — die persönliche Ergänzungsdatei neben der nun eingecheckten `settings.json` gehört nicht ins Repository.
- **`.claude/skills/github-board/SKILL.md` und `.claude/skills/ship-feature/SKILL.md`:** die wörtliche Zahl `2.72.0` weicht dem Verweis auf die gepflegte Konstante (Abschnitt 6). Sonst keine Änderung an den Skills.
- **Kein Effekt auf `docs/architecture.md`** — Entwickler-/Prozess-Tooling ohne Bezug zu Laufzeitarchitektur oder Datenmodell, gleiche Einordnung wie ADR 0017/0033/0037/0043/0046/0052. `docs/ai-workflow.md` bleibt unberührt: Ablauf und Rollenmodell ändern sich nicht.
- **Keine Datei unter `.github/workflows/`, kein neues Secret, keine neue Laufzeit-Abhängigkeit von Backend oder Frontend, keine Änderung an Board-Feldern.**
- **Ein manueller Nachweisschritt, der nicht beim `developer` liegt:** In einer frisch gestarteten Remote-Session auf dem Branch `gh --version` ausführen und das Ergebnis an Issue #314 dokumentieren — wie der Remote-Durchlauf in ADR 0052 Sache Daniels bzw. des Orchestrators, sinnvollerweise nach PR-Eröffnung und vor dem Merge. Ein vollständiger schreibender Lebenszyklus-Durchlauf ist ausdrücklich nicht gefordert. Derselbe Schritt beantwortet nebenbei die beiden lokal unbeantwortbaren Fragen: ob `gh` in einer frischen Umgebung vorinstalliert ist (Widerspruch aus Kontext-Punkt 6) und, falls nicht, ob der Bezug am Proxy scheitert. Beide Antworten sind Befunde für eine Folge-Story, keine Korrektur nebenbei.
- **Ausdrücklich nicht Teil dieser Entscheidung:** weitere Werkzeuge (`jq`, `yq` …), ein Absenken von `MIN_GH_VERSION`, ein Rückbau der `closingIssuesReferences`-Prüfung, ein Nachweis von Schreibrechten, autonom laufende Agenten. Ebenfalls nicht Teil: die Frage, ob Projects-V2-Aufrufe über den Cloud-Proxy überhaupt zugelassen sind — das betrifft den Lebenszyklus *nach* dieser Vorkehrung und gehört in die von ADR 0052 Abschnitt 1 offen gelassene Folge-Story.
- Ein späterer Wechsel dieser Entscheidung (etwa: doch das Setup-Script der Cloud-Umgebung, doch ein `Setup`-Hook-Ereignis, doch ein Devcontainer, ein Bezug aus einer anderen Quelle als `cli/cli`, oder eine Vorkehrung, die den `PATH` des Nutzers verändert) bleibt architekturrelevant und braucht eine neue, diese ADR als `Superseded` markierende ADR.
